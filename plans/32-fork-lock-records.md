# Plan 32: forks that inherit a connection, and the review's Full-tier fixes

Status: in progress on the `plan-32-fork-lock-records` branch; steps 1 to 6 (the spike, A: the unusable level, B: inert shares, C: the checkpoint, D1 to D6, docs) are done (see the Log); step 7 (the gate and the release) is next, after two questions for Michael recorded at the end of the Log. Drafted 2026-11-19. Reviewed once by the-rust-architect, whose three blockers and its should-fixes are folded in below (see the Log). Michael was interviewed on three decisions and then on the four the review opened, and took the recommended option on six of the seven (decision 2 is his own: the Patch-tier fixes ship first). Every decision is made; nothing is built yet.

The bug, race and security review of 0.4.6 (2026-11-19: a Gemini pass, then four focused reviews, each finding re-run or traced before it was accepted) ended with two fork bugs that need design, one one-line checkpoint fix in Full-tier code, and four smaller findings that touch Full-tier files or need a divergence. This plan covers all of them in one Full-tier release. The review's five Patch-tier fixes (the Django batches, `pull()`, `check(fix=True)` on a file it can't look at, `remove_old_formats()` on shards it can't judge, the JSON depth charge) ship first, as 0.4.7, and aren't part of this plan.

## What's known (reproduced 2026-11-19 on the built 0.4.6, macOS, Python 3.14)

**A. A child that inherits an open connection holds no kernel lock on that database.** SQLite keeps one lock record per database file per process, and a new connection that finds the record saying the process already holds SHARED takes no `fcntl` lock of its own. `fcntl` locks aren't inherited across `fork()`, but the record is. `pool.rs`'s module docs name exactly this hazard, and `close_idle_all` in the before-fork hook exists to avoid it, but three paths get past it:

- *A held transaction on the forking thread* (`os.fork()` inside `with cache.transact():`). The child is write-poisoned (D-020) but D-020 promises "Reads, and other cache directories, keep working". They don't: once the parent closed, reopened and wrote `a = 2` and `new`, the child still read `a = 1` and no `new`, and the parent's close had deleted the WAL and shm while the child had a live connection.
- *A lease live at the fork* (`os.fork()` from a pickle hook inside `get`). The child isn't poisoned at all: three `set()` calls returned True and a fresh open found none of them. Reported by the reviewer; not re-run by me.
- *A connection checked in between the hooks.* A before-fork hook registered before `diskcache_oxide` was imported runs after ours; if it uses the cache, `Pool::checkin` idles that connection after `close_idle_all` has already run. Same outcome: three child sets returned True and were lost. The gate lets the forking thread in between its hooks on purpose (`the_forking_thread_never_times_out_between_its_hooks`).

The child forgets inherited connections rather than closing them, which is right (closing one mid-transaction would undo the parent's frames in the shared wal-index, and any close can release state the parent relies on), so the record stays for the child's life. A fork whose before-hook never ran (CPython ignores a before-hook that raises) inherits every idle connection the same way. `parent_closes_after_fork` and `fanout_close_after_fork` in `tests/unit/fork_scenarios.py` do have the parent close while the child lives, but only for the clean case, where the child inherited nothing; no test does it with a connection open at the fork, which is why none of this showed.

**B. A cross-thread end caught mid-wait by its owner's fork strands a gate level in the child.** Thread A is in `transact()` and forks; thread B is in `tx.__exit__()` for that transaction, has moved the `HeldTransaction` onto its own stack (the Python object is `Ending`), and is waiting in `HeldShare::enter_until` behind A's fork. In the child B doesn't exist, so nothing can ever drop that share: `reset_in_child` counts it among A's own levels (`counts = own_depth()`), the gate shows one holder for good, `os.fork()` from another thread in the child hangs (`quiescent` sees `holders 1 > own 0`, and `begin_fork` has no timeout), A's `__exit__` waits out its timeout and raises `Timeout`, and A's `own_depth() > 0` changes how its writes wait on every store. The same loss happens while B sleeps in the `Lent` poll (`LENT_POLL`, with the interpreter released). Two shorter windows were traced, between `enter_until` returning `None` and `park` dropping the share, and between `drop(gate)` and `self.share.take()` at the tail of `end`; B is attached to the interpreter in both, and a fork lands only while other threads are detached or stopped, so they are probably unreachable from Python (step 1 confirms) but are modelled all the same. The parent is always fine. Reproduced with a sleeping before-fork hook to widen the window.

**C. The background checkpoint reads "busy" as "all copied".** `PRAGMA wal_checkpoint(PASSIVE)` returns `(1, -1, -1)` when another connection holds the checkpoint lock (confirmed with an `fcntl` lock on byte 121 of the shm). `Store::background_checkpoint` drops column 0 and tests `log != copied`; `-1 == -1`, so it takes the write lock and runs TRUNCATE. If the other checkpointer finishes in that gap, the whole copy runs under this process's write lock on the maintenance thread, which the function's doc says can't happen. Latency only. `turn.rs:270`'s comment ("Busy backs off on its own") is stale too.

**D. The smaller findings.**

1. A row whose `filename` isn't TEXT (`UPDATE cache SET filename = x'fffe'`) makes `get`, `delete`, `clear()` and `check(fix=True)` raise `OSError: Invalid column type Blob`, and the row stays. Every read of the column is a typed `get::<Option<String>>` (`ops.rs`, `rows.rs`, `maintenance.rs`, `check.rs`). Traced, not run: eviction's `RETURNING size, filename` fails the same way, so once that row is the oldest every `set` that must evict raises. D-013 promises a damaged row reads as a miss.
2. `incr('n', float('nan'))`, or `+inf` then `-inf`, stores a NaN, which SQLite binds as NULL: the row is mode 7 with no value, `get` raises `CorruptValueError` (or deletes it as a miss), and a later `incr` raises `TypeError`.
3. `check(fix=True)` removes any file in a value folder that's over an hour old and that no committed row names. A transaction held open for over an hour has written such a file; another process's `check(fix=True)` unlinks it, and the commit lands a row with no file. D-042 says the sweep leaves a `.val` alone for exactly this reason; `check` doesn't.
4. A handle's `types=` registry shadows the global one by name on decode but not on encode: with `Money` global under `'x'` and `Token` local under `'x'`, `c['m'] = Money(5)` encodes through the global entry and decodes through the local one, returning `Token(cents=5)`. Plan 16 makes the one-registry version of this a `TypeError`. Reported by the reviewer; not re-run by me.
5. `Store::vacuum` gives the write lock and VACUUM one deadline, then starts a fresh `timeout` for the checkpoint, so `check(fix=True)` can wait about twice its timeout.
6. `TakeAllStack<T>` gets its auto traits from `PhantomData<T>`, so it's `Sync` when `T: Sync`. It moves values between threads through `&self`, so the sound bound is `T: Send`. Latent: both uses are `Send + Sync`.

## Decisions (Michael, 2026-11-19)

1. **A child that inherited an open connection to a database can't use that database at all.** Every call on it in that child raises, for the life of the child; other caches, and a `FanoutCache`'s other shards, work. D-020 changes from "reads keep working" to this. The alternative, re-taking by hand the `fcntl` locks SQLite believes the child holds (the database file's SHARED range, the shm's DMS and read-mark bytes), would keep reads working but needs `libc` and `unsafe` and is tied to the bundled SQLite's lock layout. Refused: a loud error beats a read that can silently go stale.
2. **The Patch-tier fixes ship first, as 0.4.7**, after the patch gate. This plan's release follows it.
3. **All four smaller findings (D1 to D4) are in this plan.** D5 and D6 ride along on my recommendation: each is a few lines in a file this release already gates.

From the architect's review, decided the same day; Michael took the recommended option each time:

4. **A `durable=True` handle on an unusable database.** `Unwritable` is an operational error today, so a durable handle swallows it: in such a child every read would be a miss and every write dropped, for the life of the process, with only a log line. Decided: `Unusable` is not operational and raises on a durable handle too. Durable is for an outage that may pass; this never passes, and a worker silently running without its cache forever is what decision 1 set out to avoid.
5. **What still works on an unusable database.** Decided: `close()`, the attribute getters that answer from memory (`directory`, `timeout`, the settings), `repr`, and pickling the handle. Everything that would touch the database raises, `stats()`, `len` and `volume` included.
6. **`FanoutCache`.** Only the shard whose database was open at the fork is unusable. Decided: keyed calls on other shards work, any call that covers every shard (`len`, `clear`, `expire`, iteration, `check`) raises, and a fresh `FanoutCache(root)` opened in the child raises at open, since it can't open that shard.
7. **Other damaged columns (D1).** The review found the same poison-row problem for `size`, `mode`, `expire_time` and `store_seq`: a non-integer `size` makes `set`, `delete` and `clear()` raise and `check()` itself raise; a damaged `mode` or `expire_time` makes `get`, `set`, `delete` and `incr` raise. Decided: `filename` and `size` in this plan (they're the two that block eviction and `clear()`), with `check` gaining a `typeof()` pass that reports and, with `fix`, removes a row whose `mode`, `expire_time` or `store_seq` has the wrong type; making every reader lenient about those three stays out.

## Design

### A. Poison what was inherited, and inherit less

**A1. One rule in the child.** In the child's after-fork hook, while the forking thread is the only one, every database file this process inherited an open connection to is poisoned for all access. That covers a held transaction, a lease live at the fork (the forking thread's, or one held by a thread parked in `begin_fork` inside a hook, which nothing catches today), a parked end's transaction, a connection idled between the hooks, and a fork whose before-hook never ran, with one check. How it's computed:

- A pool learns its file: `Pool::new` takes the `FileId` and keeps it in `PoolShared` (today only `Store` has it, and the pool registry is `Vec<Weak<PoolShared>>`).
- The scan is a `pool.rs` function with no `SharedGuard`, like `close_idle_all`. It never calls `reset_if_stale` (which forgets stale connections and would erase the evidence) and flags any pool with `!idle.is_empty() || checked_out > 0`, whatever its generation.
- It runs in `end_fork_child` after the generation bump and before the gate reopens.
- The scan never blocks. When the before-hook didn't run, `quiesce_all` didn't either, so the pool registry or a pool's mutex can be inherited locked by a thread the child doesn't have (`tests/unclaimed_fork.rs` names the hazard). The scan uses `try_lock` only: a pool it can't lock is poisoned by its `FileId`, and a registry it can't lock sets a process-wide "every store unusable" flag. That keeps the scan from hanging, not the child: one that inherited a mutex locked can still block on it at its next blocking `lock()` (`resume_after_fork` takes the store registry on the next line), as it always could. Making every such lock skippable is outside this plan.
- `poison_live_holds` inserts into the unusable set as well as the unwritable one, so the held-transaction case never depends on a mutex.
- `checked_out` becomes load-bearing (only tests read it today): a test that a failed `connect` and every `Lease` drop path return it to 0.

A store's pin connection lives outside the pool (`Store.pin`) and never runs a statement, so the scan doesn't see it; step 1 confirms SQLite's record for a file with only such a connection is harmless (a new connection takes its own `fcntl` lock). The other connections outside the pools (`open_store`'s, `read_format`'s) open and close under one gate level with no Python callback, and the maintenance thread is joined before the claim, so none can be open at a fork.

**A1b. No lockless call before the scan.** `enter_child_early` fires only at gate depth 0. After a fork from a hook inside `get`, another library's `after_in_child` hook that runs before ours makes a nested call at depth 1, before the generation bump and the scan, on a fresh connection under the inherited record. It fires at any depth while this thread's `forking` flag is set.

**A2. Two levels in the poison registry.** `poison.rs` keeps its atomics-only shape and gains a second set: *unusable* beside *unwritable*. `check_usable(id)` is one relaxed load in a process that was never poisoned, as `check_writable` is. It sits in `Store::lease`, which every read and write goes through (the review found no path that leases any other way). `check_writable` itself reports `Unusable` for an unusable file, so every existing early check gives the stronger message with no second call. For an open it sits in `lookup` and in the slow path before the connect, and in `layout::read_format` (which `cleanup` goes through too). Every one of those is placed after the gate entry, never before: in a child, the first gate entry is what runs the scan when another library's `after_in_child` hook gets there before ours, so a check made before it reads a registry the scan hasn't filled (the architect's step 1 review; the earlier `check_writable` calls keep that gap and only fail sooner, with `lease` as the backstop). `on_pinned` checks it too, ahead of `ForkPoisoned`, so a child still inside an inherited `with` block gets the same error as everywhere else on that cache. So a fresh handle on a poisoned file in the child raises instead of opening a lockless connection. Poison stays keyed by inode and is inherited by grandchildren. Background maintenance already skips a poisoned store; it skips an unusable one the same way.

**A3. The error.** A new `Error::Unusable`, raised to Python as `RuntimeError` like `Unwritable` and `ForkPoisoned`, saying what happened and what to do: this process was forked while a connection to this cache was open on the forking thread (inside a transaction, or from a hook inside a cache call), so it can't use this cache; fork outside the transaction, or start the worker with spawn or forkserver. A `durable=True` handle raises it too (decision 4).

**A4. Don't idle a connection while this thread is forking.** `Pool::checkin` and `Pool::adopt` (a cache opened between the hooks idles one too) on the thread that holds the fork claim close the connection instead of idling it, with `NO_CKPT_ON_CLOSE` set as `close_idle_all` sets it. The claim is `ThreadState::forking`, private to the gate today: a `SharedGuard` accessor exposes it, and the check reads `pending` first so the hot check-in pays one relaxed load. It also compares the pid with the one `begin_fork` ran in, so it's never true in the child, where the claim is still set until `end_fork_child` runs and a close would be of a connection the parent owns. So a before-fork hook that uses the cache after ours leaves nothing behind, and the child isn't poisoned for it. A lease still out at the moment of `fork()` is the hook-inside-an-operation case and falls under A1.

**A5. The parent** is unchanged: it keeps its transaction, its `RuntimeWarning` for forking inside one, and everything it had.

### B. A share that crossed a fork counts for nothing in the child

The root cause is that a `HeldTransaction` can be on a thread's stack that the child won't have. Shrinking the windows (waiting before taking it out of the Python object) can't close the last few instructions, so the fix is on the child's side. My first design marked a share "away" while another thread held it and discounted the marked ones at the fork; the architect showed it wrong twice over (a count beside `Owner::levels` can't be updated atomically with it, so a fork between the two under- or over-discounts, and epoch 0 collided with "not away") and gave the simpler design below, which needs no marker, no count and nothing in the Python layer.

**B1. Every share that crossed a fork is inert.** A `HeldShare` records the gate epoch it was created in, and `try_enter` and `drop` test that instead of `owner.epoch`: a share from an older epoch enters as `Inherited` and drops without touching the counts. `reset_in_child` clears the forking thread's held count (keeping the flags) and sets `counts` to its guard depth only. So in the child no share counts, reachable or not: the stranded one can't block a fork, and a reachable one (the child's own copy of an inherited transaction) drops as a no-op.

**B2. A side effect, wanted.** A child sitting in an inherited `with cache.transact():` block stops reading as `own_depth() > 0`, so its calls on other caches wait for locks as anyone's do (`store.rs`'s write and slot waits, `check`'s refusal) instead of behaving as if inside a transaction. The existing tests that assert a child's holders include its held levels change to guard depth.

**B3. The child's `Transaction` object.** `Ending` records the process generation it was entered in. In a later generation `__exit__` raises the fork `RuntimeError` at once, instead of waiting out the timeout and raising `Timeout`, and the state becomes `Done { committed: false }`. `wait_for_end` takes the state mutex while detached, so a fork can land with it held by the lost thread: the generation is checked before the mutex is touched.

**B4. What's left stranded in the child** is the slot (`Here`, parent's generation), the write word and the hold. With decision 1 that database is unusable in the child anyway (the hold poisons it), so none of it is reachable. `HELD_STORES` is reset to 0 in the child, and an end of an inherited transaction doesn't decrement it, which also fixes the known slow-path-forever limitation the review noted. `set_pinned_active` gets the same generation check (its callers hold the slot and pass it; `Lend::drop` too).

**B5. Proof.** A shuttle model in `gate/model.rs` for "an ender at `end_child`", at each of the four points, asserting the child's holders equal its guard depth and a second fork in the child completes. No existing model calls `end_child`, and shuttle has no fork, so the model simulates the missing thread by forgetting the share at that point. Python scenarios for the two reachable windows: the `enter_until` wait (the reviewer's `phantom` repro) and the `LENT_POLL` sleep.

### C. The checkpoint

The PASSIVE row's first column is read: `busy != 0 || log != copied` is `Outcome::Busy`. The decision moves into a small pure function over the row so the three cases (`(0, n, n)`, `(0, n, m)`, `(1, -1, -1)`) are unit-tested without a second process, plus one integration test in which another connection holds the checkpoint lock (corrected in step 4's review: a connection in the same process can hold it against ours, so no second process is needed) and the turn reports busy. The stale comment in `turn.rs` goes.

### D. The smaller fixes

1. **Non-text `filename`, non-integer `size`.** One helper reads the two columns from a row leniently and returns a name that can't be a value path when the column isn't TEXT (and a size that can't match when it isn't an integer), so every caller's existing "damaged row" path runs: a miss on read, nothing unlinked on delete, `BadFilename` from `check`, and `fix` removes the row. Used at every site that reads the columns today (`ops.rs`, `rows.rs`, `maintenance.rs`, `check.rs`); a grep test keeps a typed `get::<Option<String>>` on `filename` from coming back. Three things the review caught: `check_rows` pages with `filename > ?1` on a `String`, and a BLOB sorts after every TEXT, so a lenient read would return the blob row on every page forever, so the cursor is kept as the raw SQLite value; a sentinel size must never reach `adjust_totals`, so a non-integer size counts as 0 there and in `check_totals` (whose `SUM(size)` comes back REAL and raises today); and `fix` must reach an inline row with a damaged size, which the spilled-rows index never visits. The other damaged columns are decision 7. No format change: nothing we write differs.
2. **`incr` and NaN.** `incr` and `decr` raise `ValueError` for a non-finite `delta` or `default`. With non-finite operands refused, no NaN can be reached: an overflow does store a native infinity (the review's probe: mode 7, REAL `inf`), but an infinity plus a finite number stays that infinity, and NaN needs the opposite infinity or a NaN as an operand. A row an earlier version already left NULL stays unreadable until it's read as a miss or overwritten; the changelog says so. A new divergence, D-064; step 5 runs diskcache first to record what it does.
3. **`check(fix=True)` and a held transaction.** A file no row names is removed only inside a short write transaction: `BEGIN IMMEDIATE`, ask again whether a row names it, unlink, end. With the write lock held no other connection has an uncommitted row, so the answer is final. A transaction held elsewhere makes that step raise `Timeout`, as the VACUUM after it does today; orphans already handled stay removed. The lock is taken per orphan, not for the scan, and the unlink sits in a `Store::write` closure, which may run more than once, so it treats a file already gone as done. A writer whose file was unlinked before it began fails in `commit_name` (the rename runs inside its transaction and refreshes the mtime) rather than committing a row with no file. D-050 and D-042 are updated.
4. **`types=` shadowing.** When encoding reaches a class through the global registry and the handle's own registry holds that name for a different class, `set` raises `TypeError`, as plan 16 does within one registry. Checked at encode, not at open, because global registrations can come later. One extra lookup, only on a global hit on a handle that has a local registry.
5. **`vacuum`'s budget.** The checkpoint after VACUUM gets what's left of the one deadline.
6. **`TakeAllStack`'s bounds.** The marker becomes one that doesn't lend the stack `T`'s `Sync`, with explicit `unsafe impl<T: Send> Send` and `Sync` and a SAFETY comment (the module's `allow(unsafe_code)` covers them); a const not-impl assertion inside the module pins that a `Sync + !Send` type can't be shared through it (the stack is `pub(crate)` in a private module, so a `compile_fail` doctest would fail on name resolution and prove nothing), and `store.rs`'s comment on its own assertion is updated.

Not in this plan: `STOPPED_FOR_FORK` on the stale-fork-guard path (no way found to reach it), `check(fix=True)` clearing non-oxide files from two-hex folders (D-050, deliberate), `expire=nan`, a key iterator parked behind a fork being unusable in the child, the commit's I/O with the interpreter held, `peek`'s per-pass timeout, a symlinked `.val` being followed. They stay on the review's list.

## Risks

- **A1 poisons too much.** If an idle inherited connection turns out to be common in a path we haven't thought of (step 1 lists them), children that work today would start raising. The scan's log line names the file and why, and step 2's "later hook uses the cache" scenario is the guard for the one known path.
- **B changes what a child's held levels mean.** Code that reads `own_depth() > 0` in a child inside an inherited `with` block now sees 0 (B2). That's the intent, but every reader of `own_depth` is checked in step 3, and the tests that pinned the old count change with it.
- **D1 touches the row readers in `ops`, `rows` and `maintenance`.** The helper changes only what a non-TEXT column decodes to; the conformance suite and the soak's corruption checks cover the rest.
- **A fork with no before-hook, plus another library's earlier `after_in_child` hook.** The early child entry is keyed on the forking flag, which only the before-hook sets, so that hook's cache call runs on the parent's connections before the scan. It predates this plan and stays outside it: nothing in the engine sees that fork until our own after-hook runs.
- **A lost end, seen before our after-hook.** `Transaction.__exit__` and `repr` tell a lost end by the process generation, which our after-fork hook bumps. Another library's `after_in_child` hook that runs first and touches such a transaction still sees the old generation and takes the state mutex, which the child may have inherited locked. Contrived (three threads, and a hook that ends someone else's transaction), and left.
- **The background TRUNCATE can still copy under the write lock** (the architect's step 4 review; beyond finding C, and left). PASSIVE's row counts the WAL as it was when PASSIVE began, so frames committed while it copied, by this process or another, and by other processes until TRUNCATE takes SQLite's write lock, are copied by that TRUNCATE under our write lock: about the write rate times PASSIVE's duration (up to 1.4 s seen in the soak), with no bound. Latency only, and it needs no second checkpointer, so it happens in normal operation under sustained writes. The follow-up fix is to repeat PASSIVE without the lock until a round is quick, and only then try TRUNCATE.
- **The soak can't see A or B directly** (it doesn't fork inside transactions today), hence the new fork worker in step 7.

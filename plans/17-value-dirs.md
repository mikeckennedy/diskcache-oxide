## 1. The problem

A value of 64 KiB or more lives in its own file at `aa/bb/<32 hex>.val` under the cache directory (`spill.rs`). `PendingFile::write` creates `aa/bb` with a recursive `DirBuilder` as needed, and nothing ever removes a directory: `Store::unlink`, `PendingFile::discard` and `write_new`'s cleanup remove only files. So every `aa/bb` pair a store has ever used stays, empty or not.

Measured on the htz soak (x86-64, ext4, 3.65 h in, 2026-11-06):

| Store | Directories | Empty | Files |
|---|---|---|---|
| fanout (8 shards) | 230,339 | 228,315 | 69 |
| durable | 64,319 | 63,934 | 132 |
| behind | 31,200 | 30,940 | 6 |
| chaos | 18,636 | 18,279 | 105 |
| ledger | 15,796 | 15,515 | 27 |

The fanout store was 959 MiB on disk for about 40 MiB of live data. The ceiling is 256 + 256 × 256 = 65,792 directories per store (each FanoutCache shard is a store): about 257 MiB at 4 KiB a directory, and 65,792 inodes. A default FanoutCache reaches about 2 GiB and 526,000 inodes. It takes nothing unusual to get there: a few hundred thousand large-value writes or deletes over a cache's life, which Talk Python's caches will see. On APFS directories are cheaper in bytes, but the inode and directory-entry cost is the same.

## 2. What diskcache 5.6.3 does

diskcache removes them. `Disk.remove(file_path)` (core.py:312) unlinks the file, then calls `os.removedirs(full_dir)`, both under `suppress(OSError)`: `removedirs` removes `aa/bb`, then `aa`, stopping at the first that isn't empty (the cache directory always holds the database, so it stops there). `Cache.check(fix=True)` also walks the tree and `rmdir`s every empty directory (core.py:1979). The write side copes with the race this opens: `Disk.store` loops up to 10 times over `os.makedirs(full_dir)` then `open(full_path)`, because "another cache may have deleted the directory before the file could be opened" (core.py:233).

Oxide differs from the oracle today, untested: no D-entry exists for it, and no conformance test looks at directories after a delete. The design in section 3 differs from diskcache on purpose (one level, and a sweep instead of removal on delete), so it gets D-entries. The end state after a close matches diskcache's for any directory untouched for 30 seconds (no empty directory left); the black-box tests backdate the directories' mtimes before closing to check it (review 2, change 1).

Two places diskcache does more than we will (section 9): `os.removedirs` would climb past `aa` if it could (it stops at the cache directory only because the database lives there), and `os.makedirs` is recursive, so diskcache re-creates a deleted cache root on its next large write. And one where it does less: a value file written inside a rolled-back `transact()` leaks, because `_transact` removes files only on commit (core.py:732-747; confirmed on 5.6.3 by the architect). That leak is an upstream bug for `upstream/README.md`.

## 3. Decision (Michael, 2026-11-06)

**One level of 256 directories, `aa/<32 hex>.val`, removed only by a sweep, not on every delete.** Two earlier designs, both reviewed in section 9, are superseded: A (two levels, a directory removed when its last file goes, as diskcache does) and C (one level plus that removal). Backward compatibility doesn't matter here (Michael: we already use our own file format), so existing caches are deleted once at deploy and nothing reads or migrates the old two-level shape.

Why flat 256 and no removal on delete. With removal, a directory goes only when its last file does, so it pays off only when directories far outnumber live files, which is exactly today's 65,536 and the reason for this plan. At 256 the worst case without any removal is 256 directories, about 1 MiB and 256 inodes per store (8 MiB and 2,048 at 8 shards), so per-delete removal would buy almost nothing for its cost: two directory updates per large write-and-delete in a sparse cache, a race on every one, and a mixed-version deploy hazard. Not 1,024: four times the worst case, and its advantage (a quarter of the entries per directory) only matters in the millions. A million live value files is about 3,900 per directory, which ext4's htree and APFS index without trouble; diskcache's two levels were for "older filesystems". Talk Python's caches will hold thousands.

Why a sweep anyway (Michael). With few live files most of the 256 stay, but once a cache's large values are gone, and across a FanoutCache's shards, the empties add up, and a sweep at 256 entries is a few milliseconds.

## 4. Design

### 4.1 Layout and the write

`PendingFile::write` names a new file `aa/<32 hex>.tmp`, renamed to `.val` at commit, where `aa` is the hex's first two characters. A `pub(crate) fn write_named(directory, hex, data)` does the work and `write` calls it with `random_hex()`, so core tests can put any number of files in one directory with no static state (review 1, change 5).

The create loop, inside `PendingFile::write`'s existing `run_blocking` closure, non-recursive and relative to the cache directory:

1. `mkdir(directory/aa, 0700)`. `AlreadyExists` means go on, with no `stat` (review 1, change 1: an `is_dir()` after `EEXIST` races a sweep and turns a retry into a hard failure). `NotFound` is terminal at once: with a non-recursive `mkdir` it means the cache directory is gone, and nothing in oxide removes that (review 1, change 2). Anything else is terminal.
2. `create_new(directory/aa/<hex>.tmp)`. `NotFound` means a sweep removed `aa` after step 1: restart at step 1. `NotADirectory` (`aa` is a file) and anything else are terminal.

At most 64 rounds, then the `NotFound` is returned as the write's `OSError` naming the path. No sleep. Since only a sweep removes directories, and each sweep visits a directory once, a racing writer loses at most a round or two per sweep; the bound is for a pathological loop, not for traffic.

A terminal error after this call made `aa` tries `rmdir(aa)` before returning (ignoring every error), so a failed create (`EMFILE`, `ENOSPC`, `EACCES`, `EDQUOT`, or the 64th `NotFound`) doesn't leave an empty directory it made (review 1, change 3). Not required for correctness now, since the next sweep would remove it, but it keeps the tests' "no empty directory" assertions exact.

The non-recursive create closes plan 15's known note: a process still holding a shard open after its root was deleted no longer re-creates `root/000/aa`. Its large write fails with `OSError` after one `mkdir`, where diskcache's recursive `makedirs` re-creates the tree and succeeds, while a small `set` in oxide still succeeds into the unlinked database. Test-visible against the oracle, so a D-entry (review 1, change 7a).

`commit_name`'s rename stays within one directory, and the `.tmp` keeps it non-empty from `create_new` until its owner renames or removes it, so neither a rename nor a held transaction's uncommitted file can lose to a sweep. Readers are unchanged: a missing directory is `NotFound` like a missing file (D-013, D-016).

Deletes, overwrites, `cull`, `expire`, `clear`, eviction and the end of a held transaction keep unlinking files only, as today (`Store::unlink`, `PendingFile::discard`). No per-delete cost.

### 4.2 The sweep

`spill::sweep(directory, deadline, min_age, start)` lists the store's directory, and for each entry whose name is exactly two lowercase hex characters, tries `rmdir` if the directory's modification time is at least `min_age` old: 30 seconds on close (Michael, 2026-11-06), zero on `clear()` (review 2, change 1: `clear()` has just touched every directory it emptied, so a 30 s filter would make its sweep remove nothing). The mtime is read with `symlink_metadata` (no following links); a future mtime or a failed `stat` counts as young. `start` is the entry to begin at (random in production, from `RandomState`; a parameter so tests can pin wrapping); an already-passed `deadline` sweeps nothing. A directory's mtime changes whenever an entry is added to or removed from it, so the age check leaves alone any directory a writer or a delete has touched recently: no churn on hot directories, and a writer that has just made a fresh `aa` and not yet created its file is never raced. It does not close the race, which is why 4.1's retry stays: a writer whose `mkdir` found an old directory (`AlreadyExists` doesn't change its mtime) can still lose it to a sweep between that `mkdir` and its `create_new`, and the age check and the `rmdir` are two steps anyway. One `stat` per entry, at most 256. A directory with files fails at once (`DirectoryNotEmpty`, or `EEXIST`, which POSIX also allows), a file named `ab` fails with `NotADirectory`, and every error is ignored. It removes nothing but empty directories and never removes a file: a `.tmp` may be another process's write in flight (review 1, change 9). It never recurses, so a leftover two-level tree from an old cache isn't touched (`aa` holds `bb` and isn't empty), and it never looks at anything else in the directory: a FanoutCache shard folder (`000`), the database, the user's own files. It runs in a store's own directory, never a FanoutCache root, so a FanoutCache sweeps each shard. It starts at `start` and wraps, and stops at `deadline`, so a sweep cut short leaves the rest for the next one without storing any state. It never raises and returns nothing.

When it runs (review 2, changes 2 to 4):

- **On close, decided by the release itself.** Today "last handle" is a `handles == 1` check before the release (store.rs:1069-1072), so two threads closing the last two handles at once could both see 2 and neither sweep. Instead `release_under` (store.rs:709-718), which knows for certain whether this release retired the store, returns that, and the sweep runs after the release, with no gate level held. Order: checkpoint-on-close, release, sweep. Skipped if the thread still holds a gate level (`GATE.own_depth() > 0`). Not skipped in a fork child: removing an empty directory never touches SQLite, so D-020's reasoning doesn't apply. Not tied to `checkpoint=`: that flag is documented as a WAL switch, and the sweep never waits on other processes, so no new flag either (review 2, answer 1).
- **On drop without `close()`.** A handle dropped without `close()` releases with no checkpoint (cache.rs:1048-1063, cache/fanout.rs:908-923); it sweeps the same way when its release retires the store. No `atexit` hook. A process that dies with neither leaves at most 256 empty directories per store, swept by a later close.
- **On `clear()`:** after the chunk loop, with no write lock or gate level held, with `min_age` zero. Skipped inside a held transaction (its files go at commit) and when the clear was `Interrupted`. Never changes `clear()`'s return.
- **Budget.** The sweep has its own budget, not `clear()`'s timeout: maintenance deadlines bound waiting, not work (maintenance.rs:9-14), and the sweep never waits. A FanoutCache's close or `clear()` shares one deadline across its shards (store/shards.rs:89-98), not one each. The figure is a placeholder, 100 ms, until step 4 measures how long a sweep really takes (4.4).
- **With the interpreter released**, through `gate::run_blocking` called from core after the release, for a plain store and for a FanoutCache alike (review 3, change 3). Held, a sweep stalls every other Python thread on a GIL build and holds off every stop-the-world (GC, the pause before `os.fork()`) on 3.14t, and a cold sweep on network storage may take hundreds of milliseconds. `run_blocking` runs inline when the large-WAL close path has already detached, so there's no double detach. This replaces review 2's "attached for one store" (answer 2), which assumed local-disk speeds: one store's 256 folders on a cold network volume are about 256 round trips (review 3, suggestion 1). The cost is getting the interpreter back once per last-handle close, up to the 5 ms switch interval under contention; step 4 measures it with a second busy thread. Decided without the `sdc` number (Michael left it to me): releasing costs a few ms at worst, holding could cost far more.
- `debug_assert_eq!(GATE.own_depth(), 0)` where core calls the sweep (the single-store release, `close_all_within`, `clear_from`), so every debug run checks it never runs with a gate level held (review 3, change 7).

A sweep is one more remover for a racing writer, which 4.1's loop handles.

### 4.3 Filename validation

One shared `value_path` parser, used by every place that turns a stored `filename` into a path (`Store::unlink`, `spill::read`, `spill::open`), accepts exactly `[0-9a-f]{2}/[0-9a-f]{32}.val` and builds the path from those parts. `directory.join` follows absolute paths and `..`, so today a damaged row can make `unlink` remove a file outside the cache (review 1, change 4 and suggestion 1). An invalid `filename` reads as a missing value (the D-013 path: a miss, and the row is deleted) and unlinks nothing. A miss rather than a raise matches D-013, and deleting the row repairs it (review 2, answer 3). An old two-level cache that someone didn't delete would degrade silently to misses and keep its old files and up to 65,792 directories forever, since validation won't unlink the old names and the sweep doesn't recurse; section 8's format-version question is about that.

### 4.4 Part 2: sweeping a FanoutCache's shards in parallel (Michael, 2026-11-06)

Production caches may sit on network block storage (a Hetzner Volume, EBS), where each uncached `stat`, listing or `rmdir` of a non-empty folder (ext4 reads its data block, `ext4_empty_dir`) waits a network round trip, and the device handles many requests in flight far better than one at a time. A FanoutCache's close and `clear()` therefore sweep its shards in parallel, with sequential built beside it so step 4 compares them. As the third review (9.3) requires:

- `spill::sweep_all(directories, deadline, min_age)` uses a bounded pool: `SWEEP_THREADS = 8` in total, the caller included (a constant, not `available_parallelism()`: the work waits on I/O, and htz's container has 4 CPUs). An `AtomicUsize` index hands out shards; the caller spawns `min(SWEEP_THREADS, shards) - 1` helpers and then pulls work itself, so a helper that fails to spawn just means fewer pullers and the caller always drains the list. Not one thread per shard: `MAX_SHARDS` is 256 (change 2).
- Helpers start with `thread::Builder::new().name("dco-sweep").stack_size(256 KiB).spawn_scoped(...)`, which returns an `io::Result` where `Scope::spawn` would panic, and every `ScopedJoinHandle` is joined by hand with its `Err` dropped, so a panicking helper can never re-panic into `close` or `Drop` (change 1).
- They run no Python and take no gate level, lock or connection: only list, `stat` and `rmdir`. A fork from another thread proceeds at once (sweep threads aren't gate holders), and a fork already pending at close defers every release, so nothing sweeps (9.3, checked against the code). Spawning during `Py_Finalize` is safe: the threads never touch a `PyThreadState` and are joined before drop returns.
- The whole `sweep_all` runs through `gate::run_blocking` (4.2, change 3).
- A runtime `pub(crate) fn sweep_all_with(mode: SweepMode, ...)` lets one build time both modes (change 6); the production constant picks one. Parallel stays unless it loses on a fast local disk by more than noise (change 4).
- Tests: a `#[cfg(test)]` thread-local that fails the next `n` spawns; with every spawn failed, every shard is still swept on the caller; the pool and spawn-failure tests stay in Miri lane A (change 7).
- Optional, decided by step 4's numbers: make the unit of work a slice of one store's folders, so the same pool speeds up a plain `Cache` and `Caches.close_all()` (suggestion 1); bring back the dirty flag as a 256-bit "removed a file from folder `aa`" set, deciding it together with the 30 s filter (suggestion 2).
- A stalled volume leaves a sweep thread in uninterruptible sleep and the join waits for it, as a close checkpoint's `fsync` already can; once detached, only the closing thread waits (suggestion 3).

**The budget rule, fixed before measuring** (change 4): twice the worst cold run of the chosen strategy on an 8-shard FanoutCache on `sdc` in the steady state (256 old non-empty folders per shard), rounded up, with a floor of 100 ms and a ceiling of 1 s (the same as `RELEASE_BUDGET` and the close checkpoint's). A cold number above the ceiling goes back to Michael as a finding, not a higher ceiling. Until then, 100 ms is a placeholder.

## 6. Risks

- **A writer racing a sweep.** Covered by 4.1's loop; the deterministic tests pin it.
- **Network block storage.** Uncached metadata reads cost a network round trip, so a cold sweep can be tens of times slower than on NVMe. The budget (a placeholder until step 4, 4.4) bounds it, and a sweep cut short resumes at the next close; 4.4 sweeps shards in parallel, and step 4 measures both ways.
- **Close cost.** Up to 256 `stat`s and `rmdir` attempts per store, 2,048 at 8 shards, bounded by the budget in all (a placeholder until step 4). Step 4 measures it, including a short-lived `with Cache()` pattern.
- **Mixed versions during the upgrade deploy.** Old workers write two-level files the new code reads as missing. Existing caches are deleted at deploy, with every worker stopped (plan 15's documented reset), so it doesn't arise.
- **A large write after the root is deleted** now raises `OSError` (4.1, D-entry in step 6). Deleting a cache's folder while processes have it open is already unsupported.

## 7. Decisions

Michael, 2026-11-06: flat 256 directories (section 3), no removal on delete, the sweep on the last handle's close (a budget measured in step 4, 100 ms until then, continuing at the next close) and on `clear()`, skipping directories modified in the last 30 seconds, and no compatibility with the two-level layout.

## 9. Review

### 9.1 First review, of the draft (option A, two levels with removal on delete), superseded by section 3

2026-11-06, the architect, on the draft: **PASS with required changes.** Option A is the right call, the core race argument holds (an `rmdir` can only remove an empty directory, and a `.tmp` or `.val` keeps it non-empty from `create_new` until the owner's unlink), and the placement under the gate is right. The changes below tighten the create loop, close two leaks, protect `rmdir` from a hostile `filename`, make the tests deterministic, and account for one behavior change and one oracle bug the draft didn't mention.

Verified against the code: every removal goes through `Store::unlink` (store.rs:903; callers store.rs:374, 885, 894, 1646, ops.rs:245, and through `write_files` for delete, pop, cull, expire, clear, incr over an expired large value, eviction) or `settle_with`'s `discard` (ops.rs:502). `touch` touches no file (ops.rs:411). There's no `push`/`pull` or `check()` in oxide, so nothing else to cover. Each FanoutCache shard is its own `Store` with its own directory, so shards come for free; fanout.rs's temp file lives in the root and is unaffected.

### Option A vs B vs C

A, agreed. B fixes nothing for the trees that already exist, adds a second layout forever, and needs a D-entry; C pays for both. One wording fix: A doesn't match diskcache *exactly*. `os.removedirs` climbs past `aa` (it stops at the cache directory only because the database is there), `os.makedirs` is recursive (diskcache re-creates a deleted root), and diskcache leaks a value file written inside a rolled-back `transact()` (verified on 5.6.3: `with c.transact(): c.set('k', big); raise` leaves `65/fa/<hex>.val` with no row, because `_transact` removes `filenames` only on commit, core.py:732-747). Say "matches diskcache's directory removal" instead.

### Race analysis (5.2): correct, with these confirmations and gaps

- Rename `.tmp` to `.val`: safe, same directory, and the `.tmp` keeps it non-empty. `commit_name`'s `NotFound && val.exists()` retry (spill.rs:68) is unaffected. That only holds while nothing but the owner removes a `.tmp`, so the 5.4 sweep must never remove files, only `rmdir`.
- Held transactions with files written but rows uncommitted: the file exists, so the directory can't go. Savepoint rewinds (store.rs:880-886), doomed rollbacks and the abandoned-`Lend` path (store.rs:374) all go through `Store::unlink`, so they prune too.
- A reader that has opened the file (the D-016 fallback, ops.rs:213-230) keeps its fd through unlink and `rmdir`. One that hasn't gets `NotFound` from `open` whether the file, `aa/bb` or `aa` is gone, so `spill::read`'s `NotFound` mapping (spill.rs:96) covers it, and names are never reused, so a re-created directory can't make an old name reappear.
- Pruning `aa` while a writer has made `aa` but not `aa/bb`: the writer's `mkdir(aa/bb)` gets `ENOENT` and retries. Covered, provided the loop restarts at `mkdir(aa)`.
- Fork children and other processes: `rmdir`/`mkdir` are filesystem-atomic and hold no state of ours, so a child or another process is just one more pruner. A child that forgets an inherited transaction's files (store.rs:1751) also doesn't prune, which is right.
- Gap, the `EEXIST` check is a TOCTOU (required change 1). Gap, a failed create leaks directories (required change 3). Gap, the deleted-root check is redundant (required change 2). Gap, mixed-version deploys (required change 7).

### Gate and fork placement (5.3): right

Pruning in the same closure as the unlinks, attached below `UNLINK_DETACH_AT` and inside `run_blocking` at or above it, is exactly right. `run_blocking` already allows bounded file work with a level held (gate.rs:17-21, 98-101), and unlinks run after the write lock is released (store.rs:893-894, 811-816). The 64-round create loop belongs inside `PendingFile::write`'s existing `run_blocking` closure (spill.rs:47). One addition: the cost model in 5.1 is wrong for the common case (required change 8).

### Required changes

1. **Don't `stat` after `EEXIST`.** 5.2 says each `mkdir` accepts `AlreadyExists` "only for a directory (as `open::ensure_shard_directory` does)", which is `directory.is_dir()` (open.rs:177). Here that's a race: `mkdir(aa)` gets `EEXIST`, a pruner removes `aa`, `is_dir()` is false, and the write fails hard instead of retrying. Treat `EEXIST` as "go on to the next step" with no `stat`: if `aa` is really a file, `mkdir(aa/bb)` fails `ENOTDIR`, and if `aa/bb` is a file, `create_new` fails `ENOTDIR`. Both are terminal errors. Only `ENOENT` from `mkdir(aa/bb)` or `create_new` retries. That's one syscall fewer and no window.
2. **`ENOENT` from `mkdir(directory/aa)` is terminal, with no check.** With a non-recursive `mkdir`, that error means the cache directory (or a parent) is missing. Nothing in oxide ever removes the cache directory, so there's nothing to retry and nothing to check, and a `stat` of the directory would be its own TOCTOU. Drop "checked once against the cache directory" and fail at once with `Error::Io` naming the path. A root deleted mid-loop still ends in one round, because the next `mkdir(aa)` fails.
3. **Prune on every failed create, not just `write_new`'s.** If `create_new` fails with anything but `ENOENT` (`EMFILE`, `ENOSPC`, `EACCES`, `EDQUOT`), the directories this call just made stay empty forever. If `mkdir(aa/bb)` fails, `aa` does. Likewise after the 64th `ENOENT`. `PendingFile::write` should call `prune_dirs` on every error path after its first `mkdir`, plus the `remove_file` `write_new` already does (spill.rs:85). Put it in the caller, which knows `directory` and `relative`, rather than in `write_new`, which only has a path.
4. **`prune_dirs` must validate `relative` before removing anything.** `filename` comes from the database, and `directory.join(relative)` follows absolute paths and `..` (`Path::join("/x")` replaces the base). Today a damaged row can make `unlink` remove a file outside the cache. With pruning it could also `rmdir` empty directories anywhere, `/tmp/foo` for a `filename` of `/tmp/foo/x.val`. Parse it as exactly `[0-9a-f]{2}/[0-9a-f]{2}/[0-9a-f]{32}.(val|tmp)`, build the two directory paths from those components (`directory.join(aa)`, `directory.join(aa).join(bb)`), and prune nothing otherwise. Return `()`, with no error path. Hardening `unlink` the same way is worth a follow-up (suggestion 1), but the prune must not inherit that hole.
5. **Deterministic tests for the retry, not only a timing race.** The 8-thread forced-prefix test is good for confidence but probabilistic: a "no retry" mutation could pass it on a quiet run. Add a `#[cfg(test)]` thread-local injection point between `mkdir(aa/bb)` and `create_new`, in the style of `FAIL_NEXT_END_BUSY` (store.rs:1803). When armed with `n`, it `rmdir`s `aa/bb` (and `aa`) the next `n` times. Assert: `n = 1` succeeds, the re-created directories are 0700 (D-015 is only tested on first creation today, spill.rs:243-251), `n = 63` succeeds, `n = 64` fails with `OSError` naming the path and leaves no empty directory (catches change 3), and a deleted root fails after exactly one `mkdir` (catches a spin, change 2) and creates nothing (catches "recursive create kept"). For the forced prefix, make the hex a parameter rather than a global in core: a `pub(crate) fn write_named(directory, hex, data)` that `write` calls with `random_hex()`, so core tests need no static at all.
6. **Cover the cases the step-1 list misses, and a batch that shares a directory.** Add `add` of a large value on an existing key (the `discard` path, ops.rs:311-325), an overwrite large to large, `incr` over an expired large value, `cull` through `size_limit` on `set`, and a held `transact()` that commits overwrites. In core, use the forced prefix to put two or more files in one `aa/bb` within a single unlink batch, both below and at or above `UNLINK_DETACH_AT` (8). Otherwise a mutation that prunes after the first file of a directory, or dedupes wrongly, passes every test, since random prefixes almost never share a directory. "Prune before unlink" is already caught by the plain `delete` test (a single file, so its directory is never empty at prune time). For the rolled-back `transact()` case, assert only "no empty directory" across backends: on diskcache it passes vacuously because of the leaked file. Assert "no value file and no value directory left" oxide-only, with whatever marker the conftest requires, and log the diskcache leak in `upstream/README.md` with a repro in `upstream/repros/` (convention). The four-line repro is in the review notes above.
7. **Record two behavior consequences.** (a) After the root is deleted under a live process, a large `set` now raises `OSError`, while a small `set` still succeeds into the unlinked database, and diskcache's `makedirs` re-creates the tree and succeeds. That's test-visible against the oracle, so it needs a `D-NNN` entry (or say it's out of the conformance surface and note it in D-032/D-038's neighborhood). Update plan 15 section 10's note to point here. (b) Mixed-version deploys: an old oxide writer (recursive create, no retry, spill.rs:49-50) beside a new pruner, or the 5.4 sweep, can lose the window and fail one `set` with `OSError`. That's vanishingly rare (same `aa/bb`, same few microseconds) but real during Talk Python's rolling deploys, so list it in section 7.
8. **Measure the sparse case, where pruning succeeds.** 5.1 assumes `rmdir` "fails fast with `ENOTEMPTY`", but a live cache with about 100 value files across 65,536 directories almost never shares one. The common case is that every large delete or overwrite *succeeds* at two `rmdir`s, and the next large write pays two `mkdir`s: four journaled directory updates per cycle, versus none today. `bench.gate`'s headline workloads don't spill at all (bench/gate.py:29-35), so "no regression on 99:1" is vacuous. Measure `bench.baseline`'s `set_page_entry_450k` (an overwrite: new file, old one unlinked) and a large set-then-delete loop on a near-empty cache, at 1 and 8 threads, 3.14 and 3.14t, against diskcache (which pays the same `makedirs`/`removedirs`). The bar should be "within diskcache's cost for the same cycle".
9. **Pin the 5.4 sweep's constraints if Michael picks option 2.** It only `rmdir`s, never removes a file (a `.tmp` may be another process's in-flight write, see the rename note above). It matches names exactly `[0-9a-f]{2}` at both levels, so it never touches a FanoutCache shard (`000`) or the user's own folders. It runs in the shard's directory, never the root. It runs after the chunk loop finishes, with no write lock and no gate level, through `run_blocking`, and only when `GATE.own_depth() == 0`. Inside a held transaction, skip it: the clear's files go at commit and prune there, and a 65,792-entry walk while holding a level would make a pending fork wait tens of milliseconds. It's best-effort, never changes `clear()`'s return or raises, and is skipped when `clear_until` was `Interrupted`. Against new-code writers in other processes it's safe: it's one more pruner, visiting each directory once, so it costs a racing writer at most two of its 64 rounds.

### On 5.4's recommendation

Option 2 is right, with change 9's constraints. It's safe against concurrent writers for the same reason pruning is (`rmdir` can't lose a file, and the writer retries), its cost shrinks to almost nothing once a tree is clean (after the fix, only directories with live files exist), and `clear()` is the only "make this cache empty" call oxide has, since there's no `check()`. Not option 3, for the reasons given. Option 1 is a fair fallback: the installed population is small (Talk Python and the soaks), and plan 15 already makes "delete the folder with every worker stopped" the documented reset.

### Optional suggestions

1. Harden `Store::unlink` and `spill::read`/`open` with the same `filename` validation as change 4, as a separate small change. A damaged row should never reach outside the cache directory. Today `directory.join` lets it (store.rs:904, spill.rs:93).
2. Do the batch prune in two passes: every distinct `aa/bb`, then every distinct `aa` whose `bb` was removed. It reads more clearly than per-parent "then maybe `aa`", and it's the same syscalls.
3. For the Python stress test (step 3), prefer an adversary process that loops `os.rmdir` over the forced directory (always safe, since it removes only empties) to a forced-prefix knob alone. If a knob is still needed, follow the `_sqlite_error`/`_gate_stats` precedent (crates/diskcache-oxide-py/src/lib.rs:223-304): a private `_core._force_value_prefix(prefix: str | None)` that validates four hex characters, is listed only under the private names in `_core.pyi`, is process-wide (forked children inherit it, spawned ones must call it), and is documented as test-only. In production it could only cost performance, never correctness. No environment variable (CLAUDE.md: the library has none).
4. Use `ErrorKind::DirectoryNotEmpty` (stable) in comments and tests rather than raw errno. POSIX allows `rmdir` to return `EEXIST` for a non-empty directory, and since every prune error is ignored, nothing needs to branch on it.
5. Soak step 6: also count `aa` directories with no `bb`, and `.tmp` files older than an hour, so a leak on either path shows up.

### 9.2 Second review, of sections 3 to 8 (flat 256, sweep on close and `clear()`)

2026-11-06, the architect: **PASS with required changes.** The design is sound, and simpler than A. The 256 cap does the real work: it bounds the cost with or without any sweep, so the sweep is tidiness and can stay cheap and best-effort. The race argument holds. The changes below fix one internal contradiction (the 30 s filter makes the `clear()` sweep a no-op and fails the plan's own tests), pin down where "last handle" is decided and what the drop path does, fix a soak check that would pass vacuously, and fill test and doc gaps.

#### Race analysis: correct

- **Two-step create vs the sweep.** Every interleaving ends well. If the sweep's `rmdir` comes after the writer's `create_new`, it fails with `DirectoryNotEmpty`. If it comes between the writer's `mkdir` (`EEXIST` on an old empty directory) and `create_new`, `create_new` resolves the path through a missing `aa` and gets `NotFound`, which is 4.1's retry. `rmdir` and a create in the same directory are serialized on the directory's inode lock on ext4 and APFS, so no file can land in a directory that is being removed. A fresh `mkdir` gives `aa` an mtime of now, so a sweep with a non-zero `min_age` never races the window right after a new directory is made. The retry still covers `min_age = 0` (see change 1). Treating `AlreadyExists` with no `stat` (review 1, change 1) and a terminal `NotFound` from `mkdir` (change 2) are both right.
- **Rename.** `commit_name` renames within `aa`, and the `.tmp` keeps `aa` non-empty from `create_new` until then. The `NotFound && val.exists()` retry (spill.rs:68) is unaffected.
- **Held transactions.** Uncommitted `.tmp` and `.val` files keep their directories alive. A rollback's `discard` (spill.rs:74) and a commit's unlinks leave empties for the next sweep. Closing the last handle on thread B while thread A holds a transaction on the store, which the store supports (store.rs:750-766, `give_back` on a retired store), is safe for the same reason.
- **Fork children and other processes.** The sweep touches no SQLite and no state of ours, so a child, or another process, is just one more remover. It needs no gate level: it can neither wait for a pending fork nor hold one up, and a fork in the middle of it hands the child nothing (see change 2).
- **FanoutCache.** Each shard is its own `Store` with its own directory (shards.rs:58), shard names are `{index:03}` (fanout.rs:166-168, never two characters), and a root never has a `Store` of its own (D-038). Sweeping per store is therefore exactly "every shard, never the root".
- **The rmdir after a terminal create error (4.1).** Safe. If another writer created a file in `aa` meanwhile, the `rmdir` fails. If another writer's `mkdir` got `EEXIST` just before the `rmdir`, that writer retries.

#### Required changes

1. **The 30 s filter turns the `clear()` sweep into dead code and fails the plan's own tests.** `clear()` has just unlinked every file, so every directory it emptied has an mtime of now, and 4.2's age check skips all of them (plan line 60 vs line 65). The same goes for the close right after a delete. Step 1's conformance test (line 75: write, remove, close, "holds no empty directory") and step 3's "after the last close the tree has no empty directory" (line 83) would both fail on oxide, and section 2's "the end state after a close, no empty directory, matches" (line 25) isn't true with the filter. Fix:
   - Give `spill::sweep` a `min_age: Duration` parameter. It's real API, not a `#[cfg(test)]` constant, in the same spirit as `write_named`. `clear()` passes `Duration::ZERO`: it's the explicit "empty this cache" call, the writer's retry already covers the race, and with no age check it skips the `stat` and costs a readdir plus `rmdir`s. Close passes 30 s (Michael's decision).
   - The black-box tests backdate the directories before the close: `os.utime(d, (t, t))` on every two-hex directory, with `t` a minute ago, then `close()`, then the assertion. That works against both backends (on diskcache there's nothing to backdate) and needs no hook.
   - Reword line 25 to "after a `clear()`, or a close once the directories have been idle for 30 s".
   - Worth Michael's second look, not required: the filter's two stated benefits are a fresh `mkdir`'s window, which the retry already handles, and churn, which is one `mkdir` per directory per close and closes are rare. Its cost is that the close sweep misses exactly the directories this process just emptied. Keeping 30 s at close is defensible. Just know that it mostly turns the close sweep into "clean up what earlier processes left".
2. **Decide "last handle" from the release itself, sweep after it, and put that in core.** Section 4.2 says "after checkpoint-on-close and before the release". Today "last" is a pre-check, `handles == 1` (store.rs:1069-1072). Two threads closing the last two handles both see 2 and neither sweeps, and a concurrent open can make the pre-check wrong in the other direction. The exact answer is already computed under the registry in `release_under` (store.rs:709-718: `count_handle(-1)` and then `is_retired()`). So:
   - Have `release_under` return whether this release retired the store, and sweep after it, with no gate level held. A deferred release (store.rs:733-743, behind a pending fork) doesn't sweep, which is fine.
   - Sweeping after the release also lets the connections close first (D-018).
   - Make it one core entry point, for example `Store::release_handle_with(Housekeeping)` and the `close_all` equivalent. `Cache.close` has two branches (cache.rs:390-400) and `FanoutCache.close` another (cache/fanout.rs:371-386), so a sweep wired up in the Python layer would have to be added in at least three places.
   - Keep the `GATE.own_depth() > 0` skip, because a close inside a transaction would otherwise run up to 100 ms of file work while holding a level, and a pending fork would wait for it.
   - Drop the fork-child skip, or at least stop justifying it as "follows checkpoint-on-close exactly". `checkpoint_on_close` "skips" in a poisoned child only because `checkpoint()` fails `check_writable` (store.rs:993) and the error is ignored (store.rs:1052-1056), and `rmdir` has nothing to do with D-020.
3. **Say what the drop path does, and what happens when nothing closes.** `Cache`'s `Drop` (cache.rs:1048-1063) and `FanoutCache`'s (cache/fanout.rs:908-923) release with no checkpoint, and the library has no `atexit` hook (lib.rs:247-278 registers only the fork hooks). As written, the sweep follows the checkpoint, so a cache that is garbage-collected rather than closed never sweeps. Neither does a process that exits without deallocating its globals, or a gunicorn or multiprocessing worker that ends in `os._exit`. And the `Caches` registry, which is how Talk Python holds its caches, keeps its handles for the life of the process and closes them only in `close_all()` (caches.py:512-527).
   - Recommendation: the drop path sweeps too. It's the same last-handle release, it costs milliseconds, it never fails, it runs no Python, and for many apps it is their close.
   - Add no `atexit` hook. It would put hidden I/O at exit, it would interact with forked children, and `os._exit` skips it anyway.
   - Write down that in practice the sweep runs on `clear()`, an explicit `close()` or `Caches.close_all()`, and drop. A process that dies without any of them leaves at most 256 empties per store, which the cap already bounds, and the next sweeping process removes them.
4. **Give the sweep its own deadline rather than `clear()`'s timeout, and one deadline per FanoutCache close.** Maintenance deadlines bound waiting, not work (maintenance.rs:9-14), and the sweep never waits, so "with `clear`'s timeout as the deadline (at most 100 ms past it)" (line 65) has no clear meaning past the deadline. On a FanoutCache clear it could also mean 100 ms per shard after a short timeout. The sweep's deadline only guards against a pathological filesystem. So use a constant `SWEEP_BUDGET` of 100 ms from the sweep's start for each `clear_from` (each shard's clear sweeps its own directory), and one shared deadline across `close_all`'s shards, the way it already shares the checkpoint budget (store/shards.rs:89-98). Risks (line 91) says "bounded at about 100 ms" for 2,048 entries, while 4.2 says per store. Make them agree.

After this change it finds no files, so `orphans` reads 0 and the orphan check passes vacuously, which is a silent loss of a soak guarantee. Step 5 must change it to `??/*`. Also add a check that fails if any `??/??` remains, so an old-layout leftover or a regression shows up. Existing Python tests use `rglob('*.val')` or `rglob('*')` (tests/unit/test_pop.py:83, test_cache_api.py:208, test_decode_errors.py:244, tests/conformance/backends.py:108) and work at either depth.

#### Answers to section 8

1. **Sweep flag vs `checkpoint=False`.** Don't tie them, and don't add a flag. `checkpoint` is about the WAL: the docstring (cache.rs:372-378), D-024 and `CacheLike.close` (protocol.py:107) all describe it that way, and its reason to exist is that a checkpoint can wait up to 1 s on other processes. The sweep never waits on anyone and costs a few milliseconds, so a caller who passes `checkpoint=False` to close fast has no reason to also give up the cleanup. And someone who reads `checkpoint=False` would not expect it to change what's left on disk. A dedicated flag would be new API that diskcache doesn't have, for a few milliseconds nobody has asked to save. If step 4 shows close is expensive, the fix is the optional dirty flag (suggestion 1), not a parameter. If Michael wants "close does no housekeeping" as one switch anyway, rename nothing, but say it in the docstring and in D-024's "At close" bullet.
2. **Detached vs attached.** Follow the `UNLINK_DETACH_AT` reasoning (store.rs:298-303, 903-915): attached for one store, and inside the existing `detach` when `close()` already takes it on a large WAL (cache.rs:390-397). For `close_all` over many shards, run the sweeps through `gate::run_blocking`, which already avoids re-detaching on a thread that is detached (lib.rs `detached_wait`), if step 4 shows 2,048 entries well past a millisecond. Let step 4's numbers set the threshold, as they did for the unlinks: on a busy GIL build, getting the interpreter back costs up to the 5 ms switch interval, which is likely more than a 256-entry sweep.
3. **Invalid filename: miss, not raise.** A miss is right. D-013 already defines "the file this row names can't be read" as a miss with the row removed. A damaged or hostile row that raises would make every `get` of that key an exception until someone repairs the database by hand. And the row deletion repairs it. Two details: put the parse in one `fn value_path(directory, relative) -> Option<PathBuf>` that `unlink`, `read` and `open` share (spill.rs:93, 103; store.rs:904), and `debug_assert!` in `write_named` that its own names pass it. With change 8's bump, "an old two-level cache degrades to misses" stops being a selling point, so drop that sentence from 4.3.
4. **mtime and 30 s.** mtime is reliable enough for a filter whose mistakes cost nothing. Safety comes from `rmdir` plus the retry, never from the timestamp.
   - **ext4 and APFS.** Both use nanosecond timestamps from the kernel's wall clock, and both update a directory's mtime on create, unlink and rename within it. So do tmpfs and overlayfs.
   - **NFS.** It uses the server's clock, so client skew can make a directory look young (it's skipped, harmless) or old (the retry covers it).
   - **A wall clock stepped backwards.** It leaves mtimes in the future: treat a failed `SystemTime::now().duration_since(mtime)` as young, and treat an error from `modified()` as young too.
   - **Read it without following symlinks.** Use `DirEntry::file_type()` and `DirEntry::metadata()` (lstat).
   - **30 s.** It's fine as a churn filter at close. Use 0 for `clear()` (change 1).
   - **How to test.** Use the `min_age` parameter, plus a real backdated mtime, so the test exercises the age check rather than bypassing it. In core, `File::open(&dir)?.set_modified(SystemTime::now() - Duration::from_secs(60))` uses std only (`futimens` on a directory fd works for the owner on Linux and macOS), so no `filetime` dependency. In Python, `os.utime`. Backdate after the last create or delete in that directory, since either one resets the mtime.

#### Close-time cost and placement

Last handle only is right: it matches checkpoint-on-close, and a handle closed while the cache is in use never pays. Order: checkpoint, release, then sweep (change 2). If close is never called, see change 3: the sweep is skipped, and the cap still holds. For step 4, also measure:

- a tree of 256 *non-empty*, old directories, which is the steady state of a live cache and the worst case for the close sweep (readdir, plus a `stat` and a failing `rmdir` per directory, about 512 syscalls);
- a per-request `with Cache(d) as c: c.get(k)` loop, the pattern D-024's close backoff exists for (store.rs:1047-1051). With the sweep, it pays the cost above on every exit. Optional suggestion 1 removes it for readers.

### 9.3 Third review, of 4.4 (parallel shard sweep) and the new step 4

2026-11-06, the architect: **PASS with required changes.** The motivation is real, and the core safety claim holds: the sweep threads touch only `readdir`, `lstat` and `rmdir`, hold no gate level, lock or connection, and run no Python, so they can't hold up a pending fork, and a fork can't hand a child anything half-done. Release-then-sweep order also means a child forked mid-sweep inherits stores that are already fully released. `std::thread::scope` is the right tool: it borrows the shard paths and the deadline with no `Arc`, and it guarantees nothing outlives the call. A persistent pool (rayon or our own) would be wrong here, because its threads vanish in a forked child and sit idle for the life of the process. The changes below make spawn failure and panics actually behave as 4.4 says, cap the thread count, make releasing the interpreter mandatory, and fix the measurement method, which as written can't produce a reproducible cold number on htz without touching production.

#### Checked against the code

- **Close and drop.** `FanoutCache.close` (cache/fanout.rs:369-384) and its `Drop` (cache/fanout.rs:911-921) go through `Store::close_all` → `close_all_within` (store/shards.rs:89-98), which holds one `SharedGuard` from line 96 through `release_all` (store/shards.rs:102-107). The sweep has to run after that guard drops, in `close_all_within`, once `release_all` reports which stores retired (9.2 change 2). Behind a pending fork, `release_all` defers every release (`defer_release`, store.rs:733-743), so nothing retires and nothing sweeps. That's right, and it means a parallel sweep never overlaps a fork that was already pending at close.
- **Fork gate and D-027.** `begin_fork` waits only for gate holders (gate.rs:44-48). Sweep threads aren't holders, so a fork from another thread goes ahead at once. The child has only the forking thread, which can't be the closing thread, since that one is blocked in the join. In the parent, the sweep then carries on. `pthread_create` racing a `fork()` is the same exposure as any other thread, and glibc and libmalloc reset their own locks in the child. 4.4's claim is correct.
- **Finalization.** `Cache`'s drop comment (cache.rs:1048-1053) already establishes that drop runs attached during shutdown and that detaching there is safe. Spawning OS threads during `Py_Finalize` is safe too, because they never touch a `PyThreadState` and are joined before drop returns. The one existing hazard is unchanged: a daemon thread whose detached work outlives finalization hangs when it tries to re-attach (3.14 hangs such threads by design). The process is exiting anyway, and every `rmdir` is atomic.
- **Shuttle.** The models (gate/model.rs, genlock/model.rs) abstract the store and never call `close_all`, and the sweep adds no gate state. No model change is needed (see change 7 for the one assertion worth adding).
- **Sanitizers.** Lanes B to E aren't built yet (scripts/sanitize.sh:130). Lane A runs the whole `spill::` module under Miri with isolation off (scripts/sanitize.sh:57-58), so every new sweep test lands there automatically (change 7).

#### Required changes

1. **Spawn with `thread::Builder::spawn_scoped`, and join every handle yourself.** `Scope::spawn` panics if the OS refuses the thread, so 4.4's "`EAGAIN` falls back to the calling thread" can't be built on it. `Builder::new().name("dco-sweep".into()).stack_size(SWEEP_STACK).spawn_scoped(s, f)` returns `io::Result`, and that's the call to use. Join each `ScopedJoinHandle` explicitly and discard its `Err`. `scope` re-panics on the caller for any thread that panicked and wasn't joined by hand. A re-panic in `FanoutCache::drop` is the worst place to panic, since the next stop is PyO3's deallocation path or an abort, and 4.2 promises "never raises". Stack: set it explicitly at 256 KiB. The frames are tiny (a `ReadDir`, one `PathBuf`), but ASan triples frame sizes for lanes C and E. An explicit size also stops a user's `RUST_MIN_STACK` from deciding it. Rust's std already adds glibc's static-TLS minimum (`__pthread_get_minstack`), so the extension's and libpython's TLS can't eat into it. The name makes the threads identifiable in `py-spy`, TSan reports and core dumps.
2. **A bounded worker pool, not one thread per shard.** `MAX_SHARDS` is 256 (fanout.rs:40). One thread per shard would mean up to 255 spawns per close: about 256 × 2 MiB of reserved stack at the default size, a few milliseconds of spawn cost, and an `EAGAIN` waiting to happen under a container's `pids.max` while a gunicorn deploy closes every worker at once. And past the device's useful queue depth it buys nothing. Use `SWEEP_THREADS = 8` in total, the caller included, as a fixed constant rather than `available_parallelism()` (the work waits on I/O, not CPU, and htz's container has `--cpus 4`). Share an `AtomicUsize` index over the shard list. The caller spawns `min(SWEEP_THREADS, shards) - 1` helpers, then pulls work itself. Spawn failure then needs no separate fallback path: a helper that didn't start just means fewer pullers, and the caller always drains the list. The default 8 shards still get one thread each. Test it with a `#[cfg(test)]` thread-local that fails the next `n` spawns (the caller does the spawning, so a thread-local works), in the `FAIL_NEXT_END_BUSY` style (store.rs:1803): with every spawn failed, every shard is still swept, and on the calling thread.
3. **A FanoutCache's sweep must run with the interpreter released, through `gate::run_blocking` from core.** Today both `FanoutCache.close` and its drop detach only when a shard closes on a large WAL (cache/fanout.rs:378-384, 917-921). An attached join is bad on both builds:
   - On a GIL build, every other Python thread stalls for the whole sweep. Cold on a network volume, that's hundreds of milliseconds, and up to the budget, which Michael suspects may be two seconds.
   - On 3.14t, a thread blocked while attached never reaches a safe point, so every stop-the-world (the GC, and `os.fork()`'s before-fork pause) in any thread waits for the sweep to finish.

   Call `gate::run_blocking(&|| spill::sweep_all(...))` in `close_all_within`, after the guard drops. The installed blocker detaches (lib.rs:169-175), and it runs the work inline when the large-WAL path has already detached (`DETACHED`), so there's no double detach. The Python layer then needs no new branch, and 9.2 change 2's single core entry point holds. Replace 4.2's "Attached" bullet with: a FanoutCache always sweeps through `run_blocking`; a plain `Cache` stays attached unless step 4's cold `sdc` number for one store is past about a millisecond, and then it uses `run_blocking` too (the same call, so it's a one-line decision). The reacquire cost, up to the 5 ms switch interval under contention, is paid once per last-handle close. Step 4's `with Cache()` loop measures exactly that, so run it with a second busy Python thread too.
4. **Reconcile the decision rules and repair step 4's text.**
   - 4.4 says "parallel stays unless it loses on a fast local disk by more than noise" (line 80). Step 4 says "the cold FanoutCache sweep on the network volume decides between sequential and parallel" (line 102). Keep 4.4's rule and delete step 4's sentence.
   - Step 4's second paragraph (line 102) repeats 4.4's motivation and has broken fragments: "Where: htz's attached Hetzner Volume ... small and short. on 3.14 and 3.14t, ext4 (htz or the mini's APFS for macOS)". It also names the mini, while the first paragraph names the Mac. Rewrite step 4 as one list: (a) the raw sweep timing, (b) the end-to-end close costs, (c) `set_page_entry_450k`, with each item's devices, Python builds and owner.
   - The 100 ms figure still reads as decided in 4.2's Budget bullet (line 67), Risks (lines 109-110) and section 7 (line 116). Mark each one "placeholder, see 4.4".
   - Write the rule for choosing the budget now, before the numbers exist, so it isn't picked to fit them. My proposal: the budget is twice the worst cold run of the chosen strategy on an 8-shard FanoutCache on `sdc`, steady state (256 old non-empty folders per shard), rounded up, with a floor of 100 ms and a ceiling of 1 s, the same ceiling as `RELEASE_BUDGET` and the close checkpoint's budget. A worst-case close then stays within about 3 s. If the cold number is above the ceiling, that's a finding to bring back to Michael, not a reason to raise the cap (see suggestion 2).
5. **Make "cold" reproducible without touching production.** `echo 3 > /proc/sys/vm/drop_caches` is the wrong tool on htz, for two reasons:

#### Optional suggestions

1. **Make the unit of work a slice of one store's entries, not a whole store.** On `sdc` a plain `Cache`'s steady-state close is about 256 cold directory-block reads, perhaps 250 ms at about 1 ms each, and "a plain `Cache` never spawns" leaves that sequential.

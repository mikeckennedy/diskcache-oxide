# Plan 19: sweep leftover temp files with the empty folders

Michael's ask (2026-11-07), after the htz soak showed three stores each holding one `.tmp` file forever: when the close sweep of plan 17 visits the value folders, remove the temp files a killed writer left behind too. A small step on top of `spill::sweep`; the same budget, the same random start, the same two callers.

## What a `.tmp` is and how long it lives

`PendingFile::write` creates `aa/<hex>.tmp` and writes the value into it before the row is written; `put_value` renames it to `aa/<hex>.val` inside the write transaction (`commit_name`), and a write that fails or rolls back removes both names (`settle_with` → `discard`). So a `.tmp` exists from the create until the row write reaches `commit_name`: the write of the data, and at most one wait for the write lock, bounded by the handle's `timeout`. A `.tmp` that has not been written to for an hour belongs, in every case but one, to a writer that died in that window (SIGKILL, a crash, a power cut). The exception is the trade the hour makes: a writer that is alive but has gone an hour without touching its file (paused, a frozen container, a debugger, or an app whose `timeout` is above an hour and really waiting that long on the lock) loses the file; its `commit_name` then fails, the transaction rolls back and its write raises `OSError` with nothing stored, never a partial row. Nothing else ever removes it: the soak's file scan counted them (`orphan_tmp`), and a long-lived cache collects one per such death.

A `.val` with no row is a different case: a held transaction that renamed its file and then died before committing leaves one, and only a check against the database can tell it from a committed value's file. Out of scope here, as it is for diskcache (`upstream/README.md`, bug 12 and D-013's measurements); the sweep touches `.tmp` names only.

## The change

In `spill::sweep`, for each value directory the walk reaches within its deadline and that passes the directory age check (30 s on a close, none on `clear()`): read the directory, remove every regular file named `<32 hex>.tmp` under the directory's own prefix whose mtime is at least `TMP_MIN_AGE` (1 hour) old, then the `rmdir` as before. After the age check (the architect's suggestion), so a young directory costs one `lstat` and no `readdir`, and a quiet directory holding only a dead temp file goes in the same pass; a dead temp file in a busy directory waits for it to go quiet for 30 seconds. The temp-file age is the same on both callers: `clear()` removes this process's view of the cache, and another process may have a write in flight in the same directory, which the age protects. Only `.tmp` is touched, only when its stem is 32 lowercase hex characters, only a regular file (not a symlink), and never a `.val`.

Why an hour: the longest a legitimate `.tmp` can go without being written is one write-lock wait, whose bound is the handle's `timeout` (60 s by default, and nothing stops an app from setting it higher). An hour is far past any sensible timeout and still means a killed writer's file is gone at the first close an hour later, where before it stayed forever. The sweep's mtime check is the file's own, so a slow write of a very large value, whose mtime moves with every chunk, is never mistaken for a leftover.

Cost: one `readdir` per directory visited, where the sweep used to make one `rmdir` syscall. On a large cache (thousands of files per directory) a close's 100 ms covers fewer directories than before, and successive closes cover the rest from their random starts, which is the design plan 17 already relies on. Measured below.

## Tests

- `spill::tests`: a sweep removes an old `.tmp` and keeps a young one, keeps every `.val` whatever its age, keeps a `.tmp` whose stem isn't 32 hex characters and a `.tmp` that is a directory, and with a zero directory age removes the directory the old `.tmp` kept non-empty.
- `tests/conformance/test_value_dirs.py` (oxide-only, D-042): a planted `aa/<hex>.tmp` two hours old is gone after `close()`, a young one and an old orphan `.val` beside it stay, and `clear()` does the same.

## Decisions (taken while Michael was away, confirmed by him on 2026-11-07)

- `TMP_MIN_AGE` is 1 hour.
- Same age on `clear()` as on close.
- `.val` orphans are left alone (a later step, if wanted, with a database check).
- The write path is not made to recover from the macOS `rmdir` race: recorded in D-042 and watched through the soak (the recipe is in the progress notes if it ever shows).
- Next after this plan: plan 14, lane B (ThreadSanitizer).

## Progress
- 2026-11-07: built as above; the `spill::` tests (18) and the value-dirs conformance tests (18 on 3.14 and 3.14t) pass. Cost, measured on the Mac (APFS, warm, a plain `Cache`'s last close with 256 folders, 7 runs): 256 empty folders 17 ms median (11 ms before this change: the `readdir` of an empty folder adds about 25 µs each); 10 files a folder 10 ms; 100 files a folder 32 ms; 1,000 files a folder (256,000 value files) hits the 100 ms budget and the sweep stops there, so such a cache's close spends the whole budget each time and covers about three quarters of its folders, the rest at later closes from their random starts. For the soak's stores (about 100 value files each) the close costs about 10 ms. A `clear()` that emptied the folders costs what the empty case does.
- 2026-11-07: a finding on the way, from plan 17's race test flaking about 7 runs in 300: on macOS, APFS lets `rmdir` succeed on a directory while an `open(O_CREAT|O_EXCL)` inside it succeeds too (a probe with no oxide code, `scratchpad/apfs_rmdir_probe.py` during the session: 2 orphaned files in 54,353 creates against a tight `rmdir` loop with two creators; 0 in 215,724 with eight, which keep the directory non-empty). That is the gap behind the `EINVAL` plan 17 classified as a vanished directory, one step later: the create has succeeded, and the data write or the rename then fails with `ENOENT` or `EINVAL`. The test tolerates exactly that shape on macOS (a few in 2,400 writes); Linux stays strict. D-042 records the gap and plan 17 §10 the diagnosis. **Open for Michael and the architect:** should a write recover from it, by treating `ENOENT`/`EINVAL` from the data write as a vanished directory (another round) and, when `commit_name` finds the `.tmp` gone and no `.val`, re-creating the file from the data still in hand (`put_value` has it)? The architect's recommendation, adopted: not now. It is macOS-only kernel behavior, the exposure needs an `rmdir` of an empty folder and a first write into it in the same microseconds (the probe's rate was against a tight `rmdir` loop), the failure is loud and clean (`OSError`, rollback, no row), and the recovery as proposed would put a value write under the write lock, which the design forbids. The soak would show it (any non-`Timeout` exception is a worker problem, and chaos includes `clear()`); if it ever appears, build the lock-free half only: in `create_in`, treat `ENOENT`/`EINVAL` from the data write as a vanished directory and `lstat` the parent after a successful write, going another round on `NotFound`, which settles the state before the lock is taken. Also from the review: the sweep skips a `FanoutCache`'s shards (`Role::Shard`) until plan 17 part 2, so a leftover under `fanout/` isn't reached yet; and the soak's `orphan_tmp` counts a `.tmp` from two minutes old, so it keeps counting one until a last close an hour after the kill.
- 2026-11-07: the architect's review: PASS with required changes, applied (the new mtime test joins `MIRI_SKIP`; the macOS race is any sweep's, not `clear()`'s, and the 30-second age doesn't guard it; the hour states its failure mode). Suggestions taken: the temp-file pass runs after the directory age check; the race test classifies with the production `directory_vanished` and says in its name what it tolerates; the prefix rule from `value_path`; the `clear()` docstring names the budget; D-042's "no age limit" says on the folders.

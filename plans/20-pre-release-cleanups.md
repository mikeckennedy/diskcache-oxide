## Part A: `TransactionAborted(RuntimeError)`

Today `Error::TransactionAborted` maps to a plain `RuntimeError` (`crates/diskcache-oxide-py/src/lib.rs`, `to_py_err`), so a caller can't tell it from the library's other `RuntimeError`s (fork poisoning, a nested or missing transaction, an end inside an operation, a filesystem without WAL). It is raised at four sites:

1. `store.rs:926`: a write inside a doomed held transaction (SQLite rolled it back after a full disk or an I/O error, or an operation that failed inside it couldn't be undone). Core message, which is accurate.
2. `store.rs:1824`, reached through the `Held` arm's `result.map_err(to_py_err)` (`cache.rs:1357`): the owner's own exit of a doomed or SQLite-ended transaction. Core message, accurate.
3. `cache.rs:1338`, the `Done { committed: false }` arm of `Transaction::__exit__`: the owner's exit after another thread rolled it back (D-031) or after an earlier exit ended it, including one made from inside the block's own operation (checked: a pickle hook's `__exit__` lands here). New message.
4. `cache.rs:1350`, the `Ending` wait coming back `Some(false)`: the owner's exit while another thread's end ran and rolled back. New message.

The change:

- `create_exception!(diskcache_oxide, TransactionAborted, PyRuntimeError, "...")` in `lib.rs`, beside `TransactionBusy`, created under the public package name so it pickles across `multiprocessing` like the others; registered on the module; `Error::TransactionAborted` maps to it in `to_py_err`. The other transaction-misuse errors (`NestedTransaction`, `NoTransaction`, `EndInsideOperation`, `ForkPoisoned`, `Unwritable`) stay plain `RuntimeError`: they are programming errors or environment problems, not "your writes are gone".
- It subclasses `RuntimeError`, so code catching `RuntimeError` keeps working; every site that raises it today raises it still.
- Sites 3 and 4 raise `TransactionAborted::new_err` with "the transaction did not commit: another thread or an earlier exit ended it, or it was rolled back after an error" (the architect's wording: it makes no claim about what was written, which in a fork child's poisoned copy would be wrong, and still contains "rolled back"). Sites 1 and 2 keep the core message. One class, two messages; the core error stays one variant.
- `__init__.py` re-exports it and adds it to `__all__`; `_core.pyi` gets `class TransactionAborted(RuntimeError)` with a docstring, and the `Transaction.__exit__` and `transact()` docstrings name it. `tests/unit/test_stubs.py` keeps the stub honest.

Tests:

- Adapt the existing asserts of `RuntimeError` + 'rolled back' to assert `TransactionAborted` (and that it is a `RuntimeError`): `tests/unit/test_transact.py:162`, `:325` (scenario script), `:458`, `:537`, and `tests/unit/test_concurrency.py:558`; the cross-thread cases check the new message, the doomed-write cases the core one.
- A pickling round trip (`type` and `__module__ == 'diskcache_oxide'`), a new test beside the per-class ones (`test_codec.py:513`, `test_caches.py:623`, `test_decode_errors.py:589`).
- The other `RuntimeError`s (a second `__enter__`, a nested `transact()` in a fork child) are not `TransactionAborted`.
- `FanoutCache.transact(key=)`: the cross-thread case raises it (`tests/unit/test_fanout.py`), since it shares `Transaction`.

Documentation: `user_guide/errors.qmd` (a `TransactionAborted` row in the table; the "`RuntimeError` from a transaction" section split so the class has its own heading, the quoted core message kept for case 1 and the new one added), `user_guide/transactions.qmd`, `user_guide/switching-from-diskcache.qmd`, `user_guide/divergences.qmd` (D-031's paragraph), `tests/DIVERGENCES.md` (D-031 and the FanoutCache entry name the class), the skill's exception list and transaction line, the module docstring's exception hierarchy, CHANGELOG under Changed. `make docs`, commit `site/`.

## Part B: the `open_store` registration race

`Store::open_store`'s slow path (`store.rs:444-522`) opens a connection, runs `prepare_creating`, and opens the store's pin, all before it takes the registry (which never waits on I/O). When two threads open the same directory for the first time at once, the loser finds the winner's store under the registry and drops both its connection and its pin. Both closes land beside the winner's live pool, where SQLite's unix VFS defers them (plan 18): one pending descriptor per mode. D-017 documents it as one of three remaining sources.

### Which file is the connection on

Every use of the opened connection, joining a live store or seeding a new one, has to know it is on the file the store names. Today the new-store seed (`store.rs:518-520`) never checks: a database replaced between `connect` and `open_pin` leaves the pool serving a connection on the unlinked old file, whose writes are lost (the architect, B3). So each attempt brackets its connect with two reads of `(dev, ino)` at `db_path`, inside the `retry` closure: `before`, right after `enter_until` and before `open::connect` (`None` when the file doesn't exist yet, a brand-new cache); `opened`, right after `connect` returns (required: SQLite creates the file at open). The connection is on file X when `opened == X` and `before` is `None` or `X`. While a live store pins X its inode can't be freed or reused, and the connection's own fd keeps its file allocated, so with both reads showing X the path went from X to another file and back to X around the open, with X never freed: only a rename away and back, which nothing in or around the library does. With `before` `None` the claim rests on the open itself and the read after it: a file created at the path and replaced within that microsecond window, the same class of outside interference. That is `open_pin`'s standard (it reads before and after its own open).

### The change

1. **`Store::claim_live(stores, id) -> Option<Arc<Self>>`**: find a live (`!is_retired()`) store with `file_id == id` and claim it with no pin (`debug_assert!` that none comes back, as `add_handle_until` does). `lookup` uses it too, so the two can't drift.
2. **Take 1, after `prepare_creating`, before the pin.** If the connection is on `opened` (above), take the registry and `claim_live(opened)`. On a hit: release the registry, adopt the connection into that store's pool (step 4), and return `Joined(store)` from the closure. `Joined` carries no gate: `join` runs after the closure without a level, as on the fast path (its write enters the gate itself). The claim is the last fallible step in the closure (claim, drop the registry, adopt, return; adopt can't fail), so `lockwait::retry`, which re-runs the closure only on `Err(Timeout)`, never re-runs a closure that claimed, and a failing `join` releases through `release_now_or_defer` as the fast path does. Taken after `prepare_creating` rather than straight after `connect` (the architect's suggestion): on a brand-new directory the winner registers while the loser waits in `prepare_creating` on the creation, so this placement catches that race too, and the pin's open is the only window left.
3. **No live store: the pin, then take 2**, as today, with the closure returning `Opened { gate, conn, limits, pin, file_id, conn_file }`. Under the registry, `find` (live, or retired for the same directory) and claim with the pin, reviving a retired store; the connection goes to that store only if `conn_file == file_id`, else it's dropped. A new store is seeded with it only if `conn_file == file_id`; otherwise the open fails with `open_pin`'s "the database file was replaced while it was being opened" `Error::Io` (`OSError`), since `prepare_creating` checked the old file's role and format, not the new one's. That's a behavior change only for a database replaced in the middle of an open, which today could lose writes.
4. **`Pool::adopt(&self, gate, conn)`**, wrapped by `Store::adopt` beside `give_back`: under the pool's mutex, after `reset_if_stale`, push it as idle (a `PooledConn` of the current generation, `Applied::default()`, as the seeding checkout makes it) if `idle.len() < max_idle`, else close it outside the mutex under the caller's gate level (the `checkin` surplus rule). It doesn't touch `checked_out`, a counter nothing limits on (one test assert reads it), which is why it isn't `checkout` + `checkin`: `checkout` pops an idle connection when there is one and the new connection would be dropped unused beside the pool. The generation tag is right only because the connection is opened and adopted under one gate level, so no fork can come between: `adopt` takes the generation captured at connect time and `debug_assert!`s it equals the current one. `Store::adopt` first raises the pool's idle cap to this handle's `max_connections` (`join` raises it only afterwards, `store.rs:629`), so a handle that asks for more keeps its connection, then re-checks retirement after the push, as `give_back` does. The new-store seed uses `adopt` too, replacing `checkout(|| Ok(conn))` + `checkin`, so a pre-opened connection enters a pool one way.
5. What still closes one beside a live pool after this: an open whose winner registered during its pin's open (its pin), and an adopted connection over the idle cap (its connection). D-017 says so.

`#[cfg(test)]` hook, as `shard_identity::after_open_store` does: `open_race::after_prepare(directory)`, between `prepare_creating` and take 1, so a test can park thread A there while thread B opens and registers the store.

### Tests (core, `store.rs` test module, macOS and Linux)

All take `testutil::one_global_fork_at_a_time()` (a thread parked at the hook holds a shared gate level, and another test's simulated fork would wait on it), assert `settled_handles()` rather than `handles()`, and start from a directory whose earlier store is fully dropped (or B revives a retired store instead of registering a new one). The fd counter, `(dev, ino)` over `/dev/fd` on macOS and `/proc/self/fd` on Linux, goes in `testutil` and `store/fork_timeout.rs`'s `fds_inside` shares it.

- **The race on an existing database:** A parks at the hook; B opens and registers; A resumes. A joined B's store (`Arc::ptr_eq`), `settled_handles() == 2`, the pool's `idle()` is one up and `checked_out` unchanged, and the fds on the database file are those of the store plus one more idle connection: no pending descriptor.
- **The race on a brand-new directory:** the same with no database before either open (A parks after its `prepare_creating`, which B's creation made it wait on or follow); the same assertions.
- **The idle cap:** the pool already at `max_idle` idle connections and A asking for no more: the adopted connection is closed, `idle()` unchanged, the store works, and the one pending read-write descriptor shows (asserted, as D-017 documents). With A asking for a larger `max_connections`, its connection is kept.
- **A replaced file:** A parks at the hook; the test renames a different valid, prepared database over the path; B opens it and registers. A's `opened` read sees the old file, so take 1 is skipped; its pin opens the new file and take 2 finds B's live store: A joins it (`Arc::ptr_eq`), and the pool's `idle()` didn't grow (A's connection, on the old file, was dropped, not adopted).
- **A seed on a replaced file:** A alone, parked at the hook (the hook is before the pin, so A's `conn_file` is the old file), the test renames a valid database over the path: A's open fails with `Error::Io` "replaced while it was being opened", and no store is registered.
- **A retired store** (every handle closed, then two opens race): take 1 finds nothing live, take 2 revives it with the pin, as today.
- Python, `tests/conformance/test_threads.py` (oxide-only, D-017): 16 threads open one existing directory at once behind a barrier, five rounds; every handle reads the seeded value, and closing them all leaves no fd. Not within the budget while they're open (see Progress, 2026-11-08, the burst).
- The existing open and fd suites (`test_threads.py`, `test_fanout.py`'s fd budget tests, `fork_scenarios.py`) unchanged and green, 3.14t included.

Documentation: D-017's sources of a pending descriptor change: "an open that lost the race to register its store (its connection and its pin)" becomes "an open whose winner registered while its pin was being opened (its pin), and a connection adopted into a pool already at its idle cap", and the D-017 text says a database replaced in the middle of an open now fails it with `OSError`. Plan 18's "Not changed" paragraph gets a pointer here. CHANGELOG under Fixed.

## Decisions

- Part A: one class, two messages (the architect agreed).
- Part B: a database replaced in the middle of an open fails it with `OSError` (the architect's preferred option) instead of seeding the pool from the old file.
- Part B: take 1 sits after `prepare_creating`, not straight after `connect` as the architect suggested, so it also catches the brand-new-directory race (reasoned above).

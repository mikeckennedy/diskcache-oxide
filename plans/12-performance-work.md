## Step 1: an in-place `incr`

**Why:** oxide's `incr` on a live key costs about 24 µs against stock's 17 µs, and Talk Python runs three per request (plan 11, section 3).

**What:** inside the existing `write_files` closure (so the read and the write both run under `BEGIN IMMEDIATE`, and the savepoint path inside a held transaction still applies, `store.rs:759-765`), one lookup of the row's id, mode, value, expire_time and filename, with no `PRELUDE_SQL` (its expired-row `EXISTS` sweep check is part of the cost being removed). Then:

- **Live number:** one `UPDATE cache SET mode = ?, value = ?, store_time = ?, store_seq = MAX(COALESCE((SELECT MAX(store_seq) FROM cache), 0) + 1, (SELECT next_seq FROM totals WHERE only = 1)) WHERE rowid = ? RETURNING store_seq`. The new version comes from the same expression the upsert uses (`rows.rs:104-108`), never from `totals.next_seq` alone: that's a floor raised before deletes (`rows.rs:7-11`, `raise_seq_floor` at `rows.rs:202`), not a counter, and using it could repeat an older version of the row (a stale `delete_version` would then delete the fresh value) or fall below a running `clear()`/`expire()` snapshot. `totals` isn't written. `mode` is set because an int plus a float delta is a Real (`ops.rs:125-133`). `expire_time` is kept.
- **Miss or expired:** the existing upsert path, unchanged.
- **Anything else:** `NotNumeric`, as today. (Inline numbers always have size 0 and are never spilled, `ops.rs:52`, so there's no size-change or file-backed case.)

The fast path deliberately skips `cull` and the expired-row sweep, which every `incr` runs today (`ops.rs:438`, `ops.rs:605-609`). That matches diskcache's in-place `UPDATE` but changes oxide's behavior, so it's pinned by a test.

**Done when:** the conformance suite's `incr`/`decr` cases pass against both backends, and new unit tests show:

- the version strictly increases and never repeats after a delete-then-`incr`;
- an `incr` made during a chunked `clear()` survives;
- a stale version's `delete_version` after an `incr` returns `Gone`;
- Int to Real changes the mode;
- the expiry is kept;
- the fast path runs no cull and no sweep;
- `hot_statements_are_never_reprepared` (`ops.rs:1192`) still holds.

`bench/scaling/incr_series.py` shows the gain (target: at or below stock's 17 µs on the Mac). This is a second writer of `store_seq`, so it needs a fresh soak before production.

## Step 3: public `transact()` (roadmap Phase 6b)

**Why:** grouping a request's three counter bumps into one write transaction cuts them from 79 to 48 µs on oxide, the biggest single win found (plan 11, section 4). Stock diskcache has `transact()`; oxide only has the `_hold_write_transaction()` test hook.

**Prerequisites (blocking):**

- Bound, or explicitly accept and document, the unbounded waits the gate docs say `transact()` must bound before it ships (`gate.rs:36-41`: `HeldShare::enter` while the owner is forking or parked, or when the share was inherited), and the three waits in `tests/DIVERGENCES.md:224`.
- Verify carry-overs 6 and 7 are fixed. Both already are: `begin_hold` uses `try_lock_nested` and fails with `WriteLockBusyInTransaction` at gate depth > 0 (`store.rs:1161-1168`, test at `store.rs:2169`), and `pop` decodes after commit (`ops.rs:345-351`).

**What:** `Cache.transact(retry=False)` as a context manager on the existing held-transaction machinery (`begin_hold`), used as `with cache.transact() as tx:`. `tx` is the transaction handle, whose methods are the cache's; on the owning thread, calls on the cache itself inside the block are in the transaction too, as in diskcache (Michael, 2026-11-05). An async form, `async with cache.transact_async() as tx:`, is deferred to `AsyncCache` (roadmap Phase 5), where waiting for the write lock never blocks the event loop (Michael, 2026-11-05).

- **Reentrancy lives in the binding.** The core refuses a second hold on one thread (`NestedTransaction`, `store.rs:1153`), so the Python `transact()` checks `held_by_this_thread()` and returns a pass-through context manager. As in diskcache, an inner block's exit doesn't commit, and an inner exception the caller catches doesn't undo the inner block's writes (no per-block savepoint).
- **Cross-cache refusal.** Inside one cache's transaction, starting one on another cache whose write lock another thread holds fails at once with `WriteLockBusyInTransaction` (a free lock is taken, `store.rs:1167`). It surfaces as a `Timeout` subclass so `retry=True` can tell it apart and never retries it (both errors map to plain `Timeout` today, `crates/diskcache-oxide-py/src/lib.rs:75`). diskcache's `Cache.transact` defaults to `retry=False`.
- **Durable behavior is already decided; pin it.** Starting a transaction raises on a durable handle (`tests/DIVERGENCES.md:236`). A failure inside the block raises too, because durable never swallows while this thread holds a transaction on the store (`cache.rs:546-549`). A failed COMMIT raises (`close_pinned`, `store.rs` around line 1503). Pin D-020 through the public API (`tests/DIVERGENCES.md:152`).
- **Transactions belong to a thread, not a task.** The docs say an `await` inside the block lets another coroutine on the same loop thread write inside the transaction and roll back with it, and that a fork waits, with no timeout, for every open transaction.
- **Lock order** stays write lock, then gate, then connection (`store.rs:9-16`).
- **API surface:** `CacheLike` stays without `transact` (Michael, 2026-11-05), so FanoutCache (plan 13) can still satisfy it; add a `TransactionalCacheLike(CacheLike)` protocol with `transact`, which `Cache` and `NullCache` satisfy. Add `transact` to `NullCache` (a no-op context manager, including `NullCache(invalidate=)`), and the stubs. `Caches` forwards no cache methods (its lookups return a `Cache` or a `NullCache`), so it needs only a test. Keep `_hold_write_transaction` as a thin alias until the D-012 tests move to the public API, then remove it. Divergence entries for every difference from diskcache.

**Done when:** conformance tests against diskcache for the shared semantics (commit on exit, rollback on exception, reentrancy, both nested-block rules), and unit tests for:

- fork from a non-owner thread mid-transaction, and fork from the owner (D-020);
- commit or rollback from another thread while the owner is inside an operation (`store.rs:1405-1433`);
- a GC finalizer dropping the context manager inside an operation (the `abandon` path);
- the cross-cache refusal with `retry=True`;
- a durable handle whose BEGIN times out.

`scripts/model-check.sh` passes, the user guide is updated, and a fresh soak is required.

### Design

Reviewed by a second, independent architect: PASS with required changes, all applied below (2026-11-05).

**The waits (prerequisite).** One rule bounds every end: ending a transaction gets a deadline, and an end that *couldn't run* in time (nothing released, `write_word` still `Some`) is either abandoned to the owner's operation or *parked* for the end of the fork. It is never waited for without bound.

- `HeldShare::enter` while the owner is forking or parked (`gate.rs:603-621`): add `HeldShare::enter_until(deadline) -> Option<SharedGuard>`, the same loop with the `OwnersFork` sleep also ending at the deadline. `HeldTransaction::end` (`store.rs:1384`) uses it; on `None` it returns an internal `EndOutcome::NotEnded` (not `Error::Timeout`) with nothing released. This wait exists only while a fork is pending (`gate.rs:618`), so a draining fork end is coming (`Gate::defer`, `gate.rs:321-329`).
- An inherited share (`gate.rs:609`, `ShareEntry::Inherited`): the same method calls `gate.enter_shared_until(deadline)` instead of `enter_unbounded`. That wait also exists only behind a pending fork (`gate.rs:253-260`).
- A commit from another thread waiting for the owner's operation (`store.rs:1417-1427`, the `LENT_POLL` loop): this waits on the owner's operation, not a fork, so it never parks. At its deadline it takes the abandon branch above it (`store.rs:1405-1416`: the operation rolls back when it hands the connection back) and returns `Error::Timeout`. Only a timed-out *re-entry* (`enter_until` returning `None`) inside that loop parks.
- **Parking keys on `NotEnded` only.** `close_pinned`'s COMMIT can itself return `Error::Timeout` (SQLITE_BUSY/LOCKED, `error.rs:120`, `store.rs:1513`) after `end` has already released everything (`store.rs:1441-1449`). That is a finished, failed commit: report it, never park it. On `NotEnded`, `park` moves the live fields into a new `HeldTransaction` (the husk keeps `write_word: None`, so its drop is a no-op), **drops its share first** (below), and calls `GATE.defer(|| DEFERRED_ENDS.push(t), || run_blocking(&drain_deferred_releases))`, with `DEFERRED_ENDS: TakeAllStack<HeldTransaction>` beside `DEFERRED_OWNERS` (`store.rs:85`). A parked commit returns `Timeout`; a parked rollback returns `Ok`.
- **A parked end holds no gate level** (proven in the models, 2026-11-05). Keeping the share's level while parked deadlocks: the owner's fork ends before the end is recorded, so its after-fork drain sees no flag; a third thread claims a fork; the parker's try fails behind it; and that fork, not the owner's, waits forever for the parked level, which only a drain at its own end could release (model 18 found it; model 19 pins it). So `park` drops the share before it records, keeping the write lock and the D-020 hold: other writers still wait, and a child forked before the drain is poisoned for that file (D-020) instead of being kept out by quiescence, which is safe because no thread is inside SQLite on that connection. `end` and `abandon` on a parked transaction (share `None`) enter with a plain `GATE.try_enter_shared()`, which is reentrant because only the drain, on its own level, ends one. So a drained end can't fail; the drain's push-back is an unreachable release fallback (it asserts in debug builds). Every deferral then holds no level, as handle releases don't, so `Gate::defer`'s contract (the next fork end drains) holds unchanged.
- **The drain drops each parked transaction** (`drain_deferred_releases`, `store.rs:1586`), first, on its own level and outside the registry mutex, then does the releases. Dropping, not `finish(false)`, matters: if the owner forked from inside an operation, `end` reports `EndInsideOperation` and `Drop` routes it to `abandon` (`store.rs:1474-1479`). In a child the drain finds the generation changed and forgets the connection (`close_pinned`, `store.rs:1496`).
- **Between a park and the drain the transaction is still the owner's.** The slot stays `Here(owner)`, so whenever the owner can enter the gate, `held_by_this_thread` is true, a nested `transact()` passes through, and its writes land in the transaction that will roll back. Having given the share up, the owner holds no level, so behind another thread's fork its calls wait like anyone's, and two orderings are legitimate. If the owner gets back in after that fork ends but before its drain runs, `on_pinned` succeeds and the write joins the doomed transaction, which the drain rolls back. Otherwise `on_pinned` refuses, the write waits for the write lock within its `timeout`, and once the drain has run it commits on its own, as after any cross-thread end. Neither is a silent loss: the owner's own `__exit__` reports a transaction that didn't commit (3c, below), and the store test accepts both.
- **Budgets.** An explicit commit gets the transaction's `timeout` (`HeldTransaction.timeout`). `Drop` (a GC finalizer) and a cross-thread rollback have no caller who needs the outcome, so they try once and park, rather than block a finalizer for up to `timeout`.
- **Accepted, documented, unchanged:** `Gate::begin_fork` itself (Python can't refuse a fork, D-027), and `HeldShare::enter` from `abandon` (`store.rs:1458`), which runs only on the owner thread inside its own operation, where `try_enter_shared` is reentrant and never waits. Assert that precondition with `debug_assert!`: this thread's `LENT` list holds this store's key, or its guard depth is > 0 (a `cfg(debug_assertions)` accessor; `own_depth()` includes held levels, `gate.rs:367-370`, so it proves nothing). Rewrite `gate.rs:36-41` and the `tests/DIVERGENCES.md:224` bullet to say this.
- Add a compile-time assert that `HeldTransaction: Send + Sync` (`TakeAllStack` is `Sync` only when `T` is, `stack.rs:22`).

**Rust surface (`crates/diskcache-oxide-py/src/cache.rs`).** `WriteHold` (`cache.rs:903-947`) becomes `Transaction`: `cache: Py<Cache>`, `retry: bool`, `state: Mutex<TxState>` with `TxState { Ready, Entering, Held(HeldTransaction), PassThrough, Done { committed: bool } }`. `Cache.transact(retry=False)` returns one unentered (`retry` extracted as a strict `bool`, as D-014 does). `__enter__`:

1. Under the mutex, `Ready` → `Entering`, then release the mutex. Anything else raises `RuntimeError`, including `Entering` (a concurrent `__enter__`); the state is never held across the detached `begin_hold`.
2. `cache.store.held_by_this_thread()` (`store.rs:1134`) → `PassThrough`. Checked here, not in `transact()`, and per store, so a second handle on the same directory passes through too. An inherited transaction doesn't count, so a child's nested `transact()` raises `Unwritable` from `check_writable` (`store.rs:1150`; a `RuntimeError`, D-020).
3. Otherwise loop: `ensure_open`, then `detach(begin_hold)`. On `Error::Timeout` with `retry`, `py.check_signals()?` (attached, outside `detach`) and try again. Never retry anything else.
4. Store `Held` or `PassThrough`; on any error, put back `Ready` before raising. Return `self.cache` (the `tx`). The cache, not a proxy: only the owner thread's calls join the transaction, through any handle on the store, so a proxy would be a second API with no new guarantee. diskcache yields `None`, so this is a superset.

`__exit__` takes the state out of the mutex, then acts. `Entering` raises `RuntimeError`. `PassThrough` → `Done { committed: true }`, no commit (`return false`). `Held` → `finish(exc_type.is_none())`, then `Done { committed }` with `committed` true only for a commit that returned `Ok`; an `EndInsideOperation` leaves `Done { committed: false }`. `Done` (a second `__exit__`, or the owner's exit after another thread ended it) with no exception raises `TransactionAborted` (the existing core error, a `RuntimeError`) unless `committed`; this replaces today's `abandoned` flag, which returns `Ok(false)` when another thread ended it (`cache.rs:937-944`). A GC drop of a `Transaction` runs `HeldTransaction::drop` (abandon inside an operation, park behind a fork). New exception in `lib.rs`: `create_exception!(diskcache_oxide, TransactionBusy, Timeout, ...)`, with `Error::WriteLockBusyInTransaction` mapped to it (`lib.rs:75`). Export it from `__init__.py` and `__all__`. `_hold_write_transaction` returns `Transaction` with `retry=False` until 3e removes it.

**Python surface.** `TransactionalCacheLike(CacheLike, Protocol)` with `transact(self, retry: bool = False) -> AbstractContextManager[Self]` (`protocol.py`), exported beside `CacheLike`; `CacheLike` itself gets no `transact`, because FanoutCache's shard-scoped `transact` takes a key (plan 13, section 5). `NullCache.transact` checks `retry` is a `bool` and returns `contextlib.nullcontext(self)`. With `invalidate=` it does **not** open a transaction on the real cache: a switched-off cache must never take a write lock or raise `Timeout`, so forwarded removals inside the block land at once and an exception doesn't undo them (say so in `null.py`'s docstring). `_core.pyi`: `class Transaction` (`__enter__ -> Cache`, `__exit__ -> bool`, documenting `RuntimeError` for re-entry and `TransactionAborted`'s `RuntimeError` on an exit after the transaction was ended elsewhere), `Cache.transact`, `TransactionBusy(Timeout)`.

**Divergences.** D-020 becomes pinned (drop "when `transact()` lands"). Update D-027's waits bullet and D-028's "starting a transaction" to name `transact()`. New: **D-029 `transact()` hands back the cache, and every handle on the directory shares it** (diskcache: `None`, and a second handle's `BEGIN` waits out the timeout). **D-030 A transaction on a second, busy cache fails at once with `TransactionBusy`, and `retry=True` retries only `Timeout`** (diskcache: waits, and `retry=True` loops on any `OperationalError`). It's interruptible only between attempts: each attempt waits up to `timeout`, detached. **D-031 A transaction may end on another thread, within its `timeout`** (diskcache: "may not be shared between threads"): a commit that can't reach it raises `Timeout` and rolls back, and the owner's own exit afterwards raises `RuntimeError` (`TransactionAborted`) unless it committed.

**Risks.**

- Never hold `Transaction.state` while finishing or beginning: that mutex is taken attached, and `finish` waits with the interpreter released (today's pattern, `cache.rs:921-925`). `Entering` is what keeps a second caller out meanwhile.
- Park only on `NotEnded`. An `Error::Timeout` out of `end` may be a finished, failed COMMIT whose locks are already released (`store.rs:1441-1449`); parking that husk would park nothing and hide the failure.
- `__enter__` must not go through `attempt`/`store_failed` (`cache.rs:534-551`), or a durable handle would swallow `BEGIN`.
- `park` drops the share *before* it records, and records before it flags (`gate.rs:321-329`). A parked end that keeps its level deadlocks the next non-owner fork (model 19). A drained end can't fail: on a parked transaction `end` enters on the drainer's own level, so the drain's push-back is an unreachable fallback.
- Keep `end`'s release order: the gate dropped before the write lock, then the D-020 hold, then the share (`store.rs:1445-1449`; `Lend::drop`, `store.rs:323`).
- Lock order stays write lock, then gate, then connection (`store.rs:9-16`); `begin_hold` keeps `try_lock_nested` at depth > 0 (`store.rs:1166`).

## Step 5: lift the shared-handle read ceiling (rewritten 2026-11-05 from measurements)

**Why:** plan 13's benchmark (13i) showed that FanoutCache doesn't lift the free-threaded read ceiling for threads sharing one handle, and a diagnosis then found what does it (`bench/results/read-ceiling-2026-11-05.md`, with the env-gated prototypes in `bench/results/read-ceiling-prototypes-2026-11-05.diff`; summary here). The ceiling is per store, not per handle: four handles on one directory perform like one shared handle, while four directories reach about 1.9M reads/s on the Mac and 3.4M in the Linux VM.

- **Plain `Cache`:** SQLite's per-file shared-memory mutex (`unixShmNode.pShmMutex` in `unixShmLock`, `sqlite3.c:45938`). Every read takes it twice, and it's held across the `fcntl` lock syscall, so a waiter parks in the kernel. In a 5 s `sample`, 4,644 of 4,986 mutex-wait samples were there, and 336 in oxide's pool.
- **`FanoutCache` at the default budget (one connection per shard):** a thread that collides on a shard fails `slots.try_acquire` and sleeps 50 µs (`genlock.rs:22` `POLL`, `Slots::acquire_until` at `genlock.rs:284`): 6,134 `nanosleep` samples.
- **Ruled out:** the gate and slot atomics, PyO3 extraction, refcounts and `HandleConfig` state (each under 1% of self time).

Prototypes, measured with 4 threads on one shared handle, 6-byte reads, 3.14t (k reads/s):

| Case | Mac before | Mac after | Linux VM before | Linux VM after |
|---|---|---|---|---|
| `Cache`, SQLite mutex spin | 805-831 | 1,442 | 1,187 | 1,708 |
| `Cache`, + slot spin | | | | 1,898 |
| `Cache`, + pool spin | | 1,613 | | |
| `FanoutCache(8)` default, mutex + slot spin | 768-781 | 1,192-1,204 | 1,084 | 1,518 |
| `FanoutCache(8)` at 32 connections, mutex spin | 1,223 | 1,546 | 1,292 | 1,959 |

Single-thread and separate-directory numbers don't change.

**What:**

- **5a, a spinning SQLite mutex:** the library supplies its own `sqlite3_mutex_methods` through `SQLITE_CONFIG_MUTEX`, pthread mutexes underneath (so fork behavior is unchanged: the gate quiesces before a fork, and the bundled SQLite is private to `_core.so`), spinning a bounded number of `try` attempts before blocking. Recursive and static mutexes are honored. It's installed once, before `sqlite3_initialize` and any connection. The prototype's install order (initialize, shutdown, GETMUTEX) is fragile and must not ship.
- **5b, the slot wait:** replace the fixed 50 µs poll with a short spin and yield phase before the existing poll, without holding a gate level (`reserve_slot` runs before `enter_until`, so the fork protocol is untouched). A wait woken by a condvar is rejected (see the design: it would put an OS lock outside the gate, where a fork can copy it held).
- **5c, the pool mutex:** second order (+12% on the Mac; Linux's std mutex already spins). Build only if a Linux measurement after 5a and 5b justifies it.
- **FanoutCache's default connection budget** (Michael's decision M2: 8 in total, one per shard) costs shared-handle reads: 1.05M against plain `Cache`'s 1.46M on Linux before these fixes. Report the after-fix numbers to Michael so he can decide whether to keep it.

**Done when:** the model check and `scripts/check.sh` pass; a test pins that the custom mutex methods are installed before any connection (and that `sqlite_compile_options` and threadsafety are unchanged); the 4-thread probe and `bench/fanout.py` show the gain on the Mac, in the arm64 Linux VM and on x86-64 Linux (the htz host), with single-thread numbers unchanged; every SQLite open in both crates goes through one entry point that installs the methods, pinned by a grep test; a CPU-oversubscribed run (more threads than cores) shows no regression from spinning. Spinning changes the locking that every read uses, so a fresh soak is required before production.

**5a, the mutex methods (new module `crates/diskcache-oxide-core/src/sqlite_mutex.rs`).**

- **Why the install point matters.** `sqlite3_config` refuses every option except LOG and PCACHE_HDRSZ once SQLite is initialized (`sqlite3.c:188802-188809`, `SQLITE_MISUSE`), and SQLite initializes itself on first use: `sqlite3_mutex_alloc(FAST)` calls `sqlite3_initialize` (`sqlite3.c:30660-30662`), and rusqlite calls exactly that from `ensure_safe_sqlite_threading_mode` on every `Connection::open*` (rusqlite `inner_connection.rs:45`, `:417-443`), before `sqlite3_open_v2`. rusqlite makes no other init or config call on our paths (its `trace::config_log` is unused). `sqlite3_threadsafe`, `sqlite3_libversion` and the `SQLITE_VERSION` constant don't initialize. `sqlite3_memory_used`/`_highwater` (py `_sqlite_memory`, `lib.rs:286`) don't initialize either, but they take the MEM static mutex, so they also run after `ensure_installed`.
- **One entry point for every open (R1).** `sqlite::open(path)` and `sqlite::open_in_memory()` call `ensure_installed()` and then rusqlite. Every open in both crates goes through them, tests included: today's direct opens are `open::connect` (`open.rs:191`), `open_pin` (`store.rs:1787`; harmless today only because `connect` runs first, `store.rs:450` before `:458`), `sqlite::compile_options` (`sqlite.rs:25`), and test-only `pool.rs:307`, `store.rs:2661`/`:2691`, `store/fork_timeout.rs:798`/`:1315`/`:1362` and the py crate's `codec/mod.rs:391`/`:405`. A grep test bans `Connection::open` (any variant) anywhere else in `crates/`. The py module init `_core` (`lib.rs:309`) also calls `ensure_installed()` first, before `install_fork_barrier`.
- **`pub fn ensure_installed() -> MutexStatus`**, run once under a `std::sync::Once`: `sqlite3_config(SQLITE_CONFIG_MUTEX, &METHODS)`, then `sqlite3_initialize()` inside the same `Once`, so no open through the entry point can reach SQLite between the two. It never calls `sqlite3_shutdown` or `GETMUTEX`. Statuses: `Installed` only once our `xMutexInit` has actually run (a release-build `AtomicBool` it sets), `InitFailed` when `sqlite3_initialize() != SQLITE_OK`, and `TooLate` when config returns `SQLITE_MISUSE`, logged once through the logging bridge.
- **What `TooLate` means.** It is safe only if the other initialization *finished*: SQLite then keeps its own pthread mutexes, correct and unspun. A concurrent foreign initialization is undefined behavior, not a clean `TooLate`: config checks only `isInit` (`sqlite3.c:188802`), which `sqlite3Initialize` sets at its end, while `sqlite3MutexInit` copies the default methods at its start (`sqlite3.c:30598-30627`). So config can succeed mid-init, leaving two mutex implementations, two STATIC_MAIN objects, a double init, and a `pInitMutex` allocated by SQLite's `pthreadMutexAlloc` (through `sqlite3_malloc`) later reaching our `xMutexFree`: heap corruption. Shipped code can't hit it: the bundled SQLite's symbols are private to `_core.so`, and every open in our crates goes through the entry point. A future direct open is exactly what the grep test prevents.
- **`Raced` (added after the build-order step 1 review).** `TooLate` is only the `SQLITE_MISUSE` branch. If config returned `SQLITE_OK` but our `xMutexInit` never ran, another initialization had already copied the default methods and handed out default static mutexes before our config, and finished after it: the mixed-vtable state above. `ensure_installed` reports it as `MutexStatus::Raced` ("raced"). Step 2's module init must refuse it: raise at import, or `std::process::abort()`. `InitFailed` is not terminal: the config stays in place, so a later `sqlite3_initialize` (any open) runs our methods, and the live `sqlite_mutex::status()` then reports `Installed`.
- **Our own pthread implementation, not wrapped defaults.** SQLite's pthread methods are `SQLITE_PRIVATE` (static in the amalgamation) and `GETMUTEX` returns zeros before init, which is why the prototype had to initialize and shut down. Implement all nine methods on `libc::pthread_mutex_t` (add `libc` to core from the workspace): `#[repr(C)] struct SpinMutex { raw: UnsafeCell<pthread_mutex_t> }`. `xMutexAlloc(FAST)` makes one with the default attribute, `RECURSIVE` with `PTHREAD_MUTEX_RECURSIVE`, ids 2 to 13 return `&STATICS[id - 2]` (12 statics, `PTHREAD_MUTEX_INITIALIZER`, sized from `ffi::SQLITE_MUTEX_STATIC_VFS3` with a const assert), and any other id returns null. Dynamic ones come from `std::alloc::alloc` with a null check, returning null on failure as SQLite expects (`Box` would abort on OOM), and never from `sqlite3_malloc` (it takes the MEM static mutex). Every `pthread_mutexattr_*` and `pthread_mutex_init` return is checked; a failure frees and returns null. `xMutexFree` recognizes statics by address range (`STATICS`' bounds) and leaves them alone; it destroys and deallocates dynamic ones. `xMutexInit` sets the `Installed` flag and returns `SQLITE_OK`; `xMutexEnd` does nothing. Every method is `extern "C"` with no panicking path. Core's `unsafe_code` allow moves from `stack` alone to `stack` and this module, each `unsafe` block with a `SAFETY:` comment.
- **`xMutexHeld`/`xMutexNotheld`:** SQLite calls them only inside `assert()` under `SQLITE_DEBUG`, which this build lacks, so they're `None`. Under `cfg(debug_assertions)` the struct gains an owner thread id and a depth, both atomics (the statics are shared between threads), and `xMutexLeave` `debug_assert!`s that the leaver is the owner. A failed `debug_assert!` inside an `extern "C"` method aborts the process, by design.
- **Spin policy in `xMutexEnter` (R2):** `pthread_mutex_trylock`, then `spin_loop()` hints between retries with exponential backoff (1, 2, 4, capped at 64 per gap), until a *total hint budget* `SPIN_HINTS` is spent, then `pthread_mutex_lock`. A budget, not a try count: 100 tries capped at 64 is about 6,080 hints, and on x86 a `pause` is roughly 100-140 cycles (Skylake and later), so hundreds of µs of spinning against a hold of 1-2 µs. `SPIN_HINTS` is a const chosen by the sweep below (1,024), and the budget is 0 at 2 or fewer CPUs (`available_parallelism()`, which on Linux honors a cgroup quota), read once at install. Not just at 1: in the Linux VM at a 2-CPU quota every budget was 13-16% slower than none for four threads on one shared `Cache`, because the spinners used up the quota and the holder was throttled (`bench/results/spin-sweep-2026-11-05.md`); so at 2 CPUs the methods block exactly as SQLite's own do. Measured at 3 and 4 CPUs too: spinning wins with 4 threads (+2% and +22% on shared `Cache`), so the cutoff stays at 3. It loses 14-24% with 8 threads on those quotas, which is oversubscription, not the CPU count; a CPU cutoff can't fix that, an adaptive budget might (5a-2 below). No clock reads in the loop (`Instant::now` costs more than the spin). No env-var knob ships.
- **Fork:** unchanged, because the mutexes are still pthread mutexes taken by the same SQLite call sites, and a spinner holds nothing. The gate quiesces SQLite work before a fork as now. Two SQLite uses run outside the gate, `compile_options`' in-memory connection and `_sqlite_memory` (`lib.rs:286`, which takes the MEM static mutex in this MEMSTATUS build); both are as exposed as they are today.
- **Fork during the install:** a fork while another thread is inside `ensure_installed`'s `OnceLock` leaves the child's `OnceLock` running forever, so the child's first open hangs. SQLite's own init mutex had the same hazard. Step 2's install at import closes it.
- **Python's `sqlite3` is untouched:** it loads a different library, and the bundled one is private to `_core.so`. Verified on the Mac: `nm -gU` on all four `_core*.so` exports only `PyInit__core` (two symbols on 3.15, neither SQLite's). `scripts/linux-check.sh` gains two checks (they live in `docker/in-container-check.sh`, which `scripts/linux-check.sh` runs): `nm -D --defined-only _core*.so | grep -c sqlite3_` is 0 (nothing exported) and `nm -D --undefined-only _core*.so | grep -c sqlite3_` is 0 (no system SQLite linked instead of the bundled one).
- **Tests.** (1) An integration test binary, `crates/diskcache-oxide-core/tests/sqlite_mutex.rs` (its own process, so nothing initialized SQLite first), opens a store and asserts `MutexStatus::Installed`, a debug allocation counter above zero, `sqlite3_config(GETMUTEX)` now `SQLITE_MISUSE` (init happened after our config), `sqlite3_threadsafe() == 1`, and `compile_options()` equal to a pinned list. **5a-2, an adaptive spin (`sqlite_mutex.rs`; designed 2026-11-05, built and swept, not shipped: no arm cleared the bar, see Progress and `bench/results/adaptive-spin-2026-11-05.md`).** The fixed budget wins when the holder is running on another CPU and loses when there are more runnable threads than CPUs: the holder is then often preempted mid-hold, a spinner burns its whole budget against a lock nobody can release, and every hint is quota that a runnable reader, or the holder, needed (8 threads at 3 and 4 CPUs: -14% and -24%). So each mutex must notice that its spinning is crowded or failing, and stop. Two mechanisms, both atomics on `SpinMutex`, and neither touched on the uncontended path (the first `try_lock` succeeding). Reviewed by a second architect: PASS with required changes R1-R3 and approved options, applied below (2026-11-05).

- **A spinner cap.** `spinners: AtomicU32`. A contended enter first loads it (test-and-test-and-set): at `cap` or more it blocks at once, with no RMW on the contended line. Otherwise it does `fetch_add(1, Relaxed)`, and if that prior value was already at the cap it does `fetch_sub` and blocks. An enter blocked by the cap changes neither `estimate` nor `spinners` (net). This bounds what one hot mutex can burn to `cap` cores however many readers pile up, which is the oversubscribed case. The cap is per mutex, so `FanoutCache(8)` can have up to 8 × cap spinners across its shards. Default 1; the sweep tries 1, 2 and `cpus / 2`, because at cap 1 with three waiters two park and each unlock then pays a futex wake, which could eat the Mac's +75%.
- **The spin loop's one exit (R2).** Today `spin` leaves through `return true` inside the loop (`sqlite_mutex.rs:403`). It becomes a loop that `break`s with its outcome (`Got(spent)` or `Failed`); after the loop come the `fetch_sub` on `spinners` and the estimate update, and only then, on `Failed`, `pthread_mutex_lock`. A thread parked in the kernel must never count as a spinner.
- **A decaying budget (R1).** `estimate`, in hints, starting at `SPIN_BUDGET / 2`. A contended enter's budget is `clamp(estimate.saturating_mul(2), SPIN_FLOOR, SPIN_BUDGET)`. A spin that gets the lock after `spent` hints moves the estimate an eighth of the way toward `spent` (glibc's update), computed in `i64` and clamped back into range, so `spent < estimate`, the usual case once warm, can't wrap (on `u32`, `estimate += (spent - estimate) / 8` wraps to about 2^29 in release, and the clamp then gives the full budget every time; in debug it panics inside `extern "C"`, an abort). A spin that exhausts its budget halves the estimate. glibc's adaptive mutex moves the estimate toward the maximum on a failure, which is why it can't back off (and why it gained only +8% in the sweep); here a failure decays it. `SPIN_FLOOR` (32 hints, around a µs on arm64) lets a decayed mutex recover when the load drops, with no clock, but only when holds fit in about 32 hints.
- **The `decay+probe` arm.** In case the floor alone doesn't recover, the estimate is a packed `AtomicU32`: the low 16 bits are the estimate (`SPIN_BUDGET` is at most 4,096 even in the sweep), the high 16 a count of contended enters, and every 64th uses the full `SPIN_BUDGET`. Designed in now as a sweep arm so the phase-change case shows whether it's needed; it ships only if plain decay fails that case. It costs a store on every contended enter (the count changes each time).
- **Updates** are a Relaxed load and a Relaxed store, the store only when the value changes (except the probe count). Racing waiters can lose an update; it's a heuristic. The state sits beside the lock word in the same allocation; that cache line is already contended whenever the state is touched, so no padding unless a profile shows the extra RMW.
- **Correctness doesn't move.** The adaptation picks only how many `try_lock`s run before `pthread_mutex_lock`, which every failed or capped spin still reaches. `#[repr(C)]` keeps `raw` at offset 0 (SQLite never looks inside); `new_static` initializes the new atomics in its `const fn`, `new_dynamic` writes them through the raw pointer as it does the debug fields, and `Layout::new::<SpinMutex>()` picks up the 8 bytes. No allocation, no clock, no panicking path (all arithmetic saturating or in `i64`). A budget of 0 skips every per-mutex atomic: one Relaxed load of `SPIN_BUDGET` remains, ahead of the `spinners` check, so the 2-CPU rule still means plain blocking.
- **Fork.** The gate quiesces SQLite work before a fork, so no gated enter is mid-spin. The two outside-gate uses are not covered: `compile_options`' connection, and `_sqlite_memory`, which takes the MEM static, also taken by every `sqlite3_malloc` in this MEMSTATUS build. A fork landing mid-spin there would leave the child's `spinners` raised with no thread to lower it, so that hot mutex would block for good in the child: slower, never wrong. So install a `pthread_atfork` child handler (registered in `ensure_installed`'s `Once`) that does a Relaxed store of 0 to `spinners` on the 12 statics; it runs only atomic stores, which is safe in a forked child. Dynamic mutexes can't be enumerated, but they belong to connections and are only entered inside the gate.
- **Tests.** The logic is three pure functions, `may_spin(current, cap)`, `budget(estimate, floor, max)` and `next_estimate(estimate, Outcome::{Got(spent), Failed})`, with unit tests: failures halve down to the floor and never below; successes converge on `spent`, including `spent < estimate` and `spent == 0` (no wrap: the result stays at or below the old estimate); the budget never exceeds `SPIN_BUDGET`, is 0 when that is 0, and saturates at `u32::MAX` estimates; a run of failures then successes at the floor recovers; the probe fires every 64th enter and the packed count wraps without touching the estimate. On the methods: N threads incrementing under one FAST mutex lose nothing with the cap forced to 0, 1 and 2, then a `#[cfg(test)]` accessor reads `spinners` back as 0 (no leaked count); the same on a RECURSIVE mutex with recursive re-entry under contention; and the atfork handler's body, called directly, zeroes a raised static.
- **Sweep.** `--cfg dco_spin_sweep` gains `DCO_SPIN_MODE` (`fixed`, `cap`, `decay`, `decay+probe`, `both`), `DCO_SPIN_CAP` (1, 2, `cpus / 2`), `DCO_SPIN_FLOOR` and `DCO_SPIN_NO_CPU_RULE`. Arms 0, fixed 1,024 and each mode, interleaved, median of 5: shared `Cache` and `FanoutCache(8)` at 32 connections, 1, 4 and 8 threads at `--cpus` 2, 3, 4 and 8, plus 16 and 32 threads at 8 CPUs, and the Mac at 4 and 36 threads; then htz (x86-64) for the chosen arm, with `DCO_SPIN_FLOOR` at 16, 32 and 64 (a `pause` is about 10 cycles before Skylake, about 140 after, and different again on Zen). **Phase change:** fresh-process arms never measure recovery, so one process runs 8 threads at 4 CPUs, then 4 threads; only the second phase is scored, against fixed. **Check:** confirm that the 8-thread `FanoutCache` runs actually reach 5b's slot wait, and note that `genlock.rs:57` has its own 3-CPU cutoff, so at 2 CPUs both spinners shut off together.
- **Bar (R3, sized to the noise).** The 4-thread clause, keep at least 90% of fixed's gain, applies only to cases where fixed gains 10% or more (at 3 CPUs that is `fanout8 c32 4t`, +28%; shared `Cache` there is +2%, inside the round spread). Single thread within ±3% of 0 only at 4 and 8 CPUs and on the Mac (at 2 CPUs the spread was 563-1,062). 8 threads at 3 and 4 CPUs no worse than -3% against 0, with the rounds overlapping; nothing below fixed at 8 CPUs and 32 threads; the phase-change second phase within noise of fixed. Ship the simplest arm that clears it (cap, then decay, then decay+probe, then both). If the chosen arm also matches 0 at 2 CPUs under `DCO_SPIN_NO_CPU_RULE`, `MIN_SPIN_CPUS` goes, one rule fewer. If no arm clears the bar, keep fixed and report the loss to Michael.
- **Risks.** A low cap may cost the 4-thread gain through futex wakes (hence `cpus / 2`). The extra RMW on the contended line costs something at 4 threads; the fixed arm in the same sweep shows how much. The constants are tuned on arm64, hence the htz floor sweep. No env knob ships.

**5b, the slot wait (`genlock.rs:284`).** No condvar or OS lock: the slot wait runs outside the gate, so a fork can land mid-wait, and the module's contract (`genlock.rs:1-9`) is that everything here is a generation-packed atomic a child reads as free. A futex-style wait on the word would keep that, but it needs `futex`/`os_sync_wait_on_address` per OS plus a shuttle stand-in, for a gain the prototype says is small; revisit only if the measurement leaves a gap.

**The permit is only ever taken attached (R3).** Today `try_acquire` runs attached and the detached closure only sleeps (`genlock.rs:284-292`). A permit taken inside `run_blocking` would be held while the thread re-attaches: up to the holder's 5 ms switch interval on a GIL build, a stop-the-world on 3.14t. The blocker is also `&(dyn Fn() + Sync)` returning `()` (`gate.rs:102`), so it can't hand a permit back. So the new `acquire_until` is test-and-test-and-set: `try_acquire`; on failure check the deadline; then one `gate::run_blocking` call (one detach per wait, not per poll) whose closure waits on a plain load, `in_use() < cap`, with `SLOT_SPIN` `spin_loop` hints, then `SLOT_YIELDS` rounds of `thread::yield_now()`, then the existing 50 µs sleeps until the load shows room or the deadline passes, and returns; then `try_acquire` attached again, and loop. Sleeps shorter than 50 µs don't help on Linux (the default 50 µs timer slack).

**As built (5b): no yields, and a spinner limit.** The sweeps (`bench/results/slot-wait-2026-11-05.md`) changed two things. `SLOT_YIELDS` is gone: in the Linux VM, yields were what oversubscription punished (64 per waiter took plain `Cache` at 32 threads on 8 CPUs from 1,691k to 728k gets/s), and with them at 0 the 8-CPU VM matched 4 yields on every row, the 2-CPU VM was within noise, and the Mac gave up 4% on FanoutCache at 4 threads for 8% on plain `Cache` at 36. So the wait is spin, then the 50 µs sleeps. `SLOT_SPIN` is 1,024 hints, gaps doubling to 64, and 0 at 2 or fewer CPUs (the SQLite mutex's rule, `slot_spin_for`); with the spin at 0 a waiter takes no spinner count and goes straight to the sleeps. The second change is a **process-wide spinner limit**: a waiter spins only if it can take one of `slot_spinners()` counts, `available_parallelism() / 2`, at least 1, and 4 when the count is unknown (`slot_spinners_for`); otherwise it goes straight to the sleeps. Without it, long spins cost up to 65% when oversubscribed in the VM (4,096 hints: plain `Cache` at 32 threads 1,691k to 594k). Swept at 2, 4 and half the CPUs (Mac at 36 threads, VM at 32): within noise of each other once yields were gone, so `cpus / 2` stays.

- **Fork safety.** The count (`SPINNERS`, a static `AtomicU64`) is generation-packed like the module's other counts, and the `Spinner` guard records its generation. `GENERATION` is bumped only in the child, and the parent threads that were mid-spin don't exist there, so the child reads the inherited count as 0. A guard's drop goes through `release_one`, which decrements only a word of its own generation and saturates at 0, so a stale guard can't take a count off a newer generation. If the after-fork hook were skipped (no bump), the leftover counts would only make the child's waiters skip the spin and sleep, never hang: `admit` is a try, never a wait.
- **Not modelled.** Under `cfg(shuttle)` every waiter is admitted. `admit` is try-only, so a lost or leaked count can only degrade a wait to the sleep-only path that models 1-3 (and the gate's composition models) already cover; and a process-wide static would be shared between models running in parallel, making schedules nondeterministic. The guard's give-back is unit-tested.

**Fairness.** Barging is no worse than today's poll, but spinners now beat a sleeper more often, so the done-when gains a tail check: no `Timeout` and a recorded p99.9 slot wait in a 60 s, 16-thread `FanoutCache(8)` default-budget run. Add a `starving` guard like `WriteLock`'s only if that fails.

**Shuttle.** Add `yield_now` to `sync::thread`, set `SLOT_SPIN` and `SLOT_YIELDS` to 2 under `cfg(shuttle)`, keep model 3 (`genlock/model.rs:143`), and add two models. In one, a holder releases while a waiter is mid-spin and a third thread barges: the cap is never exceeded, a far-deadline waiter gets in once the bargers stop (shuttle checks bounded schedules, so it can't prove liveness beyond that), and the count returns to 0. In the other, a deadline passes during the spin phase: it returns `None` and nothing leaks. `gate/model.rs:334` and `:541` must stay green.

## Step 6: FanoutCache (roadmap Phase 6c)

**Why:** the only change that removes SQLite's per-file shared-memory mutex (plan 11, section 2: 3.4M vs 1.5M reads/s on Linux with four threads).

**What:** the roadmap's confirmed decisions, plus the points where diskcache's real FanoutCache differs. Each difference gets a divergence entry:

- **`transact()` within one shard** (Michael's decision): a shard-scoped `transact(key)`. diskcache's `FanoutCache.transact()` locks every shard in order (`diskcache/fanout.py:70-100`), and oxide's rule that a second hold never waits makes that impossible on `begin_hold`.
- **Failures follow the handle's `durable` setting.** diskcache's FanoutCache catches `Timeout` and returns False or the default (`fanout.py:125,158`); oxide's `durable=True` already gives that, with logging, and `durable=False` raises.
- **`size_limit` is divided by the shard count**, as diskcache does (`fanout.py:38`), with per-shard culling.
- **The shard is chosen by a fixed-seed hash of `(key_type, key bytes)`**, frozen in the format, so the non-`str` keys planned for 6a need no new format.
- **The shard count is persisted safely.** Two processes creating the directory at once must agree (temporary file plus rename, or `O_EXCL`, plus the format version stamp). An opener that passes a different `shards=` gets a `ValueError`; `shards=None` reads whatever is stored.
- **The connection budget is per shard,** summing to the handle's cap, rather than one shared slot counter, which would bring back the shared atomic sharding removes.
- **Fanned out:** `len`, `clear`, `volume` and `expire`, with a `clear` or `expire` that fails partway reporting which shards finished. `__iter__` goes shard by shard, with a divergence entry. Sorted `iterkeys` is a k-way merge that holds no connection between yields.
- **`Caches` can register one.**

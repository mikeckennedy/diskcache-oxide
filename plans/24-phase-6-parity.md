# Plan 24: Phase 6, parity with diskcache where it fits the vision

Written 2026-11-10, on the branch `phase-6-parity` (cut from `plan-23-deferred-tests`, PR #2, so the two don't conflict in the core's test modules). Built from the parity inventory of diskcache 5.6.3 against oxide 0.1.2 (`abb66fd`) and Michael's interview the same day. Four releases, in this order (Michael), each committed on the branch when it's done, each green on 3.14 and 3.14t, and each reviewed by the architect: the plan before work starts, and each release when it ends. Conformance tests are written and green against diskcache 5.6.3 before oxide's implementation (roadmap, Phase 6).

## Decisions (Michael, 2026-11-10)

1. **Key types:** `str`, `bytes`, `int` (64-bit), `float`, `bool`, `None`, and tuples of those, nested. Our own canonical encoding, never pickled. Any other type raises `TypeError`, as today.
2. **Key equality is type-exact:** `1`, `1.0` and `True` are three keys. A divergence that narrows D-004 (diskcache: `1` and `1.0` are one key, `True` another).
3. **Keys and `memoize` ship as 0.2.0, with no cache deletion.** The schema and `FORMAT_VERSION` don't change, and 0.1.2 never matches rows of a key type it doesn't know, so mixed versions during a deploy are safe. The changelog says first that no cache needs deleting.
4. **One format bump for all of Phase 6, after the format-free work** (release 3). Its schema is designed before release 1 ships, so the key encoding and the tag column are designed together.
5. **Tags and `evict(tag)` are in, always indexed** (a partial index). No `tag_index` setting; `create_tag_index`/`drop_tag_index` are absent.
6. **Eviction:** `eviction_policy` gains `'none'` beside least-recently-stored. LRU and LFU are out: in diskcache's design every `get` becomes a write, and write-free reads are load-bearing (roadmap). The reasons are written in the divergences and on the roadmap page, which retracts "eviction policies are coming". They come back only with a design that keeps reads write-free.
7. **Statistics are per process:** `stats(enable=True, reset=False)` with diskcache's signature, counted in memory, not persisted and not shared across processes. They reset when the process restarts; expiry and eviction never read them. A divergence.
8. **`retry=` on every call that takes it in diskcache**, looping on a plain `Timeout` as `transact(retry=True)` does (D-030). `cache[k]`, `cache[k] = v` and `del cache[k]` keep raising `Timeout` after `timeout`, where diskcache retries forever: a D-entry, as D-034 already says for FanoutCache.
9. **Queue calls in, collections later:** `push`, `pull`, `peek`, `peekitem` in release 4. `Deque` and `Index` deferred until someone asks, with the reasons on the roadmap page.
10. **Coordination recipes raise on a `NullCache` or a `durable=True` handle.** A lock that silently doesn't lock is worse than an error.
11. **`disk=`, `Disk` subclasses and `JSONDisk` are out for good.** The README and `index.qmd` move them from "not here yet" to the divergences.
12. **Django: an oxide backend of its own, as its own phase right after Phase 6** ("it's going to be a big job"). diskcache's `DjangoCache` stays out; the roadmap's non-goal is reworded so it and the vision agree.
13. **Windows after Phase 6**, as its own plan.
14. **`read=True` and `read()` fold into the vision's large-file cache**, and the roadmap page says so.
15. **`memoize`:** diskcache's key shape exactly (`(name-or-qualname,) + args + (None,) + sorted kwargs flat`), so `__cache_key__` returns the same tuple diskcache would. `typed=True` appends each type's `'module.qualname'` string where diskcache appends the class (a divergence: we can't store a class without pickle). An argument that isn't a key type raises `TypeError` naming it, after nothing has run. `async def` functions are refused at decoration with a `TypeError` until `AsyncCache` is decided.

## Release 1 (0.2.0): keys, `memoize`, `retry=`

### The key encoding

- **`str` keys are unchanged:** `key_type = 1`, the UTF-8 text in the TEXT column, as every existing row is. Nothing about a `str` key's storage, lookup, shard or order changes, so existing caches keep working and 0.1.2 and 0.2.0 agree on every `str` key. The storage class is part of a key's identity (TEXT `'a'` and BLOB `b'a'` under one `key_type` are two rows), so a `str` key is always bound as TEXT.
- **Every other key is one new `key_type = 2` ("typed"), stored as a BLOB** (the `key` column has TEXT affinity, under which a bound integer would become text; a BLOB keeps its bytes, compares by `memcmp`, and uses the `cache_key` index: checked with `EXPLAIN QUERY PLAN`). The bytes are an order-preserving tuple-layer encoding in the style of FoundationDB's: a type code byte, then the value. No type code is `0x00` (the terminator only) or `0xFF` (the escape marker only), with gaps left for later types:

  | Code | Element | Value bytes |
  |---|---|---|
  | `0x00` | terminator (never a type) | |
  | `0x10` | `None` | none |
  | `0x20`, `0x21` | `False`, `True` | none |
  | `0x2F` | reserved: ints below `i64::MIN` | |
  | `0x30` | `int` (i64) | 8 bytes big-endian, sign bit flipped |
  | `0x31` | reserved: ints above `i64::MAX` | |
  | `0x40` | `float` | 8 bytes IEEE 754, total-order transform (negative: flip all bits; else flip the sign bit); `-0.0` stored as `0.0`; NaN refused |
  | `0x50` | `bytes` | the bytes, each `0x00` as `0x00 0xFF`, then `0x00` |
  | `0x60` | `str`, inside a tuple only | UTF-8, escaped and terminated as `bytes` |
  | `0x70` | tuple | its elements, then `0x00` |
  | `0xFF` | reserved | |

  - A lone non-`str` key is its one element (`b'x'` is `50 78 00`); a tuple key is `70 …`. A top-level `0x60` is never written (that would be a second identity for a `str` key).
  - **Sound by construction:** every element is self-delimiting (fixed width, or ends at a `0x00` not followed by `0xFF`), and a tuple ends at a `0x00` where an element would start, which no element does. So the encoding is injective and decodes one way. Order: the terminator is below every type code (a tuple sorts before a longer tuple it is a prefix of) and every code is below `0xFF` (`(b'a', None)` sorts before `(b'a\x00',)`). Across types the order is `None` < `bool` < `int` < `float` < `bytes` < `str` < tuple; within a type, value order, element by element for tuples. Ints past 64 bits can later take `0x2F`/`0x31` and sort numerically around the i64 range.
  - **Nesting limit 32**, refused at encode time (raising a limit later is compatible; adding one later isn't).
- **The format lives in the core** (`crates/diskcache-oxide-core/src/key.rs`), not the extension: release 4's `push`/`pull` encode int keys inside the write transaction, a trusted type stops a second identity for `'a'`, and a server could read keys without Python. A `TypedKey(Box<[u8]>)` has two constructors only: an `Encoder` (`none`, `bool`, `int`, `float`, `bytes`, `str`, `begin_tuple`/`end_tuple`; `finish` refuses an empty buffer, a top-level `str` and an unclosed tuple) and a strict `TypedKey::parse(&[u8])`. The extension walks the Python object and calls the encoder; golden vectors and property tests live in Rust beside `fanout.rs`'s frozen-format tests.
- **The decoder is strict and safe on hostile bytes** (a file another process or a damaged page wrote): depth-bounded, never panics, and accepts `b` only if `encode(decode(b)) == b`, so it rejects `-0.0`, NaN, unknown codes, trailing bytes, `0x00` followed by anything but `0xFF` inside data, and a top-level `str`. Iterating over a malformed typed row raises a named error (`CorruptValueError`'s sibling for keys) rather than skipping it.
- **Equality rules (D-004 rewritten, D-044):** exact types throughout (`cast_exact`; `bool` checked before `int`). Refused with `TypeError`: `IntEnum`/`StrEnum` and other subclasses, `bytearray`, `memoryview`, `namedtuple` and other tuple subclasses, `list`, and ints past 64 bits (one exception type, `TypeError`, pinned by a test; accepting more later is compatible, narrowing isn't). `-0.0` is `0.0`, as in Python `==`, diskcache's lone floats and `functools.lru_cache` (so a memoized sign-sensitive function gets `f(0.0)`'s result for `-0.0`). NaN raises `ValueError` (the type is right, the value isn't; diskcache binds a lone NaN as NULL and never finds it), including as a memoized argument: its own D-entry. No Unicode normalization: keys compare by code points, as in Python, diskcache and every stored 0.1.2 key. A lone surrogate raises `UnicodeEncodeError`, inside tuples too.

### Engine (core)

- `#[derive(Clone, Copy)] pub enum Key<'a> { Str(&'a str), Typed(&'a TypedKey) }` with `ToSql` (TEXT or BLOB), `key_type()`, `shard_bytes()`, and `From<&'a str>` so existing tests barely change. The 23 `key: &str` parameters in the core take `Key`.
- `#[derive(PartialEq, Eq, PartialOrd, Ord)] pub enum OwnedKey { Str(String), Typed(TypedKey) }` with `as_key()`: its derived order equals SQLite's `(key_type, key)` order, so FanoutCache's k-way merge uses it directly. `Cursor::Key(OwnedKey)`.
- **Iteration:** key-order paging runs `key_type = 1` then `2` (reversed for `reverse=True`), each a covering-index range scan. Insertion order drops the `key_type` filter and reads each row's key by its `key_type` (a BLOB can't be read as `String`). `iterkeys()` order is therefore every `str` key first, then the typed keys in encoding order: a divergence from diskcache (numbers, text, BLOBs by SQLite's comparison). `prefix=` stays `str`-only and a non-`str` prefix raises `TypeError`.
- The shard hash already takes the type byte (`shard_hash(key_type, bytes)`): typed keys hash `(2, encoded bytes)`, `str` keys are unchanged, and `HASH_IDENTITY` and the manifest don't change.
- **0.1.2 beside 0.2.0** (verified in the code at `8f98065`): every keyed statement binds `key_type = 1` and both iteration orders filter on it, so 0.1.2 never sees typed rows in keyed calls or iteration, while `expire`, `cull`, `clear` and `totals` work by id, `store_seq` or `expire_time` and keep counting and removing them. So during a mixed deploy 0.1.2's `len()` counts rows its iteration doesn't show: said in the changelog.

### Binding and Python

- `EncodedKey<'py>`: a borrowed `&str` for `str` keys (zero-copy, as today; `bench.gate` must show no regression) or an owned `TypedKey`. One conversion for every keyed method, `transact(key=)`, `shard_of`, and `on_decode_error`'s callback, whose key argument becomes the decoded key.
- Decoding a typed key back to Python for iteration gives exact types back.
- Stubs: `type Key = str | bytes | int | float | bool | None | tuple[Key, ...]` (PEP 695; confirm `ty` resolves the recursive alias) for every key parameter, and `Iterator[Key]` for iteration (a changelog line: type-checked callers that call `str` methods on iterated keys now need a narrowing). `NullCache._check_key` takes the same set. A private `_core._encode_key` lets Hypothesis reach the encoder.

### `memoize`

- `Cache.memoize`, `FanoutCache.memoize` and `NullCache.memoize`, with diskcache's signature `memoize(name=None, typed=False, expire=None, tag=None, ignore=())`; `tag=` arrives in release 3 (until then it isn't in the signature). The logic is pure Python (`python/diskcache_oxide/_memoize.py`); the compiled methods import it lazily and delegate (an immutable pyclass can't gain a method, and a subclass would change type identity).
- The base name is `func.__module__ + '.' + func.__qualname__`, as diskcache's `full_name`. `@cache.memoize` without parentheses raises `TypeError('name cannot be callable')`. `expire=0` or negative never stores; `None` results are cached (a private sentinel marks a miss); an exception stores nothing. Reads and writes pass `retry=True`, as diskcache's do. `wrapper.__cache_key__(*args, **kwargs)` returns the key tuple. Typed in the stubs with a `ParamSpec` and a `Memoized[P, R]` protocol carrying `__cache_key__`.
- On a `NullCache` the function runs every time, but the arguments are still checked as keys, so swapping in a `NullCache` doesn't hide a `TypeError`. Under `durable=True` an outage runs the function and drops the store (D-028).

### `retry=`

- Keyword-only `retry=False` (diskcache allows it positionally: a D-entry beside `expire_time`'s) on `set`, `add`, `get`, `pop`, `delete`, `touch`, `incr`, `decr`, `expire`, `cull`, `clear` (later `evict`, `push`, `pull`, `peek`, `peekitem`), on `Cache`, `FanoutCache`, `NullCache` and the protocols.
- One helper in the binding, `retrying(py, retry, || …)`, used by every call and by `Transaction::begin`, whose loop moves onto it (today it doesn't sleep, so at `timeout=0` it spins). Only a plain `Timeout` is retried, with the call's own `timeout` each round; not `TransactionBusy`, a poisoned child's `RuntimeError`, or decode errors. Each round leaves the fork gate and its connection slot before sleeping (a pending fork is never starved; a fork test pins it), sleeps only when a round failed quickly (`max(0, 1 ms − elapsed)`) with the interpreter released, and checks for signals, so Ctrl-C ends it.
- **Under `durable=True`, `retry=True` wins for a `Timeout`:** it is retried; any other outage is still a miss or a dropped write, as D-028 says. Written down and tested.
- A fanned-out `clear`, `cull` or `expire` that is retried resumes where it stopped (D-035's progress) and returns the total, not the last round's count.

### Release 3's schema, decided now

Format 3 keeps `key_type INTEGER, key TEXT` and the `cache_key` index exactly as they are. Tags mirror keys: `tag_type INTEGER, tag TEXT` with a partial index on `(tag_type, tag) WHERE tag IS NOT NULL`, through the same `Key` and encoder, so a `str` tag is TEXT and other tags are typed BLOBs, covering diskcache's tag types (str, bytes, int, float) with no second encoding. (Format 3 deletes caches, so an encoding mistake found before 0.4.0 could still be fixed there; nothing is planned around that.)

## Release 2 (0.3.0): small parity and the recipes, no format change

Designed 2026-11-10, after release 1, from diskcache 5.6.3's `core.py` and `recipes.py`, then revised after the architect's review the same day. Conformance tests first, as in release 1, behind feature flags (`statistics`, `check` and `recipes` exist in `backends.py`).

### Decisions (Michael, 2026-11-10, release 2)

16. **`throttle`'s two diskcache bugs are fixed, as a divergence** (and logged in `upstream/README.md` with repros): a missing bucket (after an idle gap longer than `expire`, a `clear()` or a cull) is a full bucket instead of a `TypeError`, and decoration `add`s the bucket instead of `set`ting it, so every worker that imports the module doesn't refill it.
17. **`memoize_stampede` follows `memoize`'s rules**, not the locks': it works on a `NullCache` (runs every call) and a durable handle (runs the function on an outage). Only the coordination recipes (`Lock`, `RLock`, `BoundedSemaphore`, `throttle`, `barrier`, `Averager`) refuse those handles.
18. **`RLock`'s owner gains a per-process nonce:** `'{pid}-{tid}-{nonce}'`, the nonce made at import and remade in a forked child, so two containers' pid 7 on one volume, or a reused pid, never share a lock.
19. **A forked child's statistics start at zero**, reset by the after-fork child hook, so summing workers never double-counts.
20. **`check()` doesn't report empty value folders** (they're normal on a healthy open cache, D-042); `check(fix=True)` sweeps them as the close-time sweep does. A divergence.
21. **`reset(..., update=False)` raises `ValueError`:** for `size_limit` and `cull_limit` there's no pragma to skip, so it would silently do nothing.

### Small parity, on `Cache`, `FanoutCache` and `NullCache` and the protocols

- **`reversed(cache)`:** insertion order, newest first; a FanoutCache walks shards last to first, each newest first, as diskcache chains them, and refuses inside a `transact(key=)` (D-040's list). Core: `Order::InsertedReverse` (beside `Order::Inserted`), an `id DESC` page with an `id < ?` cursor (`Cursor::Start` maps to `i64::MAX`), filtered to `key_type IN (1, 2)`. In the stateful model test.
- **`pop(key, default=None, *, expire_time=False, retry=False)`:** with `expire_time=True`, `(value, expire_time)`, or `(default, None)` on a miss. `Cache.pop` already has it from `Hit`; the locked fallback's `Popped` gains the column.
- **Pickling `Cache` and `FanoutCache`:** `__reduce__` to a module-level rebuild function taking a kwargs dict (so pickles survive options added later), carrying the absolute directory, the handle's own options (`timeout`, `serializer`, `pickle`, `durable`, `on_decode_error`, `clock`, `max_connections`, `sqlite_cache_size`, `wal_size_limit`, `wal_checkpoint`) and a FanoutCache's actual shard count. Persisted settings aren't carried. An unpicklable `clock` or `on_decode_error` raises when pickled. `TypeRegistry` gains `__reduce__` rebuilt from `registered()`; the global `diskcache_oxide.registry` reduces by name and is never copied (documented: a spawn child must import what registers its types). `copy.copy` opens a second handle.
- **`reset(key, value=ENOVAL, update=True)`** for `size_limit` and `cull_limit`: with a value, validated as the constructor does (D-005) and persisted, returned; without, read from the database (not the cached limits, which it refreshes). `update=False` raises (decision 21). Other keys raise `ValueError` saying why: `sqlite_*` (D-023), `eviction_policy` (release 3), `statistics` (use `stats()`). A FanoutCache splits `size_limit` across shards as its constructor does (`split_size_limit`), returns the total, and reports a partial failure as D-035 does (diskcache sets every shard to the full value, multiplying the budget: a bug against its own constructor).
- **`durable`**, a read-only attribute: True on a durable `Cache` or `FanoutCache`, else False, and False on a `NullCache`.
- **`stats(enable=True, reset=False) -> (hits, misses)`**, per process (decision 7): kept in a process-wide map keyed by the database's file identity (the `file_id` poisoning uses), so a cache opened per use, or a FanoutCache whose shards were closed, keeps its counts and its enable flag. Two relaxed atomics on their own cache line, counted only while enabled (one relaxed load otherwise), from the binding's `get` and `cache[k]` through `Store::record_lookup(hit)`, never inside `get_with` (which `pop` uses). A miss: missing, expired, a missing or short value file, an `on_decode_error='miss'` answer. Not counted: a refused mode (it raises), a durable outage answered as a miss, `in`, `pop`, iteration. Returns the counts as they were, then resets them (`swap(0)`), then sets `enable`, as diskcache does. A FanoutCache sums its shards and enables them all. A forked child starts at zero (decision 19). `NullCache.stats()` is `(0, 0)`. diskcache's `statistics=` constructor setting is refused with a message pointing at `stats()`. D-entry: not persisted, not shared across processes, reset at restart.
- **`check(fix=False, retry=False) -> list[warnings.WarningMessage]`**, chunked and mostly lock-free in the style of `clear()` (D-011), never holding the write lock or a gate level across a scan, so writers and forks aren't stalled:
  1. *Rows against files:* page through `SELECT id, store_seq, filename, size ... WHERE filename IS NOT NULL` by `id` (the `cache_filename` partial index), one short read per page; stat each file with no gate held. A missing file, a short or long file (`wrong file size: ...`), or a `filename` that isn't one spill writes (D-042; never turned into a path) is reported, and with `fix` removed through `delete_version` (D-013's compare-and-delete, which does nothing if the row changed meanwhile and keeps `totals` right). Never "corrected": a wrong size is a file a crash cut short, which the read path already treats as missing.
  2. *Files against rows:* list the value directories with no gate held; each `.val` is looked up (`SELECT 1 ... WHERE filename = ?`, indexed, chunked). An unreferenced `.val` or a `.tmp` is reported (`UnknownFileWarning`) and removed with `fix` only if older than `spill::TMP_MIN_AGE` (1 h, by mtime): a younger one may be a live writer's (a busy COMMIT leaves a renamed `.val` with no row between attempts; a writer waits on the lock with its `.tmp`), so it's neither reported nor removed. Unknown files in the store directory itself are reported too, but the `diskcache-oxide.sqlite*` prefix (database, `-wal`, `-shm`, a hot `-journal`), the pin and the manifest are never reported or touched, and only files inside the value directories are ever removed: regular files or links, never directories, never following a link.
  3. *Empty value folders:* not reported (decision 20); with `fix`, `spill::sweep`.
  4. *Totals:* `COUNT(*)` and `SUM(size)` against `totals` in one read snapshot (`Settings.count != COUNT(Cache.key); ...` and the `size` line, diskcache's texts); only on a mismatch, recomputed and fixed in one short `BEGIN IMMEDIATE`.
  5. *`PRAGMA integrity_check`*, and with `fix` *`VACUUM`* then a forced TRUNCATE checkpoint: the only long single steps, run through the store's write-lock path (same-process writers queue within their timeouts), never inside a held transaction (refused there). Documented: forks and writers wait for them; VACUUM writes the whole database through the WAL and needs a full temporary copy in `SQLITE_TMPDIR`/`/tmp`. Row ids survive (an `INTEGER PRIMARY KEY`).
  The core does the work (`Store::check(fix, deadline) -> Vec<Finding>`, each `Integrity`, `MissingFile`, `WrongSize`, `BadFilename`, `UnknownFile`, `Count` or `Size`, with `fixed`). The binding builds `warnings.WarningMessage` objects directly (no `catch_warnings`, which swaps global state and obeys `-W error`), with diskcache's message prefixes. `retry=True` keeps findings across rounds, de-duplicated. `durable` doesn't swallow its errors. A FanoutCache checks every shard. `UnknownFileWarning` exported (`EmptyDirWarning` too, for code that imports it, though `check()` never issues it).
- **`ENOVAL` and `UNKNOWN`**, exported: non-tuple singletons pickled by reference (diskcache's are `tuple` subclasses, which would round-trip as plain tuples). msgpack and JSON refuse them as values; with `pickle=True` they round-trip as themselves, which is harmless (decided after the release review: nothing in oxide uses `ENOVAL` as a stored-value sentinel).

### The recipes (`python/diskcache_oxide/recipes.py`), pure Python, re-exported from `diskcache_oxide`

`Averager`, `Lock`, `RLock`, `BoundedSemaphore`, `throttle`, `barrier` and `memoize_stampede`, with diskcache's signatures minus `tag=` (until release 3) and its behavior, and these differences:

- **The coordination recipes refuse a `NullCache` or a durable handle** (decision 10) with a `TypeError` at construction or decoration. On a durable handle a failed `delete` in `Lock.release` would be dropped and the lock held forever. `memoize_stampede` doesn't refuse (decision 17).
- **Inside a held transaction**, a recipe that would wait (polling inside the transaction holds the write lock, so no other process could ever release: diskcache's deadlock) raises `RuntimeError` naming the cache, through a private "held by this thread" predicate. On another cache, D-030 makes a contended recipe transaction raise `TransactionBusy` at once: documented.
- **On a FanoutCache**, each recipe's transaction is `transact(key=its key)` (D-040).
- **Transactions retry** (`transact(retry=True)`) and single calls pass `retry=True`, as diskcache's do. `Lock` and `BoundedSemaphore` poll every 1 ms.
- **`RLock`'s owner** has the nonce (decision 18); a forked child can neither re-enter nor release its parent's lock (tested). Its and `BoundedSemaphore`'s `assert`s become explicit `raise AssertionError(...)`, so `python -O` doesn't strip them.
- **`throttle`** with decision 16's fixes.
- **`barrier`** passes `tag=` to the lock factory only when given, so factories written for diskcache work.
- **`memoize_stampede`** stores `(result, seconds)` pairs as diskcache's; its recompute claim is `('diskcache_oxide.recompute',) + key`; the recompute thread doesn't `with cache:` (that closes our handle, D-018); `-log(1.0 - random())`, so a 0.0 from `random()` can't raise; arguments follow `memoize`'s rules (D-048).
- **Coordination keys can be culled** (least-recently-stored culls the oldest first, and a long-held lock is old) and `clear()` releases them, as in diskcache: the coordination guide page says to use a dedicated cache, and `eviction_policy='none'` once release 3 has it.
- Not in this release, and said on the roadmap page: `FanoutCache.cache()`, `deque()` and `index()` (deferred with `Deque` and `Index`).

## Release 3 (0.4.0): format 3, tags and `eviction_policy='none'`

Designed 2026-11-10, after release 2.

### Decision (Michael, 2026-11-10, release 3)

22. **Format 3 is a version bump, and caches are deleted on upgrade** (decision 4's "one bump", confirmed when the alternative was put to him: adding the columns in place, which would let old workers drop tags and ignore `eviction_policy='none'` during a deploy). A format-2 cache is refused with `FormatMismatchError`, which names the file and says to delete the cache with every worker stopped.

### Schema (format 3), frozen in step 2 in full

- `cache` gains `tag_type INTEGER NOT NULL` (0 untagged, 1 a `str` tag, 2 a typed tag) and `tag TEXT` (NULL exactly when untagged: `CHECK ((tag_type = 0) = (tag IS NULL))`). A tag is any key type (D-004), stored as a key is, through the same `Key` and encoder; `typeof(tag)` is `text` or `blob` (tested, as for keys). `NOT NULL` is deliberate (architect, M1): a 0.1.x-0.3.x worker that outlives the cache's deletion opens its next pooled connection by path on the new format-3 file, and its untagged `INSERT ... ON CONFLICT` then fails with `NOT NULL constraint failed: cache.tag_type` instead of silently writing rows that ignore format 3's rules (verified); the reverse, 0.4.0 on a recreated format-2 file, fails with "no column named tag_type".
- Index `cache_tag ON cache (tag_type, tag, store_seq) WHERE tag IS NOT NULL`: untagged rows cost nothing, and `evict`'s chunk statement `DELETE FROM cache WHERE id IN (SELECT id FROM cache WHERE tag IS NOT NULL AND tag_type = ?1 AND tag = ?2 AND store_seq < ?3 ORDER BY store_seq LIMIT ?4) RETURNING size, filename` is `SEARCH ... USING COVERING INDEX cache_tag (tag_type=? AND tag=? AND store_seq<?)` with no sort (architect, H1: on `(tag_type, tag)` alone every chunk sorted every row with the tag, quadratic). Pinned by an `EXPLAIN QUERY PLAN` test and a VM-steps test beside `KEY_PAGE_SHAPES`. `tag IS NOT NULL` is always written out (the QPSG rule in `open.rs`).
- `totals` gains `eviction_policy INTEGER NOT NULL CHECK (eviction_policy IN (1, 2))`, 1 least-recently-stored, 2 none, with no DEFAULT (architect, H3: 0 must never quietly mean "never evict"). In Rust an `EvictionPolicy` enum with `TryFrom<i64>`; an unknown stored value is an error at open, never read as least-recently-stored.
- `FORMAT_VERSION` 3. The manifest is unchanged (`MANIFEST_FORMAT` stays 1: the format is per shard). `schema.rs`'s doc loses "a new filename" as an option for database-only changes: since release 2, `check(fix=True)` removes value files its own database doesn't name, so two versions' databases can't share a directory's value files; one more reason decision 22 is a bump.
- `FormatMismatchError` names the directory and, by direction: an older format "was made by an older diskcache-oxide: delete <dir> with every process using it stopped"; a newer one "was made by a newer diskcache-oxide: upgrade this process". A FanoutCache names the root and says to delete the whole root (one shard deleted alone is recreated beside format-2 siblings). Never "delete the .sqlite" (its value files would be orphaned).
- `totals` is renamed `state` (Michael, 2026-11-11, after the architect's release review found that `NOT NULL` stops only an older worker's inserts: a surviving 0.1.2 handle's delete, pop, incr, cull and expire still landed, and its `cull()` evicted a 'none' cache). Every 0.1.2 call that writes or maintains reads or updates `totals`, so each now fails with "no such table"; only its `touch` and reads reach a format-3 file.
- Later, not here: a pooled connection checking the file's identity when it opens (architect M1's fix 2).

### API

- **Tags:** keyword-only `tag=None` on `set` and `add`; keyword-only `tag=False` on `get` and `pop`, returning `(value, tag)`, or with `expire_time=True` too `(value, expire_time, tag)` (diskcache's order); `(default, None)` and `(default, None, None)` on a miss. Compared by exact type (D-044's rule extended: diskcache compares tags numerically, so its `evict(1)` removes `1`, `1.0` and `True`, a `True` tag reads back as `1`, a NaN tag is stored as none, and a tuple raises), a D-entry with `diverges` tests. `incr`'s in-place update, `touch`, and `add` on a live key keep the tag; `incr` of a missing or expired key stores none (diskcache's insert); `cache[k] = v` stores none. `memoize(tag=)` (checked at decoration) and the recipes' `tag=` turn on. `NullCache` checks tags and returns no tag. `CacheLike` gains `evict` and `tag` (a changelog line).
- **`evict(tag, *, timeout=None, retry=False) -> int`:** every entry with that tag stored before the call, in chunks like `clear()` (D-011), returning the count; `evict(None)` is 0 and touches nothing (the core's `evict` takes a `Key`, never an `Option`, so no path can mean "untagged"); a FanoutCache fans out with D-035's reporting and `retry=True` resuming through `remove_on`; refused inside a `transact(key=)` (D-040's list) and, as `clear`, not run inside this thread's transaction.
- **`eviction_policy=None`** on `Cache` and `FanoutCache` (None: keep the stored one; a new cache gets least-recently-stored), `'least-recently-stored'` or `'none'`; `'least-recently-used'` and `'least-frequently-used'` raise `ValueError` saying why (decision 6); anything else `ValueError`. A read-only `eviction_policy` attribute; `reset('eviction_policy', ...)` reads and sets it (the return type becomes `int | str`: stub overloads); on a FanoutCache every shard, and the attribute is shard 0's. Reopening with an equal policy writes nothing (D-019).

The cached copy is for the attribute only (as `store.rs` says of the cached limits), so a handle opened before another process's `reset('eviction_policy', 'none')` never evicts afterwards.
- No `tag_index`, `create_tag_index` or `drop_tag_index` (decision 5).

## Release 4 (0.5.0): queue calls

Designed 2026-11-11, after release 3. `Deque` and `Index` stay deferred (decision 9). No format change.

### Decisions (Michael, 2026-11-11, release 4)

23. **`pull` decodes before it deletes, as `pop` does** (architect, H1): read and decode the head with no lock, then delete exactly that version; on losing it to another puller, read the new head; after `PULL_ATTEMPTS` (3) losses, the locked removal. An item this process can't decode (a newer deploy's registered type, a missing time zone, a failing hook) stays in the queue, keeping D-026's guarantee on the main path rather than only in a fallback.
25. **`pull` has no remove-then-decode fallback** (Michael, 2026-11-11, after the architect's release review, M1; supersedes decision 23's "after 3 losses, the locked removal"): under contention three lost races are routine, so the locked fallback would have removed, then failed to decode, exactly the foreign items decision 23 protects. `pull` keeps reading and decoding the new head until its deadline, pausing briefly (jittered, at most 2 ms) after 3 losses in a row; each loss is another puller's progress, and a puller that loses for its whole timeout raises `Timeout` having taken nothing. `Store::pull_locked` is gone.
24. **`push` never overwrites** (architect, H2): a number past either end of the range raises `OverflowError` ("the queue's key range is full"), and a computed key that is already stored is a hard error, not an upsert.

### What diskcache does (5.6.3, read from its source and reproduced by the architect)

- `push(value, prefix=None, side='back', expire=None, read=False, tag=None, retry=False)` returns the new key. In one transaction it finds the end of the range (`? < key AND key < ? AND raw = 1 ORDER BY key DESC|ASC LIMIT 1`, both bounds exclusive), takes that number plus or minus one, or 500,000,000,000,000 for an empty range, and inserts with a plain `INSERT`, then culls. With `prefix=None` the range is numeric, `0 < key < 999,999,999,999,999`, so a float or bool key in it counts: with `5.5` present `push()` returns `6.5`. With a prefix it is the strings between `'{prefix}-000000000000000'` and `'{prefix}-999999999999999'`: with an ordinary key `'user-9'` present, `push(x, prefix='user')` returns `'user-000000000000010'` and the next push raises `IntegrityError`, and `pull(prefix='q')` takes `'q-1-500000000000000'`, an item of queue `'q-1'`. Past an end, one push leaves the range (after `cache.set(1, ...)`, `push(side='front')` stores key `0`) and the next raises `IntegrityError`. A bad `side` raises `KeyError`.
- `pull(prefix=None, default=(None, None), side='front', expire_time=False, tag=False, retry=False)` returns `(key, value)`, or `((key, value), expire_time, tag)` and the pairs, as `get`'s tuples; a miss returns `default`, widened to match. In a write transaction it deletes the head, going round again past expired heads; it decodes after the delete, so a value it can't read is lost; a missing value file makes it try the next. An item is live at `expire_time == now` (`<` there; oxide's rule is `>` throughout, so conformance tests stay off exact equality).
- `peek(...)` is `pull` without the delete, but it takes the write lock and deletes expired heads it passes. `peekitem(last=True, expire_time=False, tag=False, retry=False)` is the newest or oldest row by `rowid`, any key, deleting expired ones it passes; empty raises `KeyError('dictionary is empty')`. Both spin forever when the head's value file is missing (the row is never deleted, so `continue` finds it again).
- `FanoutCache` has none of the four.

### Design

- **Core: `QueueRange`**, made only by the core: `Int` (typed `int` keys, exact type, `0 < n < 999_999_999_999_999`) or `Prefixed(prefix)` (`str` keys of exactly `{prefix}-` and 15 ASCII digits). Both are an index range on `cache_key (key_type, key)`: an int key is `0x30` and 8 bytes in order, so the range is a byte range under `key_type = 2` that no other type code can fall in (checked by the architect); a prefixed key is a text range under `key_type = 1`, and every key strictly inside it starts with `{prefix}-`, so with the exact shape `'q'` and `'q-1'` never cross. **The shape is checked in Rust** (architect, M1), not with SQL `length()`/`GLOB` (which stop at a NUL and count characters, not bytes): one statement per direction, `SELECT ... FROM cache WHERE key_type = ?1 AND key > ?2 AND key < ?3 ORDER BY key [DESC]` with no LIMIT, stepped lazily, taking the first row of exactly `prefix.len() + 16` bytes with an all-digit tail (ints: exactly 9 bytes; a malformed int row is skipped, never a `CorruptKey` that would wedge the queue). Rows to delete are collected and deleted after the statement is reset. Malformed keys in range cost a scan per call (`f'user-{id}'` keys beside a `'user'` queue): documented, with "use a prefix no other key starts with". `EXPLAIN QUERY PLAN` shapes beside `KEY_PAGE_SHAPES` (TEXT and BLOB, ASC and DESC: `SEARCH ... cache_key (key_type=? AND key>? AND key<?)`, no temp B-tree), and a VM-steps test that `push` costs the same with 10 or 100k items.
- **`Store::push(timeout, range, side, value, expire, tag, now) -> OwnedKey`**: spills before the lock as `set` does (the file's name doesn't depend on the number), then in one write transaction, with the number computed inside the `write_files` closure (it may run more than once): finds the end (expired rows count: they still hold their numbers), computes the next number or 500,000,000,000,000, raises `Error::QueueFull` (`OverflowError`) past either end (decision 24), and stores through `prelude`/`put_value`/`cull` with a hard error if `prelude`'s `stored` is `Some` for the computed key. Inside `transact()` it sees the transaction's own rows.
- **One head read for `peek`, `peekitem` and `pull`** (architect, M2): `look_up` generalizes to a locator, `ByKey(Key)`, `Head { range, side }` or `Inserted { last }`, returning `Found<T>` and the row's `OwnedKey`, so the version, the tag, the D-013 re-read and the D-016 fallback come from one statement and the existing machine; inline heads, nearly every queue item, never loop. `refuse` is passed, so a refused spilled file is never read. The head is the first *live* row (`expire_time IS NULL OR expire_time > now`); `peekitem` adds `key_type IN (1, 2)` as iteration does and walks `id` past expired rows (acceptable: `last=True` rarely meets them; documented). A spilled head whose file vanished is re-read by locator; the same version is a true miss, removed with `delete_version_nowait`, and the call goes on to the next item: it never spins (diskcache's hang). `peek`/`peekitem` never write otherwise (the project's rule), and none of the three counts in `stats()`.
- **`pull`** (decision 23; decision 25 later removed the locked fallback described here, so a lost delete now reads the head again with a short jittered backoff until the deadline) is the head read plus `delete_version`, through `pop_failed`/`decode_failed` as `pop_value` uses them. On a lost delete, read the new head; after `PULL_ATTEMPTS` losses, the locked removal, which deletes at most `CHUNK` expired heads per transaction (architect, M4) and commits and goes again under one deadline, and which **opens a spilled file under the lock and reads it after the commit** (M3, `Locked::Opened`'s pattern: no large read under the write lock, and a concurrent `check(fix=True)` can't remove the file first; a short read after the commit is a lost item, so go on; a Windows-plan note, since it relies on unlinking an open file). A refused head stays and raises as `pop` does (FIFO order and D-001: skipping it would reorder the queue). **A decode failure answered as a miss goes on to the next item**, never returns the default, so `while (item := cache.pull()) != (None, None)` workers don't stop early; a kept foreign head returns the default ("nothing I can take"). Inside a held transaction a rollback puts a pulled item back after the caller received it, as in diskcache (a doc line).
- **Binding, on `Cache` only**: `push(value, prefix=None, side='back', expire=None, *, tag=None, retry=False)` (no `read=`), `pull(prefix=None, default=(None, None), side='front', *, expire_time=False, tag=False, retry=False)`, `peek(...)` the same, `peekitem(last=True, *, expire_time=False, tag=False, retry=False)`, with diskcache's return shapes. `prefix` is a `str` (`TypeError` otherwise; `''` is valid and differs from None; NUL and Unicode work), `side` `'front'` or `'back'` (`ValueError`, a D-entry against diskcache's `KeyError`). Durable handles: a failed `push` returns None (typed by overloads: `prefix: None` → `int | None`, `prefix: str` → `str | None`), `pull`/`peek` a miss, `peekitem` `KeyError` (added to D-028). `NullCache`: `push` stores nothing and returns the first key, `pull`/`peek` the default, `peekitem` `KeyError`, all arguments validated as `Cache` does, and none forwarded to `invalidate=` (a switched-off cache must not consume a real queue). **Protocols** (M5): on `TransactionalCacheLike` (Cache and NullCache), not `CacheLike`, which FanoutCache must keep satisfying; a changelog line.
- **Eviction** (M6): under least-recently-stored the head is the oldest store, so a full cache evicts a queue's head, silently, as diskcache does. The recipe, the docs and the soak lane use `eviction_policy='none'`.
- **Key reuse** (L6): a pull from the front then a push to the front reuses the key, so "peek, then `delete(key)` as an ack" is racy, as in diskcache: documented in the recipe.

### Conformance, divergences, upstream and other tests

# Plan 28: background maintenance

Status: in progress on branch `plan-28-maintenance` (2026-11-13). The plan was reviewed once by the-rust-architect, whose findings are folded in below, and each step is reviewed by the architect on Fable before the next starts. Comes from [vision.md](vision.md#expiry-that-keeps-itself-accurate-michael-2026-10-28), with Michael's decisions (2026-11-13). It ships in 0.3.5 (Michael): 0.3.5 hasn't been released and needs the Full gate's 24-hour soak anyway, so one soak covers both.

## Where this starts

Expired entries are already invisible everywhere. Lookups always hid them, and since D-060 (0.3.5) `len()`, `iterkeys()`, `iter()` and `reversed()` do too, by the cache's clock. When a row is physically removed is now housekeeping only: disk space, `volume()`, `size_limit` and the WAL's size. Nothing a caller reads depends on it.

Today that housekeeping runs only when something else does: each write sweeps up to `cull_limit` expired rows and evicts if over the limit, the last close in a process checkpoints a large WAL and sweeps value folders, and everything else waits for the app to call `expire()`, `cull()` or `checkpoint()`. A mostly-read cache in a long-lived worker keeps its dead rows, its over-limit size, its large WAL and its stray temp files until then. The docs tell people to schedule `expire()` hourly.

This plan adds one background maintenance thread per process that does that housekeeping on a schedule, so nobody has to (Michael: a cache management activity, not just an expiry sweeper).

## Decisions

1. **One maintenance thread per process (Michael).** It serves every open store, each `Cache` and each `FanoutCache` shard. It's started with `std::thread::Builder` and named `diskcache-oxide-maintenance`. If the spawn fails (a container's pids limit gives `EAGAIN`), maintenance is off and that's counted in stats, never raised into the user's call. Each turn runs under `catch_unwind`, and a panic counts as a failure while the thread lives on.
2. **The thread never touches the interpreter.** The core's `gate::run_blocking` calls the installed Python blocker, which attaches to the interpreter on any thread not already marked detached. A turn reaches that path through value-file unlinks (8 or more in a chunk), checkpoints, the value-folder sweep and any gate wait. So the core gets a thread-local, set at thread start, that makes `run_blocking` run its closure directly. A core test installs a counting blocker and asserts a full turn never calls it, and a Python test shuts the interpreter down mid-turn.
3. **One setting, `maintenance_interval=` (Michael's naming direction).** It goes on `Cache`, `FanoutCache` and `Caches(...)`/`register(...)`, in seconds. The default is **300 s**, `0` turns maintenance off, and anything else must be at least 1 s, with `bool` rejected as D-014 does. Tests get a shorter interval through a hidden hook. The setting is per process and not stored in the database (Michael): it's how this process behaves, and a script or test can pass `0` for itself without turning maintenance off for the app. Two handles in one process share a `Store`, so the store uses the shortest interval any live handle asked for, as `max_connections` follows the largest.
4. **Why 300 s (Michael's question, the review's numbers).** When nothing needs doing, a turn per store is one no-wait read: the claim row, an `EXISTS` probe on the expiry index, the `state` row, two cached PRAGMAs and a `stat` of the WAL. That's about 10-20 µs, and it takes no write lock, writes nothing and doesn't move `data_version`. Talk Python's shape is about 29 stores per worker (5 caches plus 3 FanoutCaches of 8 shards), so this is about 0.5 ms per worker per interval. At 60 s that's about 0.007% of a core; at 300 s, about 0.0013%. A short interval wastes almost nothing, but it buys nothing either. The interval only sets how long dead rows, an over-limit size or a large WAL linger, and minutes is plenty for all three: the docs say hourly today. A longer interval doesn't mean more total work, since each row is deleted once whatever the interval. It means fewer, larger turns, which the budget caps (decision 9). Writes keep up on their own: each removes up to `cull_limit` (10) expired rows, so a cache still being written finds almost nothing for the sweep, and a backlog builds only on caches nobody writes to. At 300 s, an idle 50k-row cache with a 1-hour TTL has about 4,200 rows per turn (42 chunks, about 5.5 ms). If all 50k expire at once, that's two 50 ms turns. 300 s also keeps short scripts and recycled workers from running maintenance at all (decision 7).
5. **Tasks share one base tick, each with its own cadence.** A closed `enum Task`, dispatched statically, with each task due at `max(interval, its minimum)`. In turn order:

   | Task | Cadence | Shared across processes |
   |---|---|---|
   | Expire, then cull if over `size_limit` | the interval | yes, by the claim row |
   | WAL checkpoint, only past its trim size | the interval | no (one `stat` when it's small) |
   | Value folders and dead `.tmp` files | `max(interval, 1 h)`, matching `TMP_MIN_AGE` | yes, by its own claim row |
   | Idle connection trim | `max(interval, 5 min)` | no, in-process |

   Checkpointing follows expiry because the deletes just grew the WAL. Folders emptied in this turn are skipped by the folder sweep's 30 s `min_age` and go next hour.

   The turn also culls (Michael). Size eviction otherwise runs only on writes, at most `cull_limit` per write, and in explicit `cull()` calls. A burst of large values, or `reset('size_limit', smaller)`, can leave a mostly-read cache over its limit until enough writes come. So the turn checks the size, the same check `set` and `cull()` make (one shared `ops::Fill`), and evicts down to the limit only when the cache is over it, `cull_limit` rows at a time (at most 100), so a background trim never evicts more at once than the `set` it stands in for. It never evicts under `eviction_policy='none'`, and never when the stored `cull_limit` is 0, which in diskcache means "no automatic culling, the app culls itself" (Michael, 2026-11-13): expired rows still go.

   The value-folder sweep in the background covers what the close-time sweep can't: long-lived processes that never reach a last close, and FanoutCache shards, which don't sweep today (D-042). Running it in every process also makes D-042's rare APFS race between `rmdir` and a first write more likely, so the D-042 entry says so and the soak watches for it.

   Connection trimming closes connections idle for longer than its cadence. It always keeps one and never closes a transaction's pinned connection, and it does this under the gate, as `close_idle_all` does. It needs an idle-since stamp on each pooled connection. It goes last in the plan and ships only if `bench.memory` shows it's worth having.

   **Kept explicit, never in the background:** `PRAGMA optimize`, because ANALYZE writes `sqlite_stat1`, which makes every connection in every process re-prepare and can move query plans off the ones the plan tests pin. Also `check()` in any form, because `integrity_check` is O(database) and a long read keeps the WAL from truncating.
6. **The per-store state lives on `Store`.** The schedule (step 1's `Schedule`) sits in a `Mutex` that's locked only under a shared gate level, with the guard as proof, as the pool's mutex is, and checked free at fork beside `pool::quiesce_all`. It's never held across a turn: lock, `begin`, unlock, run, lock, `finish`, unlock. The counters the request path reads (turns, failures, the pending-warning flag) are atomics beside it. The thread collects `Arc<Store>`s under the registry lock, lets go of it, then locks one schedule at a time; only `Store::open` holds the registry and then one schedule, to place a new store. Each `Arc` is dropped outside both mutexes, while the thread still holds its gate level, since a last `Arc` closes files (step 1 review). O(N) for about 30 stores, which costs nothing. There's no separate heap of `Weak<Store>` and nothing to rebuild after a fork. A store that retires and is revived keeps its history.
7. **Scheduling and spreading (Michael).** Stores are spread across the interval, never all at once: four caches opened together on 60 s take turns at 60, 75, 90 and 105 s, and on the default 300 s at 75 s apart. A new store's first turn is placed once, when the store is created, in the middle of the widest gap between the other stores' coming turns within the window from one to two intervals ahead. So opening never leads straight into maintenance (D-019, decision 10 of the first draft), and a test that sets entries, sleeps and calls `expire()` sees what diskcache would. Existing turns never move (built in step 1, replacing the first draft's re-spreading, which could only move turns earlier): nothing can keep pushing a turn back, and a `with Cache(...)` per request, which retires and revives the store, keeps its schedule. A store that closes leaves a gap rather than re-spreading the rest; the next store to open fills the widest one. A handle that asks for a shorter interval may bring the store's next turn earlier, never later.
8. **The thread parks with `std::thread::park_timeout`, never a condvar.** The gate's rules forbid a mutex taken outside a gate level (`gate.rs`, module docs): a fork landing while the thread held a condvar's mutex would leave the child with a locked mutex. A store that registers sets an atomic "schedule changed" flag and calls `unpark()`. That's harmless if the thread is gone, as it is in a forked child. With no store wanting maintenance, the thread parks with no timeout, so an idle process costs nothing.
9. **A turn never makes a request wait.**
   - Every read on the turn is no-wait. `Store::read` waits with a timeout, so the turn needs a `read_nowait`: try the slot, try the gate, a zero busy window.
   - Every write is no-wait, through a new `write_files_nowait`. It's `write_nowait` with `Changed`, so value files are unlinked after the lock drops. The existing `write_nowait` takes no `Changed` and would leak the files of file-backed rows.
   - The turn doesn't reuse `chunked` or `pause_between_chunks`. Those retake the lock with `LockPriority::AfterYield`, ahead of waiting request writers. Instead, before each chunk the turn checks `write_waiters() > 0` and ends if anyone is waiting, with no yield-and-retake.
   - `CHUNK` stays at 100 rows, about a 130 µs lock hold for inline values. Each turn has a budget of about 50 ms.
   - A turn cut short by the budget or a waiting writer, rather than ended by running out of work, runs again about 1 s later with its claim refreshed. Otherwise a 1M-row backlog at 300 s would take hours.
   - Over-limit eviction shares one helper with `cull_from`, parameterized by lock mode and budget, rather than a third copy of that loop.
10. **The forced checkpoint doesn't hold the write lock for its copy.** (And it records nothing in the WAL's counters or backoff, which describe the request path's checkpoints: the gate-tooling review found a background attempt that didn't succeed arming the 1 s backoff the last `close()` honors, so close could leave a 500 MiB WAL behind. A core test now asserts a busy or no-slot background checkpoint leaves the backoff unarmed.) Today `checkpoint_rounds` holds this process's write lock around the whole checkpoint, and a PASSIVE copy has taken up to 1.4 s under the soak. On the maintenance turn, a PASSIVE checkpoint runs first without the write lock: in WAL mode it doesn't block writers, and it does the long copy. Then a `try_lock` with no waiters attempts the short TRUNCATE. The step is skipped unless the WAL is over its trim size, and it respects `wal.in_backoff()`.
11. **The cross-process claim stores a fact, not a policy.** A `settings` row holds `last_swept_at` (`maintenance.expire_at`, and `maintenance.dirs_at` for the folder sweep). Each process skips the work while another process's claim is under 90% of its own cadence old, so the shortest interval among the open processes sets the pace, as decision 3 promises. A process's own claim (the time it last wrote, remembered in memory) never counts against it, so its continuation goes on; the 90% lets a process whose ticks run a little ahead take the work over once and keep it, rather than the two trading it on jitter. A `last_swept_at` more than a few seconds in the future is stale and ignored, which covers the wall clock stepping back. Skew between processes isn't a concern, since WAL mode means one host and one clock. The row is read once, cheaply, before any work, and read again inside the claiming `BEGIN IMMEDIATE` as a compare-and-set, so two processes that both saw a stale row don't both sweep. The value-folder task has its own row. Builds that don't know these rows ignore them, since settings are read by name, so the format stays 3: a core test writes both rows and an unknown `maintenance.*` one, then reopens as a plain cache and as a shard and runs `check`. The folder sweep's claim is the one write a tidy cache sees, once an hour per store.
12. **The probe uses the delete's predicate exactly:** `expire_time IS NOT NULL AND expire_time < ?now`, as `expire_from` and the write path's `any_expired` do. A probe that used `<=` would report work the delete won't do. All the tidy checks fold into one read: the claim row, `EXISTS` on the probe, `state`'s size, limit and policy, and the two cached PRAGMAs.
13. **Retirement and a turn in progress.** A `Weak::upgrade` that succeeds doesn't make the store live, since closed handles and deferred owners keep it alive. So `Store::begin_background_turn()` checks `!is_retired()` under the registry lock and bumps a `turns_in_flight` counter, and the turn checks `is_retired()` again before each chunk. The last release, which decides retirement under the same registry lock, waits for turns in flight, detached, within the release's own deadline (at least 50 ms). So "close returns and nothing is open" (D-018) holds, except for a turn inside a WAL checkpoint, or closing the process's last connection on a large WAL, which can outlast the wait: then one connection stays open briefly. The turn checks for retirement before it starts a checkpoint. A `FanoutCache` close waits for all its shards under one deadline. Two releases don't wait, deliberately: a failed open's (no budget left) and the end-of-fork drain's (it mustn't sleep under its level). In both, a turn's connection is discarded when it goes back to the retired pool.
14. **Fork: the thread is stopped for every fork (Michael, 2026-11-13).** CPython warns on `os.fork()` in a process with more than one thread, and counts OS threads to decide (checked on Linux and macOS, 3.12 to 3.14), so a thread left running would make every fork of a process with an open cache warn: a gunicorn preload master, `multiprocessing` with fork, test suites. So `gate::begin_fork` first stops the thread and joins it, which waits only for the chunk or checkpoint in progress (a fork waits for those anyway); `end_fork_parent` starts it again if a store wants it, and `end_fork_child` starts the child's own and drops the parent's claims, health and pending warnings. A turn sees the stop request between chunks and ends at once. What follows in this decision is the first draft's design, kept for its reasoning: The child has no maintenance thread. `_after_fork_in_child` already runs in the child; it starts the thread there if any store wants maintenance, so no hot-path generation check is added. A chunk built on `try_enter_shared` already refuses during a pending fork, so the turn just ends when a chunk is refused; no separate fork check is needed. If the thread held an upgraded `Arc<Store>` when the fork landed, the child keeps it counted forever. That's harmless, the same shape as the deferred owners note.
15. **`clock=` vetoes maintenance in this process.** The thread can only use wall time, and a fake clock that runs behind it would see live entries removed. Once a handle with `clock=` joins a store, that store gets no background maintenance in this process until it retires and is revived, when no such handle can still be open. A handle's request is merged under the registry in the same step that counts the handle (`count_handle`), so nothing can come between a handle and its veto. **A revive takes the reviving handle's interval** (Michael, 2026-11-13): none of the earlier handles is open, so their asks no longer apply, and `maintenance_interval=0` on a reopen reliably means off. The store keeps its place on its grid. An explicit non-zero `maintenance_interval` with `clock=` raises `ValueError`. Other processes can't be stopped, which is no different from them calling `expire()`; the docs say so.
16. **Failures are counted and logged once (Michael).** A failed turn (a full disk, a corrupt row, a panic) is retried on the next turn and never raised anywhere. A skip because another process swept recently counts as success, since the work got done. A streak of turns that found work and removed nothing because they were refused or stepped aside (a long `transact()` holding the lock) counts one failure once it has lasted 3 intervals, then another for each further 3, never one per continuation; a turn that removed rows before stepping aside isn't starved. Health's counters (turns, rows removed, failures) are atomics, readable behind a pending fork; the last error sits with the schedule. `stats()` keeps diskcache's `(hits, misses)` tuple (D-049); instead a new `maintenance_stats()` on `Cache`, `FanoutCache`, `NullCache` and the `CacheLike` protocol returns a `MaintenanceStats` dict (the interval, turns, rows removed, failures and the last error), which `Caches.stats()` carries as `CacheStats.maintenance`. A thread that couldn't be started counts as failures there. The next single-key Python call on that cache (every one that goes through `HandleConfig::attempt`, plus `incr` and `decr`) reads a pending-warning flag with one relaxed load, and after the operation, outside the gate, logs one `WARNING` on the `diskcache_oxide` logger; a cache nobody calls shows its failures in `maintenance_stats()` only. It doesn't log again until a turn succeeds. Under `durable=True` it's still a log line, never a raise.

## Steps

1. The schedule as pure functions with a fake time source: `due(state, now) -> TaskSet`, the spreading, the never-later rule, the first-turn delay, cadences, a store with a shorter interval from a second handle, and the `clock=` veto. **Built and reviewed (Fable):** `background::schedule`. Tasks are stamped with the grid tick their turn belongs to, so a late wake never skips the next tick. Intervals are capped at a day, and placement ignores a store ticking more than 64 times in the window, so it's bounded. Placement reads only `spread()`, the regular tick, never a continuation. `join` keeps the phase when shortening and places a store that had maintenance off. `begin`/`finish`/`skip` can't leave a thread spinning, and `revive` ends a `clock=` veto. 23 tests, three of them seeded property tests (spacing of at least `interval / 2N` for N stores opened together, placement always in its window, and a simulated thread waking late with random cut-short turns that never loses a tick).
2. The core no-wait primitives: the native-thread mark in `gate`, `read_nowait`, `write_files_nowait`, `begin_background_turn` and the retirement wait. Tests: the counting-blocker test, a no-wait read refused under a pending fork, and value files unlinked on the no-wait path. **Built and reviewed (Fable):**
   - `gate::mark_native_thread`: a native thread's `run_blocking` never reaches the Python layer's blocker.
   - `Store::begin_background_turn` returns a `BackgroundTurn`, whose `read` and `write_files` never wait. They refuse on a retired store, report only busy as `None` and pass real errors through, and they use `WriteTx`.
   - The in-flight count is a generation-tagged `Slots`, so a forked child reads a parent's turn as none.
   - `release_under` returns a `#[must_use]` `Retirement`, which forces each caller to wait for turns or say why not. `FanoutCache` waits for every shard under one deadline.
   - Tests: native unlinks of 10 files with no blocker call, a failed chunk rolls back and unlinks nothing, no-wait refusals, a turn refused after retirement, the central close-during-turn race with nothing left open, a close bounded by its budget, a shard close waiting, and refusal behind a fork.
   - The fork-mid-turn child case goes in step 5's Python fork tests, since the core has no in-process child.
3. The turn on a `Store`: the tidy read, the claim compare-and-set, expire and cull in budgeted chunks that end for a waiting writer, the continuation, the lock-free checkpoint and the folder sweep (shards included). **Built and reviewed (Fable):**
   - `background::turn`: `Store::maintenance_turn` returns a `TurnReport` with why it stopped (`Stop::Budget | Yielded | Refused | Retired`), rows removed, whether it saw work, and the first error. A failed task doesn't stop the later ones. A store poisoned by a fork gets no turn.
   - `Store::background_checkpoint`: PASSIVE without the write lock. The short TRUNCATE follows only when PASSIVE copied every frame, so the copy never happens under the lock. It never takes a store's last free connection, so a one-connection store doesn't checkpoint in the background. A pending fork is recorded as such.
   - `ops::Fill`, shared with `cull()`.
   - 21 tests: tidy reads write nothing; expiry with value files; rewrites before and between chunks; trimming `cull_limit` rows at a time with the overshoot bounded; `cull_limit=0` and `'none'` never evicting; expired-first; the claim cases and the in-write re-check; claim rows across reopen and `check`; a failed task; a refused turn recording no claim; poisoned, retired and pending-fork stores; the checkpoint truncating, refusing under a reader, and skipping a one-connection store; folder sweeps on shards; and a whole turn on a native thread with no blocker call. Tests: a no-op on a tidy cache under its limit; eviction of a cache left over its limit with no writes; no eviction under `'none'`; the claim, through a raw `open::connect` connection standing in for another process, since the registry allows one live `Store` per file; the shortest interval winning; a stale future claim being ignored; the budget splitting a large backlog; and expiring keys overwritten during a sweep never losing a fresh value. The delete already re-checks `expire_time` and `store_seq`; this test keeps it that way.
4. The thread: the `Builder` spawn and its failure path, `park_timeout` and `unpark`, `catch_unwind`, and the start after fork. **Built and reviewed (Fable):**
   - `background::worker`: one thread per process that never touches the interpreter. It parks with no timeout when nothing is due, and a store whose turn came earlier, or that was revived, wakes it. It stops and is joined before every fork, then restarts after (decision 14).
   - Handle requests are merged in `count_handle`, under the registry (decisions 3 and 15).
   - Decision 16's rule, as above. A panicked turn counts as its store's failure, with the panic's message; a pass that panics is counted process-wide.
   - Signals are left open, like any Python thread's: blocking them needs `pthread_sigmask`, so `unsafe`, for no difference from Python's own threads.
   - Tests: a real thread on 150 ms intervals sweeps a store nobody touches, leaves `OFF` and `clock=` stores alone, honors a shorter interval, skips a retired store and resumes on reopen, stops for a fork and comes back, takes a reopening handle's veto and interval, counts a held write lock as one starved streak, and raises one warning per streak. `record` gets table tests.
   - The shuttle model, `background/model.rs`, rebuilds the turn-against-last-close protocol on shuttle's primitives around the real `genlock::Slots`, since the registry and pool are `std` mutexes. Model 1 is a turn against the last close; model 2 adds a reopen and a second close. Each has a reach check, and both failed when `give_back`'s second retirement check was removed. Not modeled, by decision: the thread's stop-and-join for a fork and park against unpark, which are `std::thread` and a counter (traced by hand), and which the Python fork tests and the sanitizer lanes' maintenance pass exercise with real threads. A shuttle model (`scripts/model-check.sh`) covers a turn against `release_handle` and a revive, a fork landing between chunks, and park against unpark.
5. The Python surface: `maintenance_interval=` on the three constructors and `register`, the `clock=` rule, the hidden short-interval hook, the stubs, the `maintenance` stats group and the deduplicated WARNING. **Built and reviewed (Fable):**
   - `maintenance_interval=`: `None` is 300 s, `0` is off, otherwise 1 s to a day. `bool` raises `TypeError`, anything out of range `ValueError`.
   - It's carried through pickling and a rejoin after close. `clock=` vetoes the directory in this process, and with `maintenance_interval=0` too: the review caught that veto being lost when a default handle shared the directory.
   - `maintenance_stats()` and `MaintenanceStats`; `CacheStats.maintenance`.
   - The WARNING, including on `incr`/`decr`.
   - Hidden `_core` hooks for tests (`_set_maintenance_floor`, `_fail_next_maintenance_turns`), set and undone in one place (`tests/maintenance.py`).
   - D-061, with D-018, D-019, D-042 and D-055 amended.
   - The stub's claims match the code: per process and not stored, shortest open handle wins, first turn one to two intervals out, the hourly claim write, no background checkpoint at `max_connections=1`, and forks without Python's hooks.
   - `tests/unit/test_maintenance.py` covers the settings, sweeping, the veto across handles, failure logging on `get` and `incr`, a fork with a positive control for CPython's warning (the child runs its own thread and the parent's comes back), and a clean interpreter exit mid-turn. Conformance: an oxide-only test that rows go within about an interval with no writes, and a divergence entry covering what the background now changes. Explicit `expire()` and `cull()` can return less than diskcache would, because maintenance removed rows first; `volume()` and the WAL's size change on their own; and D-042's "shards don't sweep yet" goes away. Unit tests that assert on raw rows or `volume()` pass `maintenance_interval=0`.
6. Connection trimming, behind a `bench.memory` measurement; dropped if it saves nothing for sync gunicorn workers. **Deferred past 0.3.5:** the `TrimPool` task runs as a no-op. The saving is a connection's page cache (at most about 1 MiB at the default 256 pages), only for threaded workers; sync gunicorn workers keep about one connection per store, which trimming must keep anyway.
7. Docs: drop "nothing sweeps in the background yet" from the home page, Getting started, the web-workers and monitoring recipes and the skill; describe `maintenance_interval=`, the tasks and their cadences in Storage and WAL; update D-042; add a changelog entry. **Done:** the home page, Getting started (a new "Background maintenance" section), Storage and WAL (the tasks, the setting, taking turns, forks, `clock=`, reporting), the Caches guide, Troubleshooting, the web-workers and monitoring recipes, the skill, the roadmap ("Done: background maintenance (0.3.5)"), the divergences page (D-061) and the changelog (the headline, `maintenance_interval=`, `maintenance_stats()`, the `CacheLike` change). No guide tells people to schedule `expire()` any more.

## Gate

This is the Full tier (`scripts/release_tier.sh` counts `background/` as Full): the first long-lived background thread in a fork-sensitive core, touching the write lock, the fork gate, the registry and retirement, and the WAL checkpoint. That means every sanitizer lane, with the TSan and ASan Python lanes also running a third pass under `--maintenance-interval=0.01` (a pytest option, `tests/conftest.py`): every cache a test opens runs maintenance on that interval, in the processes the tests start too (through `DCO_MAINTENANCE_INTERVAL`), tests that assert what maintenance changes by design are marked `races_maintenance` and left out, and the pass fails if fewer than 20 turns ran beside it. The pass covers the oxide conformance suite and the unit tests where maintenance meets forks, threads, transactions and the forced checkpoints. Then a 5-second-interval soak, and the 24-hour release-shape soak, both reporting turns and failures in `status.txt` and keeping the fd leak check, which now covers a new thread.

## Open questions

None. Michael settled the first draft's three on 2026-11-13: the interval is per process (decision 3), failures are counted and logged once (16), and the turn culls too (5). The default interval is 300 s (decision 4).

# Plan 30: a FanoutCache's default page cache is split across its shards

Status: proposed (2026-11-16), not started. Reviewed once by the-rust-architect (findings folded in below: keep every core file untouched so the tier stays Patch; the fork wording; the closed-handle reuse path; `Caches(defaults=...)`; a test hook; the shard counts the tests use; the memory assertion; D-037; large inline values against the floor). Michael's decision (2026-11-16): change the default, but don't make `FanoutCache` the default or recommended cache yet.

## Why

`sqlite_cache_size` is SQLite's page cache per connection, 256 pages (1 MiB) by default, on `Cache` and on each `FanoutCache` shard alike. A thread that touches every shard of a `FanoutCache(shards=8)` holds a connection on each, so it carries 8 MiB of page-cache budget where the same thread on a plain `Cache` carries 1 MiB. Measured on the M5 Max with the 0.3.5 PGO wheels (quick runs, one round, a 50 MB database of 1 KB values, uniform keys; scripts in the session scratchpad, to be replaced by plan 29's `bench/fanout.py` run), RSS growth per process over its post-import baseline, with throughput:

| Case | `Cache` | `FanoutCache(shards=8)` today | with 32 pages per connection |
|---|---|---|---|
| GIL, 1 thread, 99:1 | 4.7 MiB, 422k ops/s | 15.0 MiB, 438k | 6.1 MiB, 399k |
| GIL, 1 thread, 90:10 | 4.9 MiB, 156k | 15.2 MiB, 240k | 6.4 MiB, 215k |
| 3.14t, 8 threads, 99:1 | 24.7 MiB, 360k | 33.2 MiB, 680k | 22.0 MiB, 569k |
| 3.14t, 8 threads, 90:10 | 18.8 MiB, 139k | 26.0 MiB, 297k | 22.3 MiB, 305k |

Each shard holds about an eighth of the data, so it needs about an eighth of the page cache. Splitting the default keeps most of the `FanoutCache` speedup (web gardens, free-threaded threads, write-heavy mixes) at about a plain `Cache`'s memory, so choosing a `FanoutCache` stops being a memory decision.

## Decisions

1. **The default only.** When `sqlite_cache_size` isn't passed, a `FanoutCache` gives each connection `max(MIN_SHARD_CACHE_PAGES, DEFAULT_CACHE_PAGES / shards)` pages, using the shard count the cache actually opens with (the stored count, which can differ from `shards=` since 0.3.5's mismatch warning). 8 shards get 32 pages (128 KiB); 1 shard keeps 256. A passed `sqlite_cache_size` keeps its meaning, pages per connection, on every shard, so nobody's explicit setting changes.
2. **The floor.** `MIN_SHARD_CACHE_PAGES = 32` (128 KiB): one maximal inline value plus the pages that reach it (Michael's answer 1). Reached at 8 shards and up, so a 256-shard cache doesn't run its connections on one page each.
3. **Where it's resolved.** In the PyO3 layer, beside the `max_connections` default (`crates/diskcache-oxide-py/src/cache/fanout.rs`, `base_for`, which applies `Store::default_total_connections(shards)`). `Settings.cache_pages` becomes `Option<u64>` (`cache.rs:923` gives `None` when not passed), with a doc comment like `max_connections`'s ("`None` when not given: a `Cache` takes 256, a `FanoutCache` its split"), and `Settings::options` takes `cache_pages` as a parameter, as it does `max_connections`. `Cache` passes `unwrap_or(DEFAULT_CACHE_PAGES)`; `base_for` passes `unwrap_or_else(|| shard_default_pages(shards))`. Floor division (3 shards get 85). `MIN_SHARD_CACHE_PAGES` and `shard_default_pages` live in `fanout.rs`, importing `DEFAULT_CACHE_PAGES` from the core without editing it: **no core file changes**, because `release_tier.sh` calls any diff under `store` Full, comments included. The stale "about `16 × sqlite_cache_size`" in the `default_total_connections` doc comment (`store/shards.rs:20-24`) waits for the next Full-tier release; the new bound goes in the constant's doc comment and in D-023/D-037. The core store is unchanged: it takes `cache_pages: u64` per shard, and its rule that a store uses the largest `cache_pages` any handle asked for (`store.rs`, `fetch_max`) still holds per shard. Two `FanoutCache` handles on one root with the default get the same value; an explicit larger one on either wins for that shard, as today.
4. **Everything that opens a FanoutCache gets it** (checked by the architect against the code):
   - `FanoutCache(...)`, and `Caches` (`_open` calls `FanoutCache` or `_open_fanout_keeping_stored`, passing `sqlite_cache_size` only when set).
   - A stored count that differs from `shards=`, and the format-fallback redirect: `base_for` runs inside `attempt` with `manifest.shards()`, and `layout::resolve` re-runs `attempt` on the versioned subdirectory, so both get the count actually opened with no extra code.
   - A pickle: `ReopenOptions::build` writes `sqlite_cache_size` only when passed, so a 0.3.5 pickle reopens with the new default.
   - A fork: no reopen happens. The child keeps the `Store` and its `cache_pages`, and its new connections apply it at lease (`pool.rs:38`, `store.rs:2058-2073`).
   - A closed handle used again (`StoreHandle::reopen` → `add_handle_until`) revives the same `Store` and keeps its value.
   - **`Caches(defaults={'sqlite_cache_size': ...})` makes the value explicit for every registered cache, `FanoutCache` shards included** (`register` merges `self._defaults | settings`, `caches.py:274`), so the split is lost there (question 5).
5. **The largest request still wins per shard (D-023).** A default handle (32) and an explicit 256 on the same root leave each shard at 256 until every handle closes. An explicit value below the default is raised to 32 by any default handle on the same root. Both are today's rule; D-023 says them in a sentence.
6. **The floor's cost, stated.** The per-thread budget equals a plain `Cache`'s up to 8 shards. Past that the floor holds, and a heavily sharded cache uses more memory rather than giving up a full inline read (Michael, 2026-11-16). At 32 shards the split would give 8 pages and the floor gives 32: a thread touching every shard holds 32 × 32 pages = 4 MiB (a plain `Cache`: 1 MiB), and the whole cache's cap is 64 connections × 128 KiB = 8 MiB (today 64 MiB). At 256 shards a thread touching every shard holds 256 × 32 pages = 32 MiB, and the whole cache's cap is 512 connections × 128 KiB = 64 MiB (today 256 MiB and 512 MiB). D-023 gives these numbers.
7. **Nothing on disk.** `sqlite_cache_size` is per process and never stored, so no format change and no settings row. Release tier: Patch (PyO3 layer only); `scripts/release_tier.sh` confirms. Ships in the next release that ships code.
8. **Not the recommended default (Michael).** The docs say what a `FanoutCache` costs and buys, with plan 29's measurements, and keep a plain `Cache` as the default in the recommended setup.

## Steps

1. **Code**, in `cache.rs` and `fanout.rs` only, as decision 3 says.
2. **A test hook.** Nothing reports `cache_pages` today. Add `FanoutCache._cache_sizes() -> list[int]` (and `Cache._cache_size()`): for each shard, `Store::read` (public, `store.rs:1306`) running `PRAGMA cache_size` on a leased connection, as the core test `connections_get_the_largest_cache_size_any_handle_asked_for` does. A leased connection shows what SQLite really applied, so the hook can test the largest-wins rule, lease-time application and a forked child. Private names are exempt from `test_stubs`, and the grep ban covers opens and the raw C API, not a PRAGMA through a `Connection`.
3. **Tests** (`tests/unit/`): the default at 1 shard (256), 3 (85, uneven), 4 (64) and 16 (floored to 32; the split alone would give 16). 8 shards can't tell the floor from the split, and 64 shards × 4 fds hits macOS's 256 limit under non-interactive ssh. Also: an explicit value unchanged on every shard; a default handle plus an explicit larger one (the larger wins); a stored-count mismatch; `Caches.fanout`; `Caches(defaults=...)` (whichever way question 5 goes); a pickle round trip; a forked child; a plain `Cache` unchanged at 256.
4. **The memory test, Michael's ask**, on `.venv-mem` with `DCO_REQUIRE_MEMSTATUS=1`, in the pattern of `tests/unit/test_memory.py` (`_core._sqlite_memory`), with `maintenance_interval=0` so the background thread leases nothing during the measurement. It asserts on the page-cache part, since connection overhead (that test's `CONNECTION_OVERHEAD`, 512 KiB) makes 8 shards' fixed cost higher than one connection's: one thread touching every shard of `FanoutCache(shards=8)` grows SQLite memory by at most 8 × (32 × `PAGE_SLOT` + `CONNECTION_OVERHEAD`), well below today's 8 × 256 × `PAGE_SLOT` (about 10.5 MB), so the test proves the split happened. `bench/memory.py` gets a `--shards` option and per-shard budget math, since it hardcodes `Cache`, `DEFAULT_PAGES` and `DEFAULT_CONNECTIONS`.
5. **Docs.** `_core.pyi`: `sqlite_cache_size` on `FanoutCache` ("As for `Cache`, per connection", line 1166) gets the default split, and the `max_connections` text that says "16 × sqlite_cache_size" is updated. The FanoutCache guide page (the memory side of "Should you use it?", rewritten in plan 29 from the studio run), Storage and WAL's memory bound, D-023 and D-037 in both divergence files (D-023's row on the divergences page too), the `Caches` docstring and guide for question 5, the skill, and `CHANGELOG.md` under Unreleased (Changed: the default, and that a passed value is unchanged).
6. **Measure.** Plan 29's extended `bench/fanout.py` confirms the table above on the studio, with uniform and zipf keys, and with 16 KiB and 64 KiB values at 8 and 32 shards and 16 and 32 pages. Values up to 64 KiB are stored inline (`spill::THRESHOLD`), so one value's overflow chain is about 16 pages: at 32 pages, reading one pushes the B-tree interior pages of the table and its four indexes out of the cache, and at 16 it evicts everything, and a `set` spills to the WAL before commit. The architect leans to a floor of 32 unless the 16-page run shows no loss. If zipf or the large values show a real loss, revisit the divisor and the floor before release.
7. **Gate.** `cargo clippy`, `cargo test`, the suite green on 3.14 and 3.14t against oxide, `scripts/check.sh`, then the Patch gate when it ships.

## Michael's answers (2026-11-16)

1. **The floor holds one maximal inline value and the pages that reach it** (Michael, revised 2026-11-16: "enough to read a large entry of 64k bytes without extra allocs"). A 64 KiB value (`spill::THRESHOLD`) is about 17 overflow pages of 4 KiB, plus the table B-tree's root and interior pages, the row's leaf and the key index's pages, about 21-24 pages in all. So 16 pages (64 KiB) is too small, and **the floor starts at 32 pages (128 KiB)**, reached at 8 shards and up: a cache with more than 8 shards gives each connection 32 pages, not less. Answer 6's benchmark confirms 32 is stable and shows whether 64 buys anything.
2. **A plain `Cache`'s 256 pages: profile it, don't change it here.** Plan 29's `bench/fanout.py` run also measures a plain `Cache` at smaller page caches, to see whether less memory costs speed, uniform and zipf. The aim is not to squeeze memory so far that speed falls apart; a change to `Cache`'s default, if the numbers argue for one, is a later plan of its own.
3. **Its own branch**, `plan-30-fanout-page-cache`, after plan 29 lands on `main`, with a PR, as plan 28 did.
4. **A registry-wide `sqlite_cache_size` skips `FanoutCache` entries.** `Caches(defaults={'sqlite_cache_size': ...})` applies to plain caches only; a `FanoutCache` keeps its split unless its own `register(..., sqlite_cache_size=)` names a value. That changes `caches.py`'s merge for that one key (Patch tier), and the `Caches` docstring and guide say so.
5. **Its own patch release** (the next version number, per the version rule), through the Patch gate: `scripts/check.sh` on all four Pythons, `scripts/sanitize.sh --quick`, the 2-hour release-shape soak. It also carries plan 29's `caches.py` docstring fix.
6. **The floor is settled by the benchmark, on stability as well as speed.** The floor starts at 32 pages (answer 1) and stays there only if the studio run (1 KB, 16 KiB and 64 KiB values, 8 and 32 shards, 16, 32 and 64 pages, uniform and zipf) shows no real loss and no instability at 32; otherwise it goes up to 64. The 16-page runs show what the floor protects against. Michael (2026-11-16): if a lower floor introduces instability, we don't lower it that much. A small page cache can't cost correctness (SQLite's `cache_size` is a soft target and keeps pinned pages past it), so instability here means erratic performance, and the run measures it: run-to-run spread (min, max, coefficient of variation across rounds), get and set latency at p50, p99 and p99.9, and the WAL writes a large `set` spills. The same test decides between the split values themselves: if 32 pages at 8 shards is unstable with large values, the divisor changes too, not just the floor.

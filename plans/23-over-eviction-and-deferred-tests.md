# Plan 23: The over-eviction fix and the tests held for after 0.1.1

Written 2026-11-09. Everything here changes `crates/`, which plan 21 freezes until 0.1.1 is published, so it all lands right after the release and ships as 0.1.2 (Michael's call, 2026-11-09). Nothing in this plan is in the 0.1.1 wheels.

## How these were found

A coverage run and a hand-picked mutation campaign on `e108542`: 55 plausible bugs planted one at a time in a scratch copy, 42 caught by the tests (76%), 13 survived. The survivors that were real gaps and testable from `tests/` are closed in `2b57026` (`tests/unit/test_totals.py`, a refused `add` leaving no file, the `Caches` busy-open retry, `close_all()` forgetting a failed open). The campaign's main finding was that every size-pressure test used inline values on oxide: `tests/conformance/test_eviction.py` says its values spill, and at 60,000 bytes they do on diskcache (threshold 32,768) but not on oxide (65,536). Running that suite at 70,000 bytes as well found the bug below.

## The bug: a write that sweeps expired large values evicts live entries it should keep

`cull` in [ops.rs](../crates/diskcache-oxide-core/src/ops.rs) removes expired rows first (`delete_expired`), then evicts the least recently stored only if the cache is at or over `size_limit`. It judges that with `before.size + size_delta`: the `totals.size` the prelude read before the write, plus the write's own change. The value files the sweep just removed are still in that number, so the cache looks over its limit although the sweep freed enough, and `delete_oldest` takes live entries with what's left of the `cull_limit` budget. Inline values don't show it, since their freed pages come off through `freelist_count`.

- Seen as: `test_expired_entries_are_culled_before_older_live_ones` at 70,000 bytes keeps `k010` onward and `big`, but loses the live `k000` to `k004`. diskcache 5.6.3 and the community fork pass.
- Impact: up to `cull_limit − swept` live entries evicted per such `set`, `add` or `incr` of a missing key, the three writes that cull (9 at the default), recomputed on their next miss. No wrong value, no leak; `totals` stays exact (`test_totals.py`). Only a size-limited cache that is at its limit, holding expired values over 64 KiB. Talk Python's `show_pages` (10 GiB of large values) is the cache that can meet it.
- Not a divergence: diskcache is right and oxide's own doc comment on `cull` says what it should do.

## Step 1: The fix

`RowWriter::delete_batch` already sums the removed rows' sizes for `adjust_totals`. Return that sum with the rows as a named `#[must_use]` `RemovedBatch { rows, freed }` (`must_use` on `Removed` doesn't reach through a `Vec`, so a dropped sweep would leak files silently), from `delete_expired` and `delete_oldest` (whose callers don't need `freed`), and have `cull` judge the limit with `before.size + size_delta − freed`. No extra query in release builds; a `debug_assert_eq!` against `totals.size` checks the reckoning in every core test (the Python suites run the release extension, which doesn't carry it). Confirmed in a scratch copy with a two-query form of the same subtraction: the failing case passes, with all 308 core tests, `test_totals.py` and `test_model.py`.

Core unit tests beside `culling_shares_one_budget_and_evicts_least_recently_stored`: a sweep of expired spilled values that brings the cache under its limit leaves every live row in place, through `set` and `add` (with the precondition asserted: nothing culled during the fill, and over the limit by the stale reckoning), and through an `incr` of a missing key in a test of its own (an incr adds no bytes, so the cache is filled past its limit with culling off first); one where the sweep isn't enough, so eviction runs with exactly the rest of the budget (the survivors named); and the first inside a held transaction that rolls back, with rows and value files all back.

## Step 3: Tests of tricky code no test runs (from the coverage run)

Production code is at 96.2% of lines (260 of 6,827 unrun, both builds merged, forked children counted). The unrun parts worth a test, in order:

1. **A write whose `COMMIT` comes back busy.** A `cfg(test)` hook of its own (not `FAIL_NEXT_END_BUSY`, which the held end consumes) in `WriteTx::commit`, in place of the `COMMIT`, returning `Timeout` without running it, so the transaction is really open and the `ROLLBACK` before the retry really runs. Not in `run_cached`, which `BEGIN`, `SAVEPOINT` and `ROLLBACK` share. Pinned by: the operation succeeds, its closure ran twice, an `incr` moved by exactly one delta, totals exact. A spilled `set` variant runs `commit_name`'s retry arm and `settle_with`.
2. **A forked child that inherited a held transaction.** The `d020` scenario forks from the owner thread, so in the child the share is the forker's own and the `inherited` branches (`store.rs`) are never taken: they need a transaction owned by a thread other than the forker, which with the before-hook in place means the owner parked in `begin_fork` behind another thread's claim (A forks and waits on B's level; B, holding the transaction, forks and parks; A's child ends B's hold and expects a fast `RuntimeError`). A must claim first, which Python can't observe: a sleep plus a check in the child, not strict determinism. `ShareEntry::Inherited => enter_unbounded` in `gate.rs` looks unreachable from the store (its one caller, `abandon`, is shadowed in a child): test it at gate level or remove it. **The WAL survivor is the most valuable test here and gates 0.1.2:** the parent writes more inline data inside the hold than the connection's page cache holds, asserts the `-wal` file grew, forks; the child ends the inherited hold; the parent reads every value back before and after its commit, and a fresh process reads them too (the parent's own page cache could hide damage). It may expose a real engine bug; a fix for that gets its own commit, CHANGELOG line and log entry.
3. **One deadline across the write-lock wait and the SQLite wait.** A thread inside a write holds both locks, so the two waits can't be stacked that way: in `store.rs`'s tests a helper thread takes `store.write_lock` directly and holds it for 90% of the timeout (signalling before the timed write starts, holding no gate level) while a raw `open::connect` connection holds `BEGIN IMMEDIATE` throughout; the write must time out within 1.45 timeouts (the mutant gives 1.9). `begin_hold` has the same two-phase shape and gets the same test.
4. **The unclaimed-fork wiring** (`end_fork_child`'s `None` arm; `reset_in_unclaimed_child` itself is run on a local gate by `gate.rs`'s tests). Not safe inside the lib's tests: `one_global_fork_at_a_time` doesn't stop another test's thread holding a std mutex at a raw fork, `end_fork_child` runs once per pid and bumps the global generation, and the lib denies `unsafe`. Its own integration test binary with one test, as `tests/sqlite_mutex.rs`: thread B holds a `begin_fork` claim, the test thread raw-forks, the child calls `end_fork_child`, does one store operation with a short timeout and `_exit`s under `catch_unwind`; the parent `waitpid`s and B ends its claim. Ignored under Miri.
5. **Forced-checkpoint outcomes:** the write-lock-timeout `Busy` and `NoSlot` (`max_connections = 1`, a reader blocked in its closure, a short `checkpoint` from another thread, expecting `Ok(false)`). `checkpoint_once`'s own `Busy` and two "replaced while opening" cases are already tested (`open_race.rs`); name the branch still unrun before writing one.
6. Small ones from the campaign: the write-time sweep's `expire_time < now` boundary (one row expired earlier, one expiring exactly now, then a `set`); `Decision::Nothing` with the WAL exactly at its limit; `delete_version_nowait` from inside a `get_with` decode returning `Skipped` (gate depth, not a busy lock, being what refuses); the D-016 fallback in a poisoned child reporting a miss (D-020).

Each item is its own commit, green on its own. Only item 2's WAL test gates 0.1.2; the rest follow.

Not worth a test: `const fn` constructors, `unreachable!` and `debug_assert!(false)` arms, the SQLite-initialized-first mutex statuses, the codec's serde fallbacks (plan 22's notes), `volume == size_limit` exactly, and the stale-idle-connection loop in the pool (equivalent: `close_idle_all` empties it before every fork).

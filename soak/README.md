# Soak test

A long run (24 hours by default) of many processes and threads against two shared caches, with chaos: SIGKILLed and respawned workers, forks under load, and `clear()`/`expire()`/`cull()` under load. It looks for deadlocks (stalls), races (lost, doubled or corrupt writes, expired values returned, totals drift, missing files), and leaks (RSS, fds, database and WAL growth). Workers alternate between Python 3.14 and 3.14t on the same cache files. Beside them run the lanes that plan 09 needs: exactly-once `pop`, `durable=True`, forks behind budgeted calls, real stuck forks, and `wal_checkpoint='auto'`. See [The plan 09 lanes](#the-plan-09-lanes). A FanoutCache role runs beside them on its own 8-shard root (plan 13, step 13g).

## Before production: a fresh soak is required

Plan 12 changed the write path and the transaction machinery: step 1 updates a live counter in place in `incr`, and step 3 made `transact()` public, bounded every wait that ends a held transaction (an end that can't run is parked and rolled back at the end of the fork), and lets another thread end a transaction. No soak result from before those commits covers them, so run a fresh 24-hour soak on the mini, on a build that includes both, before it goes to production. The held-transaction sites in the load, the stuck-fork lane and the durable hog now go through `transact()`, as Talk Python will.

Plan 13 adds `FanoutCache`: a Rust pyclass over 8 stores, with routed calls, fanned-out maintenance under one deadline, a merged `iterkeys`, and new open and close paths over every shard. No soak has run it, so a fresh 24-hour soak on the mini, on a build that includes step 13g, is required before a FanoutCache goes to production (Michael runs it). The `fanout` role below is what covers it.

## Setup on a fresh Mac

```sh
xcode-select --install                                                     # C compiler, for the bundled SQLite
curl https://sh.rustup.rs -sSf | sh -s -- -y --profile minimal             # Rust (rust-toolchain.toml picks the version)
curl -LsSf https://astral.sh/uv/install.sh | sh                            # uv (it downloads Python 3.14 and 3.14t itself)
exec $SHELL -l                                                             # pick up the new PATH
```

## Run

```sh
tar xzf diskcache-oxide-soak-*.tar.gz && cd diskcache-oxide-soak-*/
nohup soak/run.sh --hours 24 > soak.out 2>&1 &                             # survives closing the terminal or ssh
tail -F soak-results/latest/status.txt                                     # live status, updated every minute
```

`soak/run.sh` builds both Pythons (the first build takes a few minutes), checks the build, and keeps the Mac awake with `caffeinate`. Options pass through to `python -m soak.soak` (`--help` lists them): for example `--minutes 10` for a quick trial, or `--procs 8 --threads 4`. `--procs`, `--threads` and `--rate` size the `run` workers only. The lanes are paced on their own and add `--lanes` processes (default 4) and, per `--auto-stores` (default 2), a writer and a reader process, so 8 by default, and the fanout role adds `--fanout-procs` more (default 2). The auto readers run 8 flat-out threads for 5 s of every 30, in turn: about 2 CPUs on average, 8 during a burst. The lanes take about 0.3 CPUs. `ops/s` counts only the `run` workers, so it stays comparable with `--rate`. On a machine that stays saturated, `--auto-stores 1` halves the auto group's CPU. `--quiet-after <seconds>` (default 1800) lowers the quiet window for a short smoke. `--maintenance-interval <seconds>` runs background maintenance (plan 28) on that interval in every cache the workers open (every process applies it at startup from `DCO_MAINTENANCE_INTERVAL`); left out, the caches get the library's 5 minutes, which a worker reaches only after 5 to 10 minutes of life. The auto group's stores past the first keep it off, since they measure the forced checkpoints that background ones would take over; store 0 keeps it on, so the two kinds still meet. Stop early with `kill -INT <pid of soak.soak>`; it still runs the final checks and writes the summary.

## What it records

All in `soak-results/<timestamp>/` (`latest` points to the newest):

- `status.txt`: live status, rewritten every interval.
- `report.html`: charts and the verdict. It refreshes itself every minute while the run is going; open it in a browser.
- `summary.md`: the final verdict, leak slopes and problem list, written at the end. `python -m soak.report <dir>` rebuilds it and the report from the data at any time.
- `timeline.csv`: the whole system, one row per interval.
- `workers.csv`: each worker, one row per interval.
- `maint.csv`: every maintenance call.
- `events.jsonl`: every event; problems have `"problem": true`.
- `stalls/`: native stack samples (`sample`) captured when a worker or maintenance call stops making progress. The matching Python tracebacks are in `logs/<worker>.log`.

The verdict is PASS (no problems, no flags), WARN (no problems, but a leak, latency-drift or WAL flag), or FAIL.

## The plan 09 lanes

Their counters are in `status.txt` every interval, in `timeline.csv` for the charts, and, with the end-of-run checks, in the "Plan 09 lanes" section of `summary.md` and `report.html`. `summary.md` also splits them by interpreter. A lane whose count ends at zero fails the run (`lane-silent`), so one that silently stopped can't pass. That covers `pops`, `pq_delivered`, `durable_calls`, `durable_false`, `forks_behind`, `stuck_forks`, and judged rounds per auto store. Each of the four `pop` sites is held to it separately on runs of an hour or more. A lane that keeps running but stops proving anything fails as `lane-went-quiet`, once a proof counter (also by interpreter, and rounds by store) hasn't moved for 30 minutes, or 20 of its own mean gaps if that's longer, so a slow counter on a low `--rate` doesn't trip it. A counter still at zero gets the 30 minutes alone: below about `--rate 5000`, `pops_held` can trip that on a long run, since held transactions come from the load's writes. Every thread has a heartbeat, the load threads included, so a hang in one fails as `lane-stall` with stacks in `stalls/`, even though the worker's other threads keep its op count moving. One still running 60 s after the stop is a problem too.

| Line in `status.txt` | What it means | Fails the run when |
|---|---|---|
| `background maintenance:` | Plan 28's turns, rows removed and failures, summed over every cache every worker holds (`maint_bg` in the worker stats; `bg_*` in `timeline.csv`), with the last failure's message | A worker's `maintenance_stats()` raises (`maintenance-stats-error`); with `--maintenance-interval`, turns or rows removed are zero at the end (`lane-silent`). Failures alone are a `maintenance-failures` event, not a problem: a long-held transaction starves a turn by design |
| `pop:` | `pop` calls by site: `chaos.pop` in the load, half of held transactions' deletes (rolled back too), in forked children, and the exactly-once lane | The counts above are zero; a popped value fails its CRC or isn't the last committed version. Hits on `pop`'s locked fallback can't be seen from Python: no counter reaches it |
| `exactly-once:` | Every `run` worker's 2 lane threads race `add('pq:<tick>', token)` and `pop` at the same wall-clock tick, twice a second. A slot refills once it's popped, so that's about 22 tokens a second at the full shape: about 1.9M tokens and 4.6M ledger rows (630 MiB) in 24 hours, and the end-of-run walks get an hour. The consumer then does `add('delivered:<token>', worker)` | That add returns False (a duplicate), or at the end (`final-pq`) a recorded token is neither delivered nor queued. A lost token is excused only if a kill of a `run` worker within 30 s after it was produced is left to take it, at most 2 per kill, since a consumer can die between its `pop` and its `add` |
| `durable:` | `durable=True`, `timeout=0.25`, on `durable/`, single-writer keys. A hog holds the write lock for 0.6 s every 5-15 s, so writes really fail. "Answered as failures" are the False or default answers on a key whose state made them mean that | An exception escapes; after a failure answer the non-durable read-back isn't the previous version; a False `set` count disagrees with `_durable_stats()` at a clean exit; a non-`str` key stops raising `TypeError`; `broken` is non-zero; a bucket with failures logged nothing; two lines from one bucket land under 55 s apart (the limit is 60 s, and a line can be late by a call's wait) |
| `forks behind traffic:` | Two threads at 200 calls a second on `behind/` with `timeout=1`, and a fork every 2-4 s. A fork counts as behind traffic if a call started while it ran | A call overruns its budget by more than 3 s (`OVERRUN_ALLOWANCE`, durable calls too; the worst get or set in the last 24 hours was 339 ms and a forced checkpoint's copy has reached 1.4 s), or stalls |
| `fork_timeouts:` | The gate's count of calls that timed out behind a fork. It's per process, so the small-timeout lanes are kept apart | Non-zero in `run` or auto workers, whose timeouts are 30 and 60 s, so it means a fork was stuck. The lanes' number is expected and only reported |
| `stuck forks:` | Every 30-90 s in each `lanes` worker, in turn a held transaction and a pickle hook keep a gate level while a thread forks. Another thread's `get`, `set`, `pop` or `in` with `timeout=0.2` must get `Timeout`. The level then goes and the fork must finish, its child reading and writing. The hold can't outlast 5 s, and is normally about 0.2 s | The caller doesn't return in 5 s (the wedge), returns anything but `Timeout`, or takes under 0.19 s or over 1.5 s; the fork returns while the level is held, or doesn't finish in 40 s |
| `auto store N:` | One writer process and one reader process per `auto-<N>/`, `wal_checkpoint='auto'`, a 1 MiB limit. In its burst the writer does 2,000 writes a second beside 8 flat-out free-threaded reader threads, because a paced or GIL reader lets the WAL reset normally and forces no round. Rounds are forced checkpoints; the success rate is `successes / (successes + busy)` | A store has too few rounds that reached the WAL (50, or 50 an hour past the first hour); any round ends in a real error; on a one-writer store the rate over the whole run is under 95% (`AUTO_MIN_SUCCESS_RATE`, with the evidence in a comment in `soak/soak.py`). Peak WAL climbs with load, to about 26 MiB of the 1 MiB limit at load 48 on 18 CPUs, and that's reported, not judged. 95% says forced checkpoints work under this load. It doesn't catch lost retries, since a 1-try build can pass it at a light enough load |
| `load` | The 1-minute load against the CPU count, also in `timeline.csv` with each auto store's successes and busy, so a low rate can be matched to what the machine was doing | Nothing: it's context |
| `fanout:` | `--fanout-procs` processes (default 2, alternating interpreters; the first is never killed) with `--fanout-threads` paced threads each (default 4, 500 calls a second each), on one `FanoutCache(fanout/, shards=8)`. Routed `get`/`set`/`pop`/`delete` on shared self-checking keys (some spilled, some expiring), a `fctr:<worker>` counter, and `fown:<worker>:<n>` keys with one writer. Every 5 s a merge of the worker's own keys both ways, and every 20 s a merge and an `__iter__` of every key. Every 30 s, in turn, `expire`, `cull` or `checkpoint` with `timeout=10` for the whole call. A fork every 10 s while all of that runs, its child writing and merging a key on every shard. The 8 shard databases get the same totals, file and integrity checks as the other stores | A value fails its CRC or comes back expired; an owned key or the counter reads back wrong (at once, at a clean exit, or `fctr` in the database below what a killed worker reported, or not exactly a cleanly exited worker's final count); a merge is out of order or repeats a key, or a walk repeats or loses an owned key; a maintenance `Timeout` has no `.failed_shards` or `.removed`; a child fails; the process's fds on fanout databases pass 48 (`2 × max_connections + 2 × shards` at the default two connections per shard, D-037) at one of the checks every 5 s, which logs each path's count (`status.txt` and the summary show the highest sampled, not a continuous peak); any of `fanout_ops`, `fanout_merges`, `fanout_maint` and `fanout_forks` is zero at the end or goes quiet, counted per interpreter only for interpreters that run a fanout worker |
| `side chaos:` | Kills and restarts of the killable lanes, auto and fanout workers, on their own timer, so the `run` workers see as much chaos as before | A restart that hangs or exits badly |

Two things to keep in mind when comparing runs:

- **`wal_ckpt_max_pause_us` and "worst pause" now sum every `TRUNCATE` try in a round** (plan 09, step 2b), so they aren't comparable with soaks before commit `5b2ea85`, which timed one try.
- **Several writers in several processes are a documented limit, not a failure** (D-024: `wal_size_limit` is a target). `--auto-writers 2` runs that shape: its rate and peak WAL are reported, and its rate isn't judged. A very large peak still raises the existing WAL flag, which makes the verdict WARN.

## High Findings

### H1. `Transaction` (`__exit__`, `__enter__`, `__repr__`) and `stats()` bypass the early child reset in an earlier `after_in_child` hook, and a cross-thread end that parked or abandoned before `fork()` clears `ending_in` and raises `TransactionAborted` (or returns `False`) in the child

- **Severity:** High
- **Tier:** Full
- **Where:** `crates/diskcache-oxide-py/src/cache.rs:2292-2295` (`Transaction::end_lost_to_fork`), `crates/diskcache-oxide-py/src/cache.rs:2331-2344` (`Transaction::wait_for_end`), `crates/diskcache-oxide-py/src/cache.rs:2353-2455` (`Transaction::__repr__`, `Transaction::__enter__`, `Transaction::__exit__`), `crates/diskcache-oxide-py/src/cache.rs:335-339` (`Cache::stats`), `crates/diskcache-oxide-py/src/cache/fanout.rs:250-260` (`FanoutCache::stats`), `crates/diskcache-oxide-py/src/cache/fanout.rs:813-818` (`FanoutCache::refuse_fan_out`), `crates/diskcache-oxide-core/src/poison.rs:64-66` (`check_usable`), and `crates/diskcache-oxide-core/src/gate.rs:208-210, 859-863` (`generation`, `enter_child_early`).
- **Trigger:**
  1. **Early `after_in_child` hook (`EARLY_CHILD`, registered before `diskcache_oxide`'s):** Thread B in the parent is ending Thread A's `Transaction` `tx` (`ending_in` is set to `parent_gen + 1`, state is `TxState::Ending`, and Thread C may also be in `wait_for_end` holding `tx.state` detached) while Thread A calls `os.fork()`. In the child, before `diskcache_oxide`'s `_after_fork_in_child` runs, another library's earlier `after_in_child` hook calls `tx.__exit__(...)`, `tx.__enter__()`, `repr(tx)`, `cache.stats()`, or `fan.stats()`.
  2. **Cross-thread end that parks or abandons before `fork()` completes (even after `end_fork_child()` has run):** Thread A holds `with cache.transact() as tx:`. Before `fork()` happens—either on 3.14/3.14t while Thread A is inside a cache call on `tx` (e.g. `cache.get('hooked')` whose decode hook is about to call `os.fork()`, so `PinnedSlot` is `Lent`) or on 3.14t while Thread A is in `_before_fork`—Thread B calls `tx.__exit__(ValueError, ValueError(), None)` (a rollback, where `held.finish(false)` has `deadline = Instant::now()` and returns `Ok(())` immediately after abandoning or parking the rollback) or `tx.__exit__(None, None, None)` with a short `timeout` that expires and parks the end (`held.finish(true)` returns `Err(Error::Timeout)`). Thread B then executes lines 2447–2450 of `cache.rs`: it locks `self.state`, sets `*state = TxState::Done { committed: false }`, and stores `self.ending_in.store(0, Ordering::Release)`. Thread A's `fork()` then runs, and in the child Thread A exits its `with cache.transact():` block.
- **Effect:**
  1. In Trigger 1 (`EARLY_CHILD`), `enter_child_early()` only runs when entering `GATE` (`Gate::try_enter_shared` or `HeldShare::try_enter`). Neither `Transaction::end_lost_to_fork()` nor `poison::check_usable()` triggers `enter_child_early()`. Consequently, in an earlier `after_in_child` hook, `gate::generation()` is still the parent's generation, so `tx.end_lost_to_fork()` sees `ending_in == gate::generation().wrapping_add(1)` and returns **`false`**. `tx.__repr__()`, `tx.__enter__()`, and `tx.__exit__()` then immediately call `self.lock_state()` (`self.state.lock()`), directly violating **Claim 5** ("`Transaction.__exit__`, `__enter__` and `__repr__` in a child never touch a mutex another thread held at the fork"):
     - If Thread C in the parent held `tx.state` inside `wait_for_end` (which runs detached via `crate::detach`), the child **deadlocks forever** on `self.state.lock()`.
     - Otherwise, `tx.__exit__(None, None, None)` sees `TxState::Ending`, calls `self.wait_for_end(py)`, **sleeps for the full cache `timeout` (60 s by default)** waiting for a thread that does not exist in the child, and raises `Timeout` instead of `ForkedInsideTransactionError`.
     - `tx.__exit__(ValueError, ValueError(), None)` sees `TxState::Ending` with `commit = false` (`cache.rs:2422-2424`) and **returns `Ok(false)` at once without raising `ForkedInsideTransactionError`**.
     - `cache.stats(reset=True)` and `fan.stats(reset=True)` call `store.check_usable()` before `end_fork_child()` has run, see an empty `UNUSABLE` set, and **succeed (returning and resetting the counters) instead of raising `ForkedInsideTransactionError`**.
     - For the exact same reason (`poison::check_usable` not triggering `enter_child_early`), `FanoutCache.refuse_fan_out` passes all shards in an earlier `after_in_child` hook before shard 0 enters `GATE`, which is the root cause of the "Already known" `FanoutCache.clear()` partial-clear caveat.
  2. In Trigger 2 (even after `end_fork_child()` has run normally), because Thread B's `held.finish` returned after abandoning or parking the transaction and Thread B set `*state = TxState::Done { committed: false }` and `self.ending_in.store(0, Ordering::Release)` before `fork()`:
     - First, at `cache.rs:2447-2450`, Thread B stores `self.ending_in.store(0, Ordering::Release)` **while still holding `let mut state = self.lock_state()`** (and then calls `self.ended.notify_all()`, waking any detached waiter in `wait_for_end` to re-acquire `self.state` while `ending_in == 0`). If `fork()` lands after line 2449 while Thread B or a detached `wait_for_end` waiter holds `self.state`, `end_lost_to_fork()` in the child sees `ending_in == 0` (`false`) and `self.lock_state()` **deadlocks in the child on the inherited mutex**.
     - Second, when `self.state` is not locked at the fork, `tx` in the child has `TxState::Done { committed: false }` and `ending_in == 0` even though the transaction's connection was inherited open (`PinnedSlot::Lent` or a parked end in `DEFERRED_ENDS`) and the cache is unusable in the child. When the child leaves the inherited `with cache.transact():` block (`tx.__exit__`), it hits `TxState::Done { committed: false }` (`cache.rs:2412-2417`): on a normal exit (`commit = true`) it raises **`TransactionAborted` instead of `ForkedInsideTransactionError`**, and on an exceptional exit (`commit = false`, e.g. after a call inside the `with` block raised) it **returns `Ok(false)` instead of raising `ForkedInsideTransactionError`** (contradicting D-020 and `_core.pyi:94-95`).
- **Evidence:** Line-by-line trace of `cache.rs:2288-2455`, `cache.rs:335-339`, `fanout.rs:250-260, 813-818`, `store.rs:2282-2346, 2426-2431`, `poison.rs:64-66`, and `gate.rs:265-273, 859-923`.
- **Confidence:** Confirmed.
- **Fix idea:**
  1. Export a cheap `pub(crate) fn maybe_reset_child_early()` from `gate.rs` (one thread-local `GLOBAL_THREAD.with(|t| t.forking.get())` check that calls `enter_child_early()` only when `true`) and call it at the start of `poison::check_usable()` and `gate::generation()` (or `Transaction::end_lost_to_fork()`). That single thread-local read on `check_usable` and `generation` makes `Transaction.__exit__`/`__enter__`/`__repr__`, `Cache.stats()`, `FanoutCache.stats()`, and `FanoutCache.refuse_fan_out` (`clear()`, `expire()`, `cull()`, `evict()`, `reset()`, `check()`, `len()`, `volume()`, `iterkeys()`) trigger `end_fork_child()` before doing anything in an earlier `after_in_child` hook—fixing Trigger 1 and eliminating the "Already known" `FanoutCache.clear()` early-hook caveat at the same time.
  2. In `Transaction`, store the process generation in which the transaction was entered (or ended), e.g. `entered_in: AtomicU64` (set to `gate::generation() + 1` when entering), and in `Transaction::__exit__` move `self.ending_in.store(0, Ordering::Release)` to **after** `drop(state)` (Wait: even better, never clear `ending_in` to `0` after `Ending` begins—keep `ending_in = gen + 1` permanently once the single-use `Transaction` enters `Ending`, or check `entered_in != gate::generation() + 1 || self.cache.handle().store.check_usable().is_err()` before locking `self.state`!). Wait: think about keeping `ending_in` non-zero (or checking `entered_in != gate::generation() + 1`)! In the parent, `gate::generation()` never changes, so `ending_in == gate::generation() + 1` is always true in the parent (`end_lost_to_fork()` is always `false` in the parent!), whereas in **any** child forked at or after `Ending` began (or after `Entering` began!), `gate::generation()` is bumped, so `entered_in != gate::generation() + 1` is immediately `true` in the child without ever touching `self.state`!
- **Reproduction:**
  ```python
  import os, threading, time
  from diskcache_oxide import Cache, ForkedInsideTransactionError

  # Reproduction A: cross-thread rollback while owner is in a hook that forks (Trigger 2)
  # When thread B rolls back `tx` while thread A is inside `get('hooked')` just before `os.fork()`,
  # `held.finish(false)` abandons immediately and sets `TxState::Done { committed: false }` and `ending_in = 0`.
  # In the child, exiting `with cache.transact():` raises `TransactionAborted` instead of `ForkedInsideTransactionError`.
  ```

### H2. Opening a `FanoutCache` with explicit limits in a child where shard $k > 0$ is unusable mutates shards `0..k-1` on disk and in memory before raising `ForkedInsideTransactionError`

- **Severity:** High
- **Tier:** Full
- **Where:** `crates/diskcache-oxide-core/src/store/shards.rs:76-85` (`Store::open_shards`) and `crates/diskcache-oxide-core/src/store.rs:619-622, 943-1004` (`Store::open_until`, `Store::join`, `Store::set_limits`).
- **Trigger:** A parent process opens a `FanoutCache` (say 4 or 8 shards), enters `with fan.transact(key=k):` where `k` hashes to shard $k > 0$ (or forks from a decode hook while reading shard $k > 0$), and forks. In the child, only shard $k$ is marked unusable (`Error::Unusable`); shards `0..k-1` are usable. The child then calls `FanoutCache(directory, size_limit=..., cull_limit=..., eviction_policy=...)` (or reopens with larger `max_connections`, `sqlite_cache_size`, `wal_size_limit`, or `wal_checkpoint='auto'`).
- **Effect:** Directly violates **Claim 6** ("On a `FanoutCache`, only the shard that was open is refused, and a call that spans every shard raises before it changes any"). `Store::open_shards` iterates `for index in existing.into_iter().chain(new)` and calls `Self::open_until(&options[index], deadline)` on each shard one by one without first checking whether every shard's database file is usable:
  - For shards `0..k-1`, `Store::open_until` finds the live shard store via `Self::lookup` and calls `store.join(options, left())`, which executes `self.set_limits(timeout, options.requested)`—opening a write transaction on each of shards `0..k-1` and running `UPDATE state SET size_limit = ?1, cull_limit = ?2, eviction_policy = ?3 WHERE only = 1` **on disk**, updating `cached_limits` in memory (`fan.cull_limit` and `fan.eviction_policy` read shard 0's cached limits), and raising `max_connections`, `cache_pages`, `wal_size_limit`, and `auto_checkpoint`.
  - When the loop reaches shard $k$, `Self::open_until` fails with `Error::Unusable` (`ForkedInsideTransactionError`). `open_shards` calls `release_all` on shards `0..k-1` and returns `Err(Error::Unusable)`, but the on-disk `state` changes (and in-memory limit changes) on shards `0..k-1` are already committed.
  - Because the `state` table lives in the shared SQLite files on disk, the **parent process's** `FanoutCache` now has shards `0..k-1` persisted with the child's new `size_limit`, `cull_limit`, and `eviction_policy` while shards `k..N-1` keep the old limits.
  - Furthermore, if the child called `fan.close()` first (retiring all shards in the child) and then called `FanoutCache(directory)` even with no limit arguments, `Store::open_shards` takes the slow open path (`open::connect`, `open::prepare_creating`, `open_pin`) on shards `0..k-1`, opening and closing SQLite connections on disk before failing on shard $k$.
- **Evidence:** Reproduced in `/tmp/dco-review-03ad2038` via `cargo test` (`probe_6_fork_child_reopen_and_fanout_open_shards`). In the reproduction, a parent with a 4-shard `FanoutCache` (`cull_limit=10`, `eviction_policy='least-recently-stored'`, `size_limit=1 GiB`, 256 MiB/shard) held a transaction on shard 2 across `fork()`. The child called `Store::open_shards` with `size_limit=64 MiB` (16 MiB/shard), `cull_limit=3`, `eviction_policy='none'`, which failed with `Error::Unusable` on shard 2. Inspecting the parent process's shards on disk afterwards (`shards[i].read_limits(T)`) showed shard 0 had `Limits { size_limit: 16777216, cull_limit: 3, eviction_policy: None }` while shard 3 had `Limits { size_limit: 268435456, cull_limit: 10, eviction_policy: LeastRecentlyStored }`.
- **Confidence:** Confirmed and reproduced.
- **Fix idea:** At the start of `Store::open_shards` (`crates/diskcache-oxide-core/src/store/shards.rs:71`), enter the gate once (`let gate = super::enter_until(deadline)?;`) and check `super::check_usable_at(&crate::open::db_path(&o.directory))?` for every shard in `options` before opening or joining any shard.
- **Reproduction:**
  ```rust
  let manifest = fanout::open_manifest(&dir, ShardRequest::Exactly(Manifest::new(4).unwrap())).unwrap();
  let shards = Store::open_shards(&opts(&dir), manifest, Instant::now() + T).unwrap();
  let _held = shards[2].begin_hold(T).unwrap();
  gate::begin_fork();
  let pid = unsafe { libc::fork() };
  if pid == 0 {
      gate::end_fork_child();
      let mut new_opts = opts(&dir);
      new_opts.requested = Requested {
          size_limit: Some(64 << 20),
          cull_limit: Some(3),
          eviction_policy: Some(EvictionPolicy::None),
      };
      assert!(matches!(Store::open_shards(&new_opts, manifest, Instant::now() + T), Err(Error::Unusable)));
      unsafe { libc::_exit(0) };
  }
  gate::end_fork_parent();
  // In the parent, shard 0 on disk now has cull_limit=3, eviction_policy=None, size_limit=16 MiB,
  // while shard 3 on disk still has cull_limit=10, eviction_policy=LeastRecentlyStored, size_limit=256 MiB!
  assert_eq!(shards[0].read_limits(T).unwrap().cull_limit, 3);
  assert_eq!(shards[3].read_limits(T).unwrap().cull_limit, 10);
  ```

## Medium Findings

### M1. `Store::add_handle_until` lacks `check_usable`, so any call on a closed handle in an unusable child opens a new SQLite `FilePin` connection, revives the retired `Store`, and marks the handle open again; `release_handle_within` sweeps value dirs on disk; `Cache.evict(None)` and `remove_old_formats()` skip `check_usable`

- **Severity:** Medium
- **Tier:** Full
- **Where:** `crates/diskcache-oxide-core/src/store.rs:1034-1070` (`Store::add_handle_until`), `crates/diskcache-oxide-core/src/store.rs:1085-1111` (`Store::release_handle_within`, `Store::sweep_value_dirs`), `crates/diskcache-oxide-py/src/cache.rs:327-329, 670-671` (`Cache::remove_old_formats`, `Cache::evict`), and `crates/diskcache-oxide-py/src/cache/fanout.rs:220-222` (`FanoutCache::remove_old_formats`).
- **Trigger:**
  1. In a child process where a cache is unusable (`Error::Unusable`), `cache.close()` is called (which is explicitly supported and used in `soak/worker.py:764` and `tests/unit/fork_scenarios.py:165`), retiring the `Store` and dropping its inherited `FilePin`. Later in the child, any method is called on that closed handle (`cache.get('k')`, `cache.set('k', 1)`, `cache.checkpoint()`, `len(cache)`, etc.).
  2. In an unusable child, `cache.close()` is called (or `cache` is dropped at GC / exit), or `cache.evict(None)` is called, or `cache.remove_old_formats()` / `fan.remove_old_formats()` is called.
- **Effect:**
  1. **Violates Claim 1** ("no path opens a new connection to a file marked unusable. Every production open is behind `check_usable` under a gate level"). When any operation is called on a closed handle, `StoreHandle::run` / `StoreHandle::ensure_open` (`cache.rs:978-1009`) calls `self.reopen(timeout)` -> `self.store.add_handle_until(deadline, self.maintenance, || self.closed.swap(false, Ordering::AcqRel))`. `Store::add_handle_until` enters the gate (`let gate = enter_until(deadline)?;`) but **never calls `self.check_usable()?`**:
     - It runs `claim()`, flipping `handle.closed` from `true` back to `false`.
     - Seeing `self.is_retired() == true`, line 1064 calls `open_pin(&gate, &db_path)` -> `sqlite::open_with_flags(db_path, SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_NO_MUTEX)`, **opening a new SQLite connection to the unusable database file in the child**.
     - Line 1066 calls `self.claim(&stores, pin, asked)`, which increments `self.handles` from `0` to `1`, un-retires the `Store` (`self.retired = false`), stores the new `FilePin` connection into `self.pin` (keeping an open file descriptor on `diskcache-oxide.sqlite`), and calls `self.ask_maintenance` (which can spawn the background maintenance thread).
     - `add_handle_until` returns `Ok(())`, and only then does the operation (`get`, `set`, `checkpoint`, etc.) fail at `lease` / `check_usable` with `Error::Unusable`, leaving the handle reopened (`handles == 1`, `retired == false`, `closed == false`) with a newly opened SQLite connection pinned on the unusable database file.
  2. **Violates Claim 3** ("never unlinks or truncates a file on the parent's behalf"). When the last handle on an unusable `Store` in the child is released by `cache.close()` or `Drop for Cache`, `Store::release_handle_within` (`store.rs:1091-1093`) calls `self.sweep_value_dirs(spill::SWEEP_MIN_AGE)` without checking `!self.is_poisoned()`. Because `Gate::reset_in_child` cleared inherited `HeldShare` levels, `GATE.own_depth()` is `0` in the child, so `spill::sweep` walks the parent's active cache directory on disk, unlinking stale `.tmp` files and `rmdir`-ing empty value directories.
  3. On `Cache`, `cache.evict(None)` (`cache.rs:671`) returns `Ok(0)` before touching `self.handle` or `check_usable()`, so in an unusable child `cache.evict(None)` silently returns `0` instead of raising `ForkedInsideTransactionError` (whereas `FanoutCache.evict(None)` at `fanout.rs:511` calls `self.refuse_fan_out("evict()")?` first and raises `ForkedInsideTransactionError`). Similarly, `Cache.remove_old_formats()` (`cache.rs:327-329`) and `FanoutCache.remove_old_formats()` (`fanout.rs:220-222`) do not check usability before scanning and unlinking old-format files in `config.root`.
- **Evidence:** Reproduced in `/tmp/dco-review-03ad2038` via `cargo test` (`probe_6_fork_child_reopen_and_fanout_open_shards`), and verified by line-by-line inspection of `store.rs:1034-1111`, `cache.rs:327-329, 670-671`, and `fanout.rs:220-222`.
- **Confidence:** Confirmed and reproduced.
- **Fix idea:**
  1. In `Store::add_handle_until` (`store.rs:1040`), call `self.check_usable()?;` immediately after `let gate = enter_until(deadline)?;` (before `if !claim()`).
  2. In `Store::sweep_value_dirs` (`store.rs:1105`), add `|| self.is_poisoned()` to the early return (`if self.role != Role::Plain || GATE.own_depth() > 0 || self.is_poisoned() { return; }`).
  3. In `Cache::evict` (`cache.rs:671`), when `encode_tag(Some(tag))?` is `None`, check `self.handle.run(timeout, |_| self.handle.store.check_usable()).map_err(to_py_err)?;` before returning `Ok(0)`; in `Cache::remove_old_formats` and `FanoutCache::remove_old_formats`, check `self.handle.store.check_usable()` / `self.refuse_fan_out("remove_old_formats()")` first.
- **Reproduction:**
  ```rust
  // Inside child after fork with a transaction held on `store`:
  gate::end_fork_child();
  store.release_handle();
  assert_eq!(store.handles(), 0);
  let closed = AtomicBool::new(true);
  let res = store.add_handle_until(Instant::now() + T, Maintenance::OFF, || closed.swap(false, Ordering::AcqRel));
  assert!(res.is_ok()); // Succeeds, opens a new FilePin connection, flips `closed` to false, sets `handles` to 1!
  assert_eq!(store.handles(), 1);
  ```

### M2. `Caches._resolve` and `DjangoCache.open_handle` serve an inherited `NullCache` in an unusable child during the parent's retry window, and `Caches` serves `NullCache` for a disabled cache that was already opened in the parent

- **Severity:** Medium
- **Tier:** Patch
- **Where:** `python/diskcache_oxide/caches.py:379-425` (`Caches._resolve`, `Caches._open`) and `python/diskcache_oxide/djangocache.py:553-577` (`DjangoCache.open_handle`).
- **Trigger:**
  1. **Inherited retry window (`_failed` in `Caches`, `unavailable` in `DjangoCache`):** In the parent, handle A holds a transaction (`with c.transact():`) or write lock on a cache directory while another thread (or lookup) accesses a durable `Caches` registration (`caches['x']`) or `DjangoCache` backend on the same directory with a short timeout. That open times out and records `self._failed['x'] = (now + 1.0, NullCache())` (or `unavailable[self.directory] = (now + 1.0, NullCache())`, or `now + 10.0` on another open failure). The parent then forks inside `with c.transact():`. Within the remaining 1 s (or 10 s) cooldown window, the child accesses `caches['x']` or `django_cache.get(...)` / `django_cache.set(...)`.

In the child, `poison_live_holds()` and `pool::files_with_connections()` use `try_lock()` exclusively: if `LIVE_HOLDS` or `pool::REGISTRY` was inherited locked (an unhooked fork while another thread mutated the registry), `mark_all_unusable()` sets `ALL_UNUSABLE = true`; if an individual `PoolShared.state` mutex was inherited locked, `files_with_connections()` reads `pool.file` (stored outside the mutex on `PoolShared`) and marks that file unusable.
- **Claim 3 (No parent fd closed, and no parent file unlinked or truncated by the child):** `PooledConn::forget`, `FilePin::drop`, and `close_pinned` all call `std::mem::forget` on connections whose `generation != gate::generation()`, so `sqlite3_close` never runs on an inherited connection in the child (and even on `Store::drop` behind a pending fork, `Pool::drop` and `FilePin::drop` leak when `try_enter_shared` returns `None`). `close_pinned` (`store.rs:2491-2494`) returns `(Err(Error::ForkPoisoned), Vec::new())` when `pinned.generation != gate::generation()`, so neither `files.removed` nor `files.created` from the parent's uncommitted transaction is unlinked by the child. Between the parent's `begin_fork` and `end_fork_parent`, `Pool::checkin` and `Pool::adopt` check `gate::forking_in_parent(gate)` (which checks `std::process::id() == FORKING_PID`, so it is false in the child before `end_fork_child` runs) and close surplus connections with `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE` set. The one place a child still touches the parent's cache directory on disk is `Store::release_handle_within` calling `sweep_value_dirs` on an unusable store and `remove_old_formats()` (filed under **M1**).
- **Claim 4 (`Gate::reset_in_child` and `HeldShare` epoch):** Checked in `gate.rs:514-525, 607-623, 744-793` and verified with Shuttle (`gate::model::m22`, 10,000 iterations). `reset_in_child()` increments `self.epoch` (`SeqCst`), masks `owner.levels` down to `FLAGS` (preserving `FORKING` until `ForkGuard::finish` clears it two lines later), and stores the forking thread's `t.depth.get()` into `self.counts` (clearing both `parked` in the high 32 bits and every other thread's or share's `holders` in the low 32 bits). Any `HeldShare` created before the fork has `share.epoch != gate.epoch`, so `HeldShare::try_enter` returns `ShareEntry::Inherited` and `HeldShare::drop` returns immediately without touching `owner.levels` or `gate.counts`, even if another thread in the parent was halfway through `try_enter` or `HeldShare::drop` at the instant of `fork()`.
- **Claim 7 (`store_seq` monotonicity and index seek on bundled SQLite 3.54.1):** Checked `EXPLAIN QUERY PLAN` on the bundled SQLite 3.54.1 across all five statements (`upsert` including its `ON CONFLICT DO UPDATE` path, `UPDATE_NUMBER_SQL`, `raise_seq_floor`, and `seq_snapshot`). Every one compiles the scalar subquery `(SELECT MAX(store_seq) FROM cache WHERE store_seq < 4611686018427387904)` into a single `SEARCH cache USING COVERING INDEX cache_store_seq (store_seq<?)`. Because SQLite's B-tree order sorts `INTEGER` and `REAL` numerically (via exact `sqlite3IntFloatCompare`) before all `TEXT` and `BLOB` values, the `< 4611686018427387904` range excludes all `TEXT`, `BLOB`, and numbers $\ge 2^{62}$. Among sound rows with an intact `state.next_seq` and `store_seq < 2^62 - 1`, `store_seq` never repeats. The edge cases where `state.next_seq` itself is a fractional `REAL` or non-integer, or a row has `store_seq = 2^62 - 1`, are filed as **M3**.
- **Claim 8 (Compare-and-delete safety in `check(fix=True)`):** Checked `RowWriter::delete_damaged` (`rows.rs:311-319`) and `Store::check_rows` (`check.rs:238-244`). In `check_column_types`, `delete_damaged(id)` re-evaluates `WHERE id = ?1 AND {WRONG_TYPE}` inside the `DELETE` transaction under the write lock, so a concurrent overwrite (which keeps `id` and writes valid column types) causes `delete_damaged` to match 0 rows and spare the healthy row. In `check_rows`, `delete_version` deletes `WHERE id = ?1 AND store_seq = ?2`; because an in-place overwrite (`ON CONFLICT DO UPDATE`) evaluates `max_store_seq!()` while the existing row is still in `cache`, any overwrite of a row with an integer `store_seq < 2^62` receives a strictly larger `store_seq`, and any overwrite of a row with `store_seq >= 2^62` receives a `store_seq < 2^62`, so `store_seq` always changes on overwrite and `delete_version` never deletes a row that an overwrite made healthy. The cases where `check(fix=True)` raises on damaged `size` values or skips `filename = ''` / page-boundary duplicates are filed as **M4**.
- **Claim 9 (`lenient_filename` and path traversal safety):** Checked `rows::lenient_filename` (`rows.rs:23-32`) and `spill::value_path` (`spill.rs:231-236`). `lenient_filename` maps `Null` to `None`, valid UTF-8 `Text` to `Some(String)`, and any non-UTF-8 `Text`, `Blob`, `Integer`, or `Real` to `Some("<damaged filename>")`. Every path construction from a row's `filename` (`spill::read`, `spill::open_for_read`, `Store::unlink`, and `Store::check_rows`) passes through `spill::value_path`, which requires `relative.split_once('/')` to yield `(dir_name, file_name)` where `dir_name` is 2 lowercase ASCII hex chars, `file_name` ends with `.val` preceded by 32 lowercase ASCII hex chars, and the 32 hex chars start with `dir_name`. No damaged `filename` can produce a path outside the cache directory or match a non-value file inside it.
- **Area C (Background checkpoint `wal::passive_copied_everything`):** Checked `wal.rs:90-98`, `store.rs:1730-1759`, and `background/turn/tests.rs:472-534`. SQLite's `PRAGMA wal_checkpoint(PASSIVE)` returns `(busy=1, log=-1, checkpointed=-1)` when another connection holds the checkpoint lock. Previously `log == checkpointed` (`-1 == -1`) was misread as "everything copied", sending the background turn into `TRUNCATE` under the write lock. `passive_copied_everything(busy, log, copied)` now requires `busy == 0 && log >= 0 && copied == log`, and when `busy != 0` or `copied < log`, `background_checkpoint` returns `Some(Outcome::Busy)` without taking the write lock and without arming the close path's WAL backoff.
- **Area D2 (`incr` / `decr` rejecting `inf` and `NaN`, D-064):** Checked `crates/diskcache-oxide-py/src/cache.rs:2882-2894` (`number`) and `crates/diskcache-oxide-core/src/ops.rs:1174-1215`. `number()` checks `!real.is_finite()` on both `delta` and `default` and raises `ValueError("{name} must be a finite number, not {real}")` before any store call. If a stored row already contains a non-finite float (written via `set('k', float('inf'))` or `float('nan')`), `Number::checked_add` (`ops.rs:1182-1197`) refuses `NaN` with `Error::NotNumeric` (`TypeError`) and refuses `inf + (-inf)` with `Error::NotNumeric`, while `inf + finite` stays `inf` (and finite overflow `1e308 + 1e308` yields `Error::Overflow` -> `OverflowError`, keeping the stored value finite).
- **Area D3 (`check(fix=True)` unlinking orphan value files under the write lock):** Checked `Store::remove_unnamed` (`check.rs:350-366`). Before unlinking an old value file that no committed row names, `remove_unnamed` enters `self.write(timeout, ...)` (`BEGIN IMMEDIATE`), re-queries `SELECT 1 FROM cache WHERE filename = ?1`, and only unlinks the file if still unnamed. Because SQLite's write lock prevents any other connection from holding an uncommitted write transaction, a long-running transaction that wrote a `.val` file over an hour ago either holds the write lock (making `remove_unnamed` wait up to `timeout`) or has already committed/rolled back before `remove_unnamed` checks `cache`.
- **Area D4 (Per-handle `types=` registry shadowing global registrations by name):** Checked `crates/diskcache-oxide-py/src/codec/registry.rs:259-287` (`Snapshot::by_type`, `Snapshot::by_name`). When a handle has a local `TypeRegistry` (`self.local`), `by_type` checks `local.by_type` first, then checks `global.by_type`, and if a global registration is found under `entry.name`, checks `local.by_name(&entry.name)`. If the local registry maps that name to a different class, `by_type` returns `Err(shadowed(...))` (`TypeError`), preventing a value from being encoded under a tag name that the same handle's decoder would decode as a different class.
- **Area D5 (`vacuum` and post-vacuum checkpoint sharing one deadline):** Checked `Store::vacuum` (`check.rs:425-445`). `vacuum` computes `let deadline = crate::lockwait::deadline_after(Instant::now(), timeout);` before running `VACUUM`, and passes `deadline.saturating_duration_since(Instant::now())` to the `checkpoint` that follows, so the two steps share one `timeout` budget.
- **Area D6 (`TakeAllStack` `unsafe impl Sync` in `stack.rs`):** Checked `crates/diskcache-oxide-core/src/stack.rs:15-45`. `TakeAllStack<T>` holds `head: AtomicPtr<Node<T>>` and `_marker: PhantomData<Mutex<T>>`. The explicit `unsafe impl<T: Send> Sync for TakeAllStack<T> {}` (with a compile-time `assert_sync::<TakeAllStack<Cell<u8>>>()`) is sound because every node is heap-allocated by `push(value: T)` before its pointer is published via `compare_exchange_weak(..., AcqRel, Acquire)`, and `take_all()` claims the entire linked list exclusively via `self.head.swap( null_mut(), AcqRel)` before reading or dropping any `Node<T>::value`, so no `&T` is ever shared across threads.

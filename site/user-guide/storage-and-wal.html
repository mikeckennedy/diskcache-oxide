Storage and WAL

Nobody restarts a cache. It sits inside a worker process for weeks, and whatever it does to memory and disk, it does slowly and out of sight, until an alert fires at a bad hour. So how much a cache uses has to be something you set, not something you discover. This page covers what diskcache-oxide puts on disk, and the settings that keep memory and disk where you put them.

What’s in the directory

Open the directory and this is what you find:

/var/cache/my-app/
├── diskcache-oxide.sqlite        # keys, metadata and small values
├── diskcache-oxide.sqlite-wal    # SQLite's write-ahead log
├── diskcache-oxide.sqlite-shm    # SQLite's shared-memory index for the log
└── 3f/
    └── a2/
        └── 3fa2…c91e.val         # one large value

The database file carries a format version. A future build that can’t read it raises FormatMismatchError rather than guessing.

Small values inline, large values in files

  • Under 64 KiB (after encoding), a value is stored in its database row. Reading it is one indexed lookup.
  • 64 KiB or more, it’s written to its own file, and the row points to it. This keeps the database small and its page cache hot, and large values stream straight from the file.

Writing a large value never holds the database lock while the bytes go to disk: the value goes to a temporary file first, then inside a short transaction the file is renamed into place and the row updated. The old file is removed after the commit, and file names are never reused.

A reader racing an overwrite always gets a whole value, old or new. If a value’s file really is gone (deleted by hand, or cut short by a crash, since value files aren’t fsynced), get returns the default and the orphaned row is cleaned up, so in and len don’t keep reporting an entry that can’t be read.

Size limit and eviction

cache = Cache('/var/cache/my-app', size_limit=500 * 1024 * 1024, cull_limit=10)
  • size_limit is the cache’s disk budget in bytes: the database plus value files. The default is 1 GiB and the minimum is 1 MiB.
  • When a set() finds the cache over its limit, it evicts up to cull_limit of the least recently stored entries (default 10). cull() evicts down to the limit on demand.
  • volume() reports the current size.

Least-recently-stored eviction means a get never has to write anything, which keeps reads fast and lets any number of processes read in parallel. LRU and LFU policies are planned for Phase 6a.

Memory: max_connections and sqlite_cache_size

diskcache gives each thread its own connection with a 32 MiB page cache plus a 64 MiB memory map, so its memory grows with your thread count. diskcache-oxide bounds it:

cache = Cache(
    '/var/cache/my-app',
    max_connections=8,       # connections per database file, per process (default 8)
    sqlite_cache_size=256,   # 4 KiB pages per connection: 1 MiB (default)
)

SQLite’s memory for a directory stays around max_connections × sqlite_cache_size pages, 8 MiB per process by default, however many threads use it. The 1 MiB default is the smallest size that left hot reads, writes and the threaded benchmarks unchanged. If your cache is large and read uniformly at random, raising it helps: 2,000 pages measured about 17% faster on that workload.

The write-ahead log

SQLite’s write-ahead log (WAL) is a ledger of recent changes kept beside the database, and it’s what lets readers and a writer work at the same time: the writer appends to the ledger while readers keep reading the book. Every so often SQLite folds the ledger back into the book and starts over. The catch in a multi-process app is that it can only start over when it finds a moment with no readers, and with readers in other processes that moment may never come. A burst of writes (a big fill, or a clear()) grows the log to fit the burst, and then it stays that size. diskcache-oxide’s soak tests saw logs over 1 GiB next to databases of a few MiB.

diskcache-oxide handles this in layers, from free and always on to explicit.

Always on: wal_size_limit

cache = Cache('/var/cache/my-app', wal_size_limit=64 * 1024 * 1024)   # the default

This tells SQLite to trim the log back to half the limit (32 MiB by default) whenever it resets, and scales how often SQLite checkpoints automatically. These are connection settings, so they never pause anything. At normal load they keep the log at a few MiB.

On demand: checkpoint()

cache.checkpoint()   # True if the log was reset and truncated

checkpoint() copies the log into the database and truncates it to zero. It waits briefly for in-flight reads, retrying up to the cache’s timeout, and returns False instead of raising if other processes keep the database busy. Call it when a short pause suits your app: at shutdown, in a maintenance job, or after a large clear().

At close

close() runs the same checkpoint when this is the process’s last handle on the cache and the log is over half the limit, waiting at most a second. A small log, the usual case, costs nothing extra. Pass close(checkpoint=False) to skip it.

Opt-in: automatic checkpoints

cache = Cache('/var/cache/my-app', wal_checkpoint='auto')

With 'auto', writes check the log (at most every 250 ms or 64 writes) and checkpoint it when it’s over the limit, with the interpreter released. Readers in other processes can get in the way for a moment, so it tries the final truncation up to 8 times, a couple of milliseconds each, before backing off for a second. It never fails a write. It isn’t the default because on a saturated disk the write that triggers the checkpoint can still pause for a long time, and no write should pay for housekeeping unless you asked for it. The plan is to move this into a background maintenance thread so writes never pay for it at all. Writes queue behind a checkpoint for tens of milliseconds, so a timeout under about 35 ms can time out behind one.

The limit is a target, not a bound

wal_size_limit says where the log should stay, not where it’s guaranteed to stay. Sustained writes from several processes near flat out can take it to tens of times the limit: we measured 6 GiB on free-threaded 3.15 and 21 GiB on 3.14 in 10 minutes, against a 64 MiB limit. It’s much smaller below flat out, for example 250 MiB at about 2,600 writes per second across 3 writers in auto.

In the default manual mode, with busy readers in other processes, the log grows until something checkpoints. If your app has that shape, use wal_checkpoint='auto' or call checkpoint() periodically. A script should call checkpoint() or close() after a large fill.

Maintenance calls

All of these work in chunks, release the database between chunks so other writers get in, and are safe to call while other processes use the cache:

  • expire() removes every expired entry and its value file.
  • clear() removes every entry that existed when it started, and keeps writes that land while it runs.
  • cull() evicts down to size_limit.

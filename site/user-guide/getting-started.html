Getting started

A Cache is a directory. That’s the whole mental model, and it carries further than it looks: open the same directory from any number of threads and processes and they all share one cache, nobody has to be told about anybody else, and the entries are still there after a restart, because a directory doesn’t restart. This page covers installing diskcache-oxide, the everyday operations, the handful of things that only start to matter once several processes are involved, and how to shut down cleanly.

Install

pip install diskcache-oxide
  • Python: CPython 3.14 or 3.15, including the free-threaded builds (3.14t and 3.15t).
  • Platforms: macOS and Linux. Wheels cover macOS on Apple Silicon and Linux (glibc) on x86_64 and aarch64; anywhere else pip builds from source, which needs the latest stable Rust toolchain. Windows support is planned.
  • Dependencies: none at runtime. SQLite is bundled and compiled in, so your system’s SQLite version doesn’t matter (diskcache_oxide.sqlite_version() reports the one in use).

Open a cache

from diskcache_oxide import Cache

cache = Cache('/var/cache/my-app')

The directory is required. If it doesn’t exist, diskcache-oxide creates it, readable and writable only by your user (0700). That’s deliberate: anyone who can write to a cache directory gets to decide what your app reads next, so the directory starts out as private as your home directory.

So a cron job, an admin script or a container running as a different user can’t open a directory your app created: it gets PermissionError (“Permission denied”). Run everything that shares a cache as the same user. Loosening the directory’s mode yourself doesn’t help, since the folders diskcache-oxide creates inside it for large values are owner-only too.

Every process that should share the cache opens the same path. Inside one process, opening the same directory twice gives two handles on one shared engine, with one connection pool between them.

Close it, or use with

with Cache('/var/cache/my-app') as cache:
    cache.set('greeting', 'hello')

close() returns the handle’s SQLite connections. Once the last handle on a directory in a process closes, nothing in that directory is held open, so it’s safe to move or delete.

Store and read values

cache.set('user:42', {'name': 'Sam', 'roles': {'admin', 'editor'}}, expire=600)

user = cache.get('user:42')                 # the dict, with roles still a set
missing = cache.get('user:99', default={})  # {}

value, expires_at = cache.get('user:42', expire_time=True)
  • Keys are str. Other key types raise TypeError for now (they’re planned).
  • Values can be str, bytes, int, float, bool, None, and lists, tuples, dicts, sets and datetimes made of those. They come back as the types you stored. See Serialization.
  • expire is in seconds. Leave it out for an entry that never expires. touch(key, expire=...) changes the expiry of an existing entry.

Dictionary syntax

cache['alpha'] = 100
assert 'alpha' in cache
assert cache['alpha'] == 100
del cache['alpha']        # KeyError if it's missing, like a dict

Remove values

cache.delete('user:42')             # True if it was there
value = cache.pop('session:7')      # the value, or the default if it was missing

Atomic operations across processes

Picture eight gunicorn workers, each with a scheduler that fires the same hourly job. You want it to run once. There’s no leader, no Redis, and no way for the workers to talk to each other except through the cache. That turns out to be enough. Each call below is a single SQLite transaction, so it’s atomic across every thread and process using the directory, and “store only if absent”, done atomically, is a lock if you squint. These are what make a shared cache useful for coordination, not only for caching.

# Store only if the key is absent (or expired). Exactly one caller wins.
if cache.add('job:refresh-feeds', os.getpid(), expire=3600):
    refresh_feeds()

# Counters. incr() keeps the entry's existing expiry.
cache.incr('page_views')          # 1
cache.incr('page_views', 5)       # 6
cache.decr('page_views', 2)       # 4

incr() on a missing key starts from default (0). Pass default=None to get a KeyError instead. A key holding a non-number raises TypeError.

To make several calls atomic together, group them with with cache.transact() as tx:. See Transactions.

List keys

for key in cache.iterkeys(prefix='user:'):
    print(key)

iterkeys() yields keys in sorted order (reverse=True for descending), and with prefix= it’s an indexed range scan: 400,000 keys scan in about 10 ms, against about 25 seconds for diskcache. Iterating the cache itself (for key in cache) yields keys in insertion order.

Size limits and eviction

cache = Cache(
    '/var/cache/my-app',
    size_limit=500 * 1024 * 1024,   # 500 MiB (default 1 GiB, minimum 1 MiB)
    cull_limit=10,                  # entries evicted per set() when over the limit (default 10)
)

When the cache’s on-disk volume goes over size_limit, each set() evicts up to cull_limit of the least recently stored entries. cache.volume() reports the current size in bytes.

Maintenance calls, all safe to run while other processes use the cache:

  • cache.expire() removes every expired entry and returns how many.
  • cache.clear() removes every entry that existed when it started, and keeps anything written while it runs.
  • cache.cull() evicts down to the size limit.

Timeouts

One process at a time commits to a database file. When another one is in the middle of doing so, your write waits its turn, up to the cache’s timeout (60 seconds by default), then gives up and raises diskcache_oxide.Timeout, a subclass of the built-in TimeoutError:

from diskcache_oxide import Cache, Timeout

cache = Cache('/var/cache/my-app', timeout=1.0)
try:
    cache.set('key', 'value')
except Timeout:
    ...  # the cache was too busy; carry on without it

Maintenance calls work in chunks, so they take the write lock many times. A request-sized timeout can cut an admin clear() off partway through, so clear(), expire() and cull() each take their own timeout= for that call. It bounds each chunk’s wait for the lock, not the whole call:

cache = Cache('/var/cache/my-app', timeout=1.0)  # for requests
cache.clear(timeout=10.0)                        # for the admin page

What else Timeout can mean, and what to do about every other exception the library raises, is in Errors and what to do about them.

Values that can’t be read

A cache outlives the code that filled it. Deploy a rename of a class you pickled, or have a disk hand back damaged bytes, and a row that read fine yesterday raises today. By default get raises, as diskcache does. But a cache is only a copy of data you can rebuild, so most apps would rather treat that row as a miss and move on. on_decode_error does that:

cache = Cache('/var/cache/my-app', pickle=True, on_decode_error='miss')
cache.get('homepage')  # None if the stored value can't be decoded; the bad row is deleted
  • 'miss' returns the default, deletes the bad row, and logs a warning on the diskcache_oxide logger. Only that exact stored version is deleted, so a fresh value another process wrote in the meantime survives, and the read never waits for the write lock to do it. If the lock is busy, the row stays and a later read tries again.
  • A value this version can’t read but another might, such as one written by a newer diskcache-oxide or one that needs a time zone this host lacks, is a miss too, but its row is kept. Reading it with the default 'raise' raises ForeignValueError, a subclass of CorruptValueError.
  • Pass a function instead to report the failure yourself, for example to Sentry. It’s called as report(key, exc) in place of the warning, after the row has been dealt with. Anything it raises is logged, and the read is still a miss.
  • Errors that aren’t about the stored bytes still raise: Timeout, MemoryError, an I/O error, and UnsafeValueError (a pickled value read by a cache without pickle=True, which is a configuration mistake, not damage). durable=True makes a Timeout, an I/O error or a RecursionError from a pickle hook a miss too.

It covers get, cache[key] (which raises KeyError) and pop. A row that stays (a foreign value, or a bad one whose delete had to be skipped) fails on every read, so each stored version is reported once per cache handle, not on every read.

pop decodes the value before it deletes the row, so a value that another version or host might read survives it. This table is the usual path; the fallback described below it removes the row first:

What went wrong 'raise' 'miss' or a function durable=True, with its default 'miss' or a function
A foreign value raises ForeignValueError, row kept returns the default and reports, row kept the same as 'miss'
UnsafeValueError raises, row kept raises, row kept raises, row kept
An unreadable value (malformed bytes, a failing unpickle, a registered type’s decode raising about the row) deletes that version, then raises deletes that version, returns the default and reports the same as 'miss'
An unreadable value, and that delete fails raises the delete’s error, row kept raises the delete’s error, row kept returns the default and reports both, row kept
Timeout, an I/O error or RecursionError from a pickle hook or a registered type’s decode raises, row kept raises, row kept returns the default, row kept, reported once per stored version
RecursionError from a value too deep for this thread’s stack raises, row kept raises, row kept returns the default, row kept, reported once per stored version
MemoryError or a BaseException from a pickle hook or a decode raises, row kept raises, row kept raises, row kept
The value decoded, and the delete fails raises the delete’s error, row kept raises the delete’s error, row kept returns the default, never the value, row kept

durable=True with an explicit on_decode_error='raise' follows the 'raise' column, except that when an unreadable value’s delete fails it raises the decode error rather than the delete’s.

If that delete itself fails, for example with Timeout, its error is raised under every policy with the decode error as its __cause__, unless durable=True, and the row stays.

A value still goes to exactly one caller, because pop deletes only the version it decoded. A pop that loses that delete to another writer reads again, and after 8 losses it falls back to removing the row first and decoding afterwards, so it can’t starve. If its timeout has run out by the time it loses, it raises Timeout instead: this pop deletes nothing, and whatever the other writer left stays. There are two limits:

  • That fallback is the one place a failed decode can cost the value, because the row is already gone: a foreign value in a known mode, or any error from a pickle hook (Timeout, MemoryError, an I/O error). It’s possible on a heavily overwritten key, since a pop can lose while it queues for the write lock. How often it happens hasn’t been measured yet.
  • Like get, pop doesn’t wait to clean up a row whose large value file has gone missing. It returns the default, and if the write lock is busy the row can stay until a later pop or write removes it.

A cache that can’t take a request down

It’s 3 a.m., the disk under /var/cache is full, and every request that writes to the cache is now a 500. Nothing the cache held was precious: it was all a copy of something the database still has. If every caller can fall back to its source of truth, an outage in the cache should cost you speed, not requests. durable=True makes that the rule for the calls a request makes:

cache = Cache('/var/cache/my-app', timeout=1.0, durable=True)
page = cache.get('homepage')  # None if the cache is locked, full, broken or the disk failed

“Durable” here means the cache keeps your app running. It doesn’t mean what it means in a database, where a durable write survives a crash. This option does the opposite: it can drop writes. It’s off by default.

An operational failure is a Timeout, an OSError (disk full, I/O), a SQLite error including a damaged database, or a child forked inside a transaction that can’t write. On a single-key call it’s answered like this:

Call On an operational failure
get, pop the default; get(key, expire_time=True) gives (default, None)
key in cache False
cache[key] raises KeyError
set, add, touch False
cache[key] = value drops the write
incr, decr default + delta or default - delta, as NullCache does. default=None raises KeyError
delete False
del cache[key] raises KeyError

These always raise:

  • Bugs. A non-str key, a value that can’t be stored without pickle, a non-numeric incr, an incr past 64 bits, UnsafeValueError, and misusing a transaction.
  • MemoryError and KeyboardInterrupt. That includes SQLite running out of memory.
  • Admin calls. clear, expire, cull, checkpoint, len, volume and iteration, because their callers need the truth, and most have their own timeout=. checkpoint still returns False when it’s only busy.
  • The constructor, and starting a transaction. Use Caches if opening shouldn’t raise: it gives you a NullCache until the cache can open.
  • Anything inside a transaction you hold on this cache. A dropped write there would break the transaction’s atomicity.
  • Errors from your own code, other than the pickle hooks on a read described above. A clock= function that raises, or a pickle hook on a write, raises as usual, even if what it raises is a Timeout.

on_decode_error defaults to 'miss' under durable=True, and a value you pass wins.

What a dropped call costs

A failure reaches you as “wasn’t there”, so know what each one means before you turn this on.

  • A dropped set, delete, pop or version-bump incr serves stale data. The old entry stays. It’s served until it expires, and with no expiry that means forever, or until a later write replaces it. delete returns False, the same as for a key that wasn’t there, so your code can’t tell. The log line is the only signal. If stale data would be a real problem, give those entries an expiry.
  • A pop whose delete fails returns the default, not the value, since the row is still there and a later pop could deliver the value a second time.
  • A fake incr isn’t a count. It’s what a NullCache returns, so a rate limiter fails open. Don’t use one as an id: two callers can get the same number.
  • add fails closed. It returns False under durable=True, but True on a NullCache, so Caches can give you either answer for one key. Use a separate handle without durable for claims and locks, and treat its exceptions as “not claimed”.

It doesn’t bound time

A call still waits up to its timeout before it gives up, so pair durable=True with a small timeout=. Not too small: timeout still has to exceed the work in flight, plus a fork, plus the interpreter handing over, or ordinary forks turn into misses. Beside busy threads on a GIL build, that hand-over alone takes tens to hundreds of milliseconds. See How long a call waits for a fork.

Reporting

Every swallowed failure is counted in one of three groups, and logged on the diskcache_oxide logger, so one group can’t hide another:

Group Level What’s in it
Busy WARNING Timeout: a lock or a fork outlasted timeout
Failing ERROR Everything else: a full disk, an I/O error, a damaged database
Lost invalidations ERROR Any failed delete

Each group logs its first failure at once, then at most once a minute per cache handle, with counts by operation since its last line: get: 1204, set: 37. An outage can be thousands of failures a second, and that’s one line a minute. Failures after a group’s last line stay counted until its next one, or until you call close(), which logs what’s left. Dropping a handle without close() doesn’t. An outage that ends within the minute can therefore show only its first failure until then, which is why each line says more may follow. A hook outage on a read is reported once per stored version, as in the pop table above, and counted here as busy for a timeout and failing otherwise, with no line of its own: the group’s next line includes it. Time comes from the failing call’s clock, so clock= drives it in tests. cache._durable_stats() has the running totals by group and operation, the place to look for “how many invalidations did we lose?”. It’s a private hook for now, like _wal_stats().

The limit is per handle, so a with Cache(...) per request logs on every request during an outage. A handle from Caches is opened once, so it isn’t affected.

More than one process writing

A single Cache has one write lock per directory. Reads never wait for it, but every write does, so eight worker processes that all bump counters are eight writers lining up for one lock. If your app runs several worker processes that write often (counters, rate limits, job claims), open a FanoutCache instead: it spreads the keys over several databases, each with its own lock, and in the repository’s benchmark it holds its rate at 8 processes where a plain Cache falls to about 40% of its one-process rate. For one process, or mostly reads, a plain Cache is the simpler choice.

Shutting down

Call cache.checkpoint() at shutdown if you can. It isn’t required. With readers in other processes, a burst of writes (a big fill, or a clear()) can leave SQLite’s write-ahead log much larger than the database, and SQLite only shrinks it when it gets a moment with no readers. checkpoint() makes that moment: it waits briefly for in-flight reads, copies the log into the database, and truncates it. It returns False instead of raising if other processes keep it busy.

close() does the same by default, but only when the log is large, and it waits at most a second, so closing stays cheap. Storage and WAL has the details.

Testing code that uses a cache

Two tools help here:

  • NullCache is a cache that’s switched off: every write succeeds and every read misses. Swap it in for tests or local development without touching call sites. See NullCache.
  • clock= controls the cache’s clock. diskcache-oxide reads time natively in Rust, so patching time.time doesn’t affect it on its own. Pass clock=lambda: time.time() and the cache follows your patched clock:
cache = Cache(tmp_path, clock=lambda: time.time())
